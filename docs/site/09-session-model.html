09 会话模型（Session Model）

本章要点：会话由一组固定字段描述，其中 direction 是必需的， 用于区分「我是接收方」还是「我是发送方」。session_id 由 Server 生成且在 Server 生命周期内必须唯一； 同一 client_id + file_hash 正在同步时必须复用既有会话。接收方必须持久化 临时文件、位图与会话元数据，以便进程 / 设备重启后恢复。

direction 字段（规范性）

direction 字段是必需的（规范性）：本协议的 missing_chunks 是双向消息， 其含义依赖会话方向（见 06 章）。Server 侧的会话记录必须能区分 「我是接收方」还是「我是发送方」，否则无法正确解释对端的缺失报告。

与控制连接的关系（规范性）

  • 一个 device_id（一条控制连接）可以承载多个并发会话； session_id 用于区分。
  • Server 必须为每个会话记录其所属的控制连接； 连接断开时，该连接上承载的全部会话进入中断处理（见 13 章）。
  • 会话不得跨连接迁移 —— 恢复只能通过 login 的恢复列表 重新建立关联（见 06 章、13 章）。
  • 数据面端口可以被多个会话共用：UDP 包头中的 session_id 足以区分（见 08 章）。

创建规则

#规则说明
1 session_id 由 Server 生成 Server 必须保证在自身生命周期内 session_id 唯一； 冲突时必须重新生成而不是复用。
u32 的空间有限，实现不得使用裸时间戳低 32 位 （秒级回绕 136 年、毫秒级回绕 49 天）。推荐使用「随机高位 + 递增低位」或 Snowflake（含机器位）等方式。
冲突后果严重：session_id 同时是控制面关联键与 UDP 头字段（见 08 章）， 串号会导致跨会话数据污染。
2 同文件正在同步 → 返回现有会话 「同文件」的判定键为 client_id + file_hash（同一客户端的同一内容）。
返回现有会话时，upload_accept 必须复用既有的 session_id， 并重新下发当前的 window / chunk_size / udp_port。
3 已存在完整文件 → 秒传 Server 侧已存在相同 file_hash 的完整文件时，upload_accept.file_exists = 1（bool 真）， 走 10 章定义的秒传路径（不进入 TRANSFERRING，不产生位图）。
4 否则新建会话并生成新的 session_id —

持久化（规范性）

接收方必须持久化以下状态，使其在进程重启或设备重启后仍可恢复：

  • 临时文件（含已写入的数据）
  • 位图（各 chunk_id 的接收状态）
  • 会话元数据（session_id / direction / chunk_size / chunk_count / 临时文件路径）
  • 位图必须能写入持久化副本并从该副本恢复；持久化格式与存储位置由实现决定。
  • 写入与位图更新的先后顺序由实现决定，但必须保证： 位图标记为「已接收」的块，其数据已经落在临时文件中 —— 否则恢复后会把未落盘的块当作已接收，导致空洞永不重传（见 13 章「空洞块的补发」）。
注意：位图标记与数据落盘的顺序由实现决定，但「先落盘、后标记」是保证不产生空洞块的唯一前提。

  • 会话活动超时：60 秒内无任何控制面交互或数据面活动的会话， Server 必须将其置为 ABORTED 并清理临时文件 / 位图 / 元数据。
  • 超时层级（规范性）：控制连接的空闲超时（30 秒，见 06 章「心跳与超时」） 必须早于会话活动超时（60 秒）触发。
  • 客户端在超时前可经 login 的恢复列表恢复；超时后恢复不合法 （ABORTED 是终态，见 10 章）。
  • 该阈值对应 19 章的 TIMEOUT_NO_ACTIVITY。

版本策略（规范性）

  • 版本号形如 major.minor.patch，当前为 v0.3.0。
  • 版本号只在上游明确指示时变更。 未获明确指示时，规范的任何修订（措辞澄清、勘误、章节增补） 不得变更版本号 —— 修订必须记入本章的「修订记录」。
  • 每次修订必须在本章留下记录：改了什么、涉及哪些章节。
  • 设计阶段的含义：本规范当前未冻结任何实现， 线路格式与消息集仍在演进；版本号在此阶段不承载兼容承诺， 「某版本号是否可互通」在本阶段没有意义—— 判断标准只有一条：以 06、07、08 章正文为准。 冻结首个实现之后，版本号才回到「标识兼容边界」的职责。
  • 0.x 阶段的兼容性：本规范处于 0.x 阶段，minor 变更可能是不兼容的 （例如 v0.3.0 的控制面与早期草案即不兼容）。 因此 08 章「版本比较规则」中「major 相同即视为兼容」的结论 必须结合本章与 06 章的消息集共同判断， 不得仅凭 minor 不同就假定可互通。

换言之：版本号是标识当前规范状态，不是自动递增的计数器。

已知限制

  • 不兼容：v0.3.0 的控制面与早期草案（MQTT）无法互通 —— 传输层、帧格式与消息集均已改变。升级必须同时升级两端。
  • 同一版本号下的两套线路格式：按上游指示，本次控制面二进制化未变更版本号。 因此 v0.3.0 这一版本号在修订过程中先后指代了 JSON 线路格式与 二进制定长线路格式两套互不兼容的格式。 实现必须以 06 章正文为准，不得仅凭版本号判断可互通性。
  • 控制帧现为二进制定长布局（见 06 章）：定长帧头 + 定长区 + 变长区， 无字段名重复开销。代价是可读性下降 —— 抓包不再自解释， 实现侧必须提供与 msg_type 对应的解码日志。
  • 同一版本号下的第三套线路格式：本轮 P0 修订再次改变了线路格式 （session_id 扩为 u64、控制帧新增 connection_window、TCP 数据面帧定稿）。 按上游指示本次修订未变更版本号， 因此 v0.3.0 这一版本号先后指代了 JSON、二进制（u32 session_id） 与 二进制（u64 session_id） 三套互不兼容的格式。 实现必须以 06、07、08 章正文为准，不得仅凭版本号判断可互通性。
  • 线路格式尚未冻结（设计阶段）：本规范处于 0.x 设计阶段， 线路格式仍在演进 —— 本轮即把控制帧与 TCP 数据面帧的帧头 改为「magic + frame_len + header_crc32」 （控制帧帧头 8 → 16 字节，TCP 数据面帧头 20 → 28 字节）。 版本号在设计阶段不承载兼容承诺：未发布过任何实现，也就没有"互不兼容"的对端。 实现必须以 06、07、08 章正文为准； 历史草案（JSON 载荷、session_id = u32 的二进制布局等）一律不再可用， 不得据其实现。
  • 断线恢复时，下载方向依赖 Client 提供恢复提示。 若 Client 崩溃导致本地位图丢失且无法重建， 该会话只能以 SESSION_NOT_FOUND / SESSION_ABORTED 失败。

待定议题

控制帧的紧凑二进制编码（已结项）

  • 结论：已实施。控制帧改为二进制定长布局（见 06 章「帧格式」与「消息体布局」）。
  • 落地形态：u32 magic | u32 frame_len | u32 header_crc32 | u8 msg_type | u8 flags | u8 body_version | u8 reserved | body， 消息体 = 定长区（表格式偏移/大小）+ 变长区（顺序固定）；全部小端序； 帧头 16 字节（magic = 0x574E414C，header_crc32 覆盖帧头其余 12 字节）。
  • 扩展规则：同一 msg_type 的定长区一旦发布即冻结； 新增字段只能追加在扩展区（变长区之后的尾部字节），接收方必须忽略扩展区。 这取代了原先「忽略未知字段」的 JSON 约定。
  • 配套变更：file_hash 改为 32 字节原始 Blake3；session_id 统一为 u32； result / direction / state / mode 改为 u8 枚举；proto_version 改为三个 u8； 错误码仍以符号名字符串承载（低频、需人工判读，不做数值化）。
  • 保留的代价：可调试性下降；实现侧需自备解码日志与抓包工具。

TCP 数据面通道

  • 现状：UDP 主通道 + TCP 兜底（见 05、07 章）。
  • 议题：是否将 TCP 提升为数据面主通道。
  • 收益：可删除 07 章的 PROBE 握手、11 章的 window / AIMD、 18 章的缺失分批与 08 章的包级 CRC32；吞吐不再受窗口大小与信用节奏的限制。
  • 代价：失去乱序写能力（TCP 交付有序），恢复起点退化为连续水位线； 且移动端 WiFi 的丢包不等于拥塞，TCP 拥塞控制的误判会显著降速 —— 而本协议的移动端客户端正依赖 UDP + 发送端本地 AIMD 规避这一点。
  • 倾向：维持 UDP 主通道。

TCP 降级通道的线路格式（已结项）

  • 结论：已实施。TCP 数据面帧格式见 07 章「TCP 数据面线路格式」。
  • 落地形态：u32 magic + u32 frame_len + u32 header_crc32 + u64 session_id + u32 chunk_id + u16 payload_len + u16 flags + payload； 全部小端序；帧头 28 字节；不携带载荷级 crc32（TCP 已提供字节流校验）， 但帧头携带 header_crc32 用于帧同步与失步检测。
  • 绑定帧：FLAG_BIND 帧承载 session_id，用于把 TCP 数据面连接绑定到 具体会话并完成权限校验（见 07 章）。
  • 语义对齐：chunk 边界、偏移映射、位图与裁决语义与 UDP 通道一致。

发送节奏的规范默认值方向（已结项）

  • 结论：burst_size 初值 = min(256, window)，与 window 解耦； batch_gap_us 初值 2000µs；window 规范默认值 8192、connection_window 16384 （见 11 章）。默认突发约 300 KB，AIMD 仍为推荐性发送端策略。

缺失列表的编码效率

  • 现状：18 章规定单条 missing_chunks 最多 4096 条，逐个 chunk_id 编码。 100 GB 文件缺失 1% 时需 217 批，按每批一个裁决周期计约 10.9 秒的串行地板。
  • 待办：评估 bitmap / range 编码（并为裁决引入 snapshot_version）。

写盘错误必须立即上报（已结项）

  • 本地存储失败须按 10 章「终止权」报告，不进入内容重传。

离线投递队列

  • 现状：主动投递只发生在控制连接存续期间； Client 离线时 Server 无法投递（09 章）。
  • 待办：评估是否引入 Server 侧的待投递队列（Client 重连后补投）， 以及队列的容量、过期与去重策略。

接收方的接受策略

  • 现状：协议只定义「接受 / 拒绝」的表达方式 （delivery_response + DELIVERY_DECLINED / STORAGE_FULL）， 具体策略（自动接受、询问用户、配额上限、静默时段）属产品决策。
  • 待办：由实现定义策略，并在 delivery_response.code 中给出可区分的原因， 以便 Server 侧做退避决策。

下载方向的秒传（可选扩展）

  • 现状：秒传路径只覆盖上传方向（Server 侧已有相同 file_hash 的文件）。 下载方向没有等价机制 —— 客户端本地已有该文件时，只能自行跳过下载， Server 侧的素材记录不会被更新。
  • 待办：评估是否在 download_start 中增加「本地已有该文件」的声明位， 使下载方向也能走秒传路径。

分块摘要清单（可选扩展）

  • 现状：摘要对帐已能在零内容流量下定位差异区间并定点修复， 代价是每端约 2N 的读盘与哈希。
  • 待办：评估「一次性下发分块摘要清单」（1 MB 粒度约 0.1% 流量， chunk 粒度约 0.67%）的收益 —— 它能把定位成本降到一次哈希， 代价是多一个协议产物与存储开销。当前不纳入规范。

数据面的身份认证

  • 现状：数据面只有 CRC32，它不提供身份认证 （见 20 章）。当前安全模型以「可信局域网」为前提。
  • 待办：若部署场景扩展到不可信网络，引入基于会话密钥的 AEAD （如 AES-GCM / ChaCha20-Poly1305）与 nonce / 代际机制。

恢复列表与权威快照的帧长上限（已结项）

  • 结论：已定案 —— 采用「限制单连接并发会话数」方案， 不引入 login_ack 分页，不提高 max_frame_len。
  • 内容：新增规范常量 max_sessions_per_connection = 64（见 09 章）： 一条控制连接上的并发会话数必须 ≤ 64； login.resume_count 与 login_ack.sessions_count 必须 ≤ 64 （06、13 章同步），超限时 Server 以 session_abort （reason = TOO_MANY_SESSIONS，见 19 章）拒绝新发起的会话。
  • 为何选它：64 条快照最大 2,688 字节、64 条恢复列表最大 1,280 字节， 远小于 max_frame_len（1 MiB）—— 「快照必须一帧内完整」由此恒可编码， 而 u16 计数器的值域不再构成实际约束。
  • 代价：单条连接的并发会话数被限制在 64。 该限制在现实规模下宽松（一个连接承载 64 路并发传输已属极端）， 且不影响已终止会话的历史数量。
  • 未采纳：②login_ack 分批（需改线格式与协议语义， 留作将来「大集群 / 多租户」形态的预案）；③提高 max_frame_len （单帧内存占用上升，且未给条目数硬上限，属治标）。

window / burst_size / credit_batch 的规范默认值（已结项）

  • 结论：window 规范默认值 8192、connection_window 16384； burst_size 初值 = min(256, window)，与 window 解耦； 信用批阈值 credit_batch 规范取值 clamp(window / 8, 16, 1024)（见 11 章）。
  • 说明：窗口推进由事件驱动信用承担，吞吐上界为 min(D, window / (d + K / D))，固定墙钟周期不再进入除式。

秒传与并发会话的优先级（已结项）

  • 先复用同方向的活跃会话，再判断授权与秒传条件；asset_id 随最终回执交付。

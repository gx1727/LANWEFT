26 下一阶段与路线图（Roadmap）

非规范性（Non-Normative）：本章记录尚未冻结的议题与后续版本方向， 不构成互操作要求（见 25 章）。规范正文与本章冲突时，以规范正文为准。
本章要点：版本号形如 major.minor.patch，当前为 v0.3.0， 且只在上游明确指示时变更；任何修订不得变更版本号， 必须记入本章「修订记录」。v0.3.0 已把控制面由 MQTT 迁移到 TCP 并把载荷改为二进制定长布局。 已知限制包括：v0.3.0 与早期草案不兼容、同一版本号下先后指代三套互不兼容的线路格式、 抓包不再自解释、断线恢复依赖 Client 提供恢复提示。

版本策略（规范性）

  • 版本号形如 major.minor.patch，当前为 v0.3.0。
  • 版本号只在上游明确指示时变更。 未获明确指示时，规范的任何修订（措辞澄清、勘误、章节增补） 不得变更版本号 —— 修订必须记入本章的「修订记录」。
  • 每次修订必须在本章留下记录：改了什么、涉及哪些章节。
  • 0.x 阶段的兼容性：本规范处于 0.x 阶段，minor 变更可能是不兼容的 （例如 v0.3.0 的控制面与早期草案即不兼容）。 因此 08 章「版本比较规则」中「major 相同即视为兼容」的结论 必须结合本章与 06 章的消息集共同判断， 不得仅凭 minor 不同就假定可互通。
换言之：版本号是标识当前规范状态，不是自动递增的计数器。

已知限制

  • 不兼容：v0.3.0 的控制面与早期草案（MQTT）无法互通 —— 传输层、帧格式与消息集均已改变。升级必须同时升级两端。
  • 同一版本号下的三套线路格式：按上游指示，修订未变更版本号。 因此 v0.3.0 这一版本号先后指代了 JSON、 二进制定长（session_id = u32）与 二进制定长（session_id = u64 + TCP 数据面帧） 三套互不兼容的格式。 实现必须以 06、07、08 章正文为准，不得仅凭版本号判断可互通性。
  • 控制帧现为二进制定长布局（见 06 章）：定长帧头 + 定长区 + 变长区， 无字段名重复开销。代价是可读性下降 —— 抓包不再自解释， 实现侧必须提供与 msg_type 对应的解码日志。
  • 断线恢复时，下载方向依赖 Client 提供恢复提示。 若 Client 崩溃导致本地位图丢失且无法重建， 该会话只能以 SESSION_NOT_FOUND / SESSION_ABORTED 失败。

待定议题

控制帧的紧凑二进制编码（已结项）

  • 结论：已实施。控制帧改为二进制定长布局（见 06 章「帧格式」与「消息体布局」）。
  • 落地形态：u32 frame_len | u8 msg_type | u8 flags | u8 body_version | u8 reserved | body， 消息体 = 定长区（表格式偏移/大小）+ 变长区（顺序固定）；全部小端序。
  • 扩展规则：同一 msg_type 的定长区一旦发布即冻结； 新增字段只能追加在扩展区（变长区之后的尾部字节），接收方必须忽略扩展区。 这取代了原先「忽略未知字段」的 JSON 约定。
  • 配套变更：file_hash 改为 32 字节原始 Blake3；session_id 统一为 u32； result / direction / state / mode 改为 u8 枚举；proto_version 改为三个 u8； 错误码仍以符号名字符串承载（低频、需人工判读，不做数值化）。
  • 保留的代价：可调试性下降；实现侧需自备解码日志与抓包工具。

TCP 数据面通道

  • 现状：UDP 主通道 + TCP 兜底（见 05、07 章）。
  • 议题：是否将 TCP 提升为数据面主通道。
  • 收益：可删除 07 章的 PROBE 握手、11 章的 window / AIMD、 18 章的缺失分批与 08 章的包级 CRC32；吞吐不再受 window × chunk_size / 裁决周期 的天花板限制。
  • 代价：失去乱序写能力（TCP 交付有序），恢复起点退化为连续水位线； 且移动端 WiFi 的丢包不等于拥塞，TCP 拥塞控制的误判会显著降速 —— 而本协议的移动端客户端正依赖 UDP + 发送端本地 AIMD 规避这一点。
  • 倾向：维持 UDP 主通道。

TCP 降级通道的线路格式（已结项）

  • 结论：已实施。TCP 数据面帧格式见 07 章「TCP 数据面线路格式」： u32 frame_len + u64 session_id + u32 chunk_id + u16 payload_len + u16 flags + payload； 不携带 crc32（TCP 已提供字节流校验）。绑定帧 FLAG_BIND 用于会话绑定与权限校验。

秒传与并发会话的优先级

  • 现状：09 章定义了「同文件正在同步 → 返回现有会话」与「已存在完整文件 → 秒传」 两条规则，但未定义两者同时命中时的优先级 （同 file_hash 的会话正在传输、而既有文件已完整）。
  • 待办：明确仲裁顺序，并补充 asset_id 在秒传路径上的交付语义。

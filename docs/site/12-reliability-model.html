12 可靠性模型（Reliability Model）

本章要点：可靠性由「裁决 + 完整性校验 + 重传 + 恢复 + 提交」五层构成。 裁决是唯一的推进依据（规范性）：接收方必须至少每 50 ms 下发一次 missing_chunks（mode=report），包括缺失列表为空的情况。 看门狗与保底轮询使用同一个 1000 ms 索要规则。控制连接断开不得直接置为 ABORTED，只有 60 秒会话活动超时才终止会话。

分层保障

可靠性分层（自下而上）
① 缺失裁决与位图 · 控制面统计缺失并下发 missing_chunks(mode=report)；接收端乱序写盘与位图
② 完整性校验 · crc32 包级 + 文件级 Blake3
③ 重传 · UDP 不即时重传；聚合缺失后统一下发；重传优先级高于新数据
④ 中断与恢复 · 不回滚已写入；恢复后加载位图并补传缺失
⑤ 完成与提交 · bitmap 全真 → 校验 hash → 原子重命名 → 发布完成消息
裁决是唯一的推进依据（规范性）：接收方必须至少每 50 ms 下发一次 missing_chunks（mode=report），包括缺失列表为空的情况； 发送方据此推进窗口。详见 11 章「窗口推进判据」。

保底轮询（Keep-Alive Polling）

  • Client 发送完全部数据后，若 Server 持续返回 missing_chunks（mode=report） 且 chunks 为空（缺失列表为空），但始终未下发 upload_complete， Client 进入保底轮询状态。
  • 保底轮询使用 11 章判据第 4 条的同一个 1000 ms 索要规则： Client 必须按该周期发布 missing_chunks（mode=request） 持续索要缺失列表，直至收到 upload_complete 或触发超时。
  • 目的：防止对端状态机卡死导致的会话悬挂。

连接断开的语义（规范性）

控制连接断开时，该连接承载的全部会话必须视为中断（可恢复）， 不得直接置为 ABORTED。
  • 断连不回滚已写入的数据，位图与临时文件必须保留。
  • 断连原因按 19 章分类记录：连接被关闭 → CONNECTION_CLOSED；心跳超时 → TIMEOUT_HEARTBEAT；链路层异常 → NETWORK_ERROR。
  • Client 重连后通过 login 的恢复列表恢复（见 13 章）。
  • 只有会话活动超时（60 秒，见 09 章）才把会话置为 ABORTED 并清理资源。

看门狗（Watchdog）

  • 看门狗的职责与 11 章判据第 4 条的索要规则完全一致： 发送方每 1000 ms 至少索要一次裁决，直到收到 mode=report 为止。
  • 重复的 mode=request 是幂等的，与幂等要求兼容 （见 06 章「未识别消息必须忽略，保持幂等性」）。

完整性校验

层级 / 情形规范要求
包级 每个 UDP 包尾部携带 CRC32（覆盖 16 字节头 + payload），校验失败直接丢弃，不得写入位图； 该块随即成为「未收到」，按定点补发处理 —— 单次校验失败的代价是一个块，不是整个文件
文件级 传输完成后，接收方计算全文件 Blake3 哈希，与请求中的 file_hash 比对 （file_hash 为 32 字节原始 Blake3 摘要，hash32 类型，非十六进制串）； 一致才进入 COMMIT 并发布完成消息（上传方向 upload_complete， 下载方向 download_complete）
恢复阶梯 文件级失配后按 ① 摘要对帐 → ② 复核轮 → ③ 中止 逐级恢复，每一级至多一次：
① 摘要对帐：逐区间比对摘要，零内容流量地定位差异区间 → 清零可疑块位图 → 复用既有缺失裁决定点补发；
② 复核轮：重新读取源文件并全量重发；
③ 中止：session_abort(FILE_HASH_MISMATCH)。
对帐的根区间摘要一致时，判定请求的 file_hash 与源文件不符 → SOURCE_FILE_MISMATCH，不再进入复核轮。
文件级校验失败 → 复核轮 接收方不得立即终止会话，必须进入复核轮：
① 清空位图（临时文件保留）；② 发布带复核轮标志 （missing_chunks.flags.bit1 = 1）的裁决，chunks 为空列表、 missing_count = chunk_count；③ 发送方必须重新读取源文件、 从 chunk_id = 0 起全量重发；④ 重新校验文件级 Blake3。
复核轮至多一次（计数必须随位图持久化）。
次数上限的统一表述：接收方对每个会话至多发起 1 次摘要对帐、 至多发起 1 次复核轮；发送方对每一次发起至多响应 1 次； 三者互不叠加，且重启后不得重新获得机会。
复核轮后仍失配 接收方必须发布 session_abort（reason = FILE_HASH_MISMATCH） 终止会话。此时源文件确实不可读或已被改动。
这是接收侧唯一有权发起的终止（见 10 章「终止权」）；其余终止原因一律由 Server 发起。
秒传路径 跳过数据传输时没有位图，完成条件为「既有文件校验通过并原子提交」（见 10 章「秒传路径」）

摘要对帐（Reconciliation）

目的：在不传输文件内容的前提下，定位「接收方临时文件」与「发送方源文件」 之间的差异区间，从而把修复代价从「整个文件」降到「损坏的那几块」。 它是恢复阶梯的第 ① 级，必须先于复核轮启用。

消息与方向（规范性）

消息方向说明
reconcile_request接收方 → 发送方 携带待比较的区间列表；第 1 轮只携带根区间，并置 flags.bit0（根轮标志）
reconcile_response发送方 → 接收方 携带各区间在发送方侧的摘要
发布方恒定：请求方恒为接收方，应答方恒为发送方 （与 missing_chunks 的方向规则同源，见 06 章）。

对帐区间（规范性）

项目规范要求
first_chunku32：区间起始的 chunk_id（含）
chunk_countu32：区间包含的 chunk 数
字节范围[first_chunk × chunk_size, (first_chunk + chunk_count) × chunk_size)，必须截断到文件末尾（最后一个区间的末尾 chunk 可能不满块）
区间摘要该字节范围的 BLAKE3 摘要（hash32），必须与文件级 hash 使用同一算法与同一输出长度（32 字节）
根区间first_chunk = 0、chunk_count = chunk_count；其摘要恒等于该文件的文件级 Blake3 摘要
适用前提发送方必须仍持有该源文件，且其 size 必须与会话记录一致

摘要对帐的至多一次约束、下降规则与边界情形见下方各表；修复阶段不引入任何新消息 —— 复用既有的位图与裁决机制。
  • 接收方在 VERIFY 阶段检测到文件级失配 → 必须先尝试摘要对帐； 接收侧状态必须由 VERIFY 退回 TRANSFERRING。
  • 发送方收到请求后，必须校验源文件的 size 与会话记录一致； 不一致时必须置 reconcile_response.flags.bit0（源文件已变更）且不计算任何摘要。
  • 发送方必须为请求中的每个区间读取源文件的对应字节并计算 BLAKE3 摘要， 然后以 reconcile_response 返回。
  • 接收方收到应答后，必须用临时文件的对应字节独立计算摘要，并与应答中的摘要逐区间比对。
  • 根区间一致 → 双方文件内容相同 → 请求的 file_hash 与实际文件不符 → 接收方必须发布 session_abort（reason = SOURCE_FILE_MISMATCH） 并终止会话，不得进入复核轮。
  • 根区间不一致 → 把每个「不一致」的区间二等分为左右两个子区间 （左半 = 前 chunk_count ÷ 2 个 chunk，右半 = 其余），组成下一轮的待比较区间集合； 同一轮的所有区间必须同层，二等分规则由 (first_chunk, chunk_count) 唯一确定，双方无须协商。
  • 重复下降，直到某区间的 chunk_count 达到最小粒度（规范取 1， 即定位到单个 chunk）；该 chunk 即为可疑块。
  • 接收方必须把全部可疑块的位图位清零，随后按常规缺失裁决 （missing_chunks，mode=report）报告它们；发送方必须定点补发这些块。
  • 补发完成后，接收方必须重新计算文件级 Blake3；通过则进入 COMMIT，否则转入复核轮。

边界情形（规范性）

情形规范要求
源文件已变更 reconcile_response.flags.bit0 置位时，接收方必须中止对帐并转入复核轮
请求被拒绝 reconcile_response.flags.bit1（请求超限）置位时，接收方必须中止对帐并转入复核轮
对帐不可用 发送方不实现摘要对帐（收到请求后不回应答）时，接收方必须在等待超时后转入复核轮，不得无限等待
本地 I/O 失败 接收方在回读临时文件计算区间摘要时遇到 I/O 错误，必须发布 session_abort （reason = FILESYSTEM_ERROR）终止会话，不得把它当作「内容不符」
区间摘要一致但文件级失配 只可能发生在根区间，此时必须判定为 SOURCE_FILE_MISMATCH
对帐期间的连接中断 对帐计数随会话元数据持久化（见 09 章），恢复后不得重新获得一次对帐机会；恢复流程按 13 章执行

参数规范取值含义
对帐次数每会话至多 1 次与复核轮同等约束；重启后不得重新获得机会（见 09 章持久化）

接收方必须在累计比较数超限时立即停止对帐并转入复核轮； 发送方必须在收到超出上限的请求时拒绝该请求 （以 reconcile_response 的 flags.bit1 表示请求超限），不得无条件执行。

复核轮为何必要：包级 CRC32 的漏检概率

文件级失配意味着「接收到的字节整体不等于源文件」。包级 CRC32 只有 32 位： 若一个包已经损坏，且错误的 CRC 余数近似均匀，漏检的条件概率约为 2⁻³²。 实际漏检率还取决于包损坏率与差错模式，不能仅凭文件大小推出； 文件级校验还覆盖包校验之后发生的写盘差错。 未检出的损坏会一路存活到文件级校验，从而触发恢复阶梯。
为何不立即终止（说明）：文件级失配一律立即终止，会让一个刚传完的百 GB 文件 因为一次瞬态读写错误而被丢弃。复核轮把它降级为「一次重传」而非「全部重来」； 复核轮至多一次的约束保证了最坏情况下的代价上界是两次传输，而不是无限重试。

13 中断与恢复（Resume & Recovery）

本章要点：恢复有两条路径（断线重连 / 暂停后恢复），语义一致： 都返回接收方的权威续传位置与数据面端口，都使会话回到可传输状态； 区别只在于是否需要重建连接。 断线不解除显式暂停 —— PAUSED 会话在重连后必须仍处于 PAUSED， 由 resume_session / resume_ack 显式恢复； 恢复后各视角各自回到断线前的状态。 续传起点 next_chunk_id 必须是接收方位图中第一个尚未收到的块， 位图中的空洞由周期下发的 missing_chunks（mode=report）负责指认。

路径一 · 断线重连

快照的权限边界（规范性）：Server 确定会话关联、协商参数和端口； 只有数据接收方的持久化位图决定块是否收到。两个计数不能表示稀疏位图， 不得用于重建或覆盖它。下载时 Server 必须回显 Client 提供的续传摘要； Client 保留本地 VERIFY / COMMIT 阶段。位图丢失且无法可靠重建时不得凭摘要续传。

两条路径的语义一致：都返回接收方的权威续传位置与数据面端口，都使会话回到可传输状态。 恢复后各视角各自回到断线前状态（共享状态按快照，接收方本地校验与提交阶段按持久化记录）： PAUSED 保持 PAUSED（断线不解除显式暂停）， VERIFY / COMMIT 的接收侧回到原状态。

login_ack 快照记录的字段构成

快照记录 = 定长区（字段顺序与类型取自源文「通用规则」）+ 内联 code 字符串
session_id (u64)
result / direction / state (enum8 × 3)
chunk_count (u32)
chunk_size (u32)
window (u32)
connection_window (u32)
next_chunk_id (u32)
missing_count (u32)
udp_port / tcp_port / code_len (u16 × 3)
定长区共 42 字节 → 紧随其后是 code_len 字节内联的 code 字符串
字段名称、顺序与类型取自源文「断线重连（连接重建）· 通用规则（规范性）」； 定长区长度 42 字节由源文声明。 图中不含手敲偏移：定长区内的字节排布由源文定义，字段类型即其宽度。
条目数上界与可编码性：resume_count 与 sessions_count 必须 ≤ max_sessions_per_connection（64）。 login.resume[] 每条为 20 字节定长记录 （字段：session_id / next_chunk_id / missing_count / flags）， 恢复列表最大 64 × 20 = 1,280 字节； 快照最大 64 × (42 + code_len) 字节， 均远小于 max_frame_len（1 MiB）—— 该上界保证两者始终可编码。

中断处理

  • 可随时中断
  • 保留已写入与位图
  • 中断不回滚已写入数据
  • 控制连接断开时，其上承载的全部会话一并进入中断（见 09 章）
  • 帧失步导致的断连（见 06、07 章「帧同步与失步处理」）同样属于 断线重连路径：失步的连接不得就地续解， 恢复一律经 login / login_ack 的权威快照重建

恢复的两条路径（规范性）

路径 触发条件 消息 权威状态载体
断线重连 控制连接断开后重新建立 login（恢复列表） → login_ack login_ack 的 sessions[] 快照记录
暂停后恢复 会话处于 PAUSED，连接仍存活 resume_session → resume_ack resume_ack

两条路径的语义一致：都返回接收方的权威续传位置与数据面端口， 都使会话回到可传输状态。区别只在于是否需要重建连接。

恢复后的状态（规范性）：恢复后各视角各自回到断线前的状态 （共享状态按快照，接收方本地校验与提交阶段按持久化记录，见「待恢复会话的判定」）。 「暂停后恢复」路径必须回到 TRANSFERRING（该路径的前提就是解除暂停）； 「断线重连」路径则必须按上表处理 —— PAUSED 保持 PAUSED，VERIFY / COMMIT 的接收侧回到 VERIFY / COMMIT （发送侧没有这两个状态，回到 TRANSFERRING）。

C↔C peer 会话的恢复（Stage 1）

  • peer 会话横跨两条控制连接；任一端断开，Server 必须通知另一端并把会话置为中断。 两端分别经各自的 login 恢复（没有 C↔C login）。
  • 每个设备的 resume[] 必须只包含它在其中担任 sender 或 receiver 的 peer 会话； login_ack.sessions[] 的 state/参数按该设备视角返回。
  • 恢复后数据端点可能变化：Server 必须在成功 login 后，对每个恢复的 peer 会话 重发 peer_accept（含最新端点与 transfer_token）；双方必须重新 peer PROBE。 接收方的位图/临时文件必须保留，续传起点仍是第一个缺失 symbol。
  • R1 的中转由两段既有会话组成：分别按 upload/download 恢复； transfer_id 关联两段结果。
  • 断线重连不得把 peer 会话降级为同方向的 upload/download；拓扑/角色不变， 只重新建立端点与信用基线。

断线重连（连接重建）

通用规则（规范性）

  • 待恢复会话的判定（规范性）：「待恢复」指断线时处于可恢复状态的会话， 判定按会话断线前的状态（见 10 章「状态定义」）：
断线前状态 列入 login.resume[]？ 恢复后的状态
INIT / NEGOTIATING 否 不恢复；会话按新会话重新发起
TRANSFERRING 是 各视角回到 TRANSFERRING
PAUSED 是 保持 PAUSED —— 断线不解除显式暂停；恢复仍走「暂停后恢复」（resume_session / resume_ack）
VERIFY / COMMIT 是 各视角各自回到断线前的状态（接收侧回 VERIFY / COMMIT，发送侧回 TRANSFERRING）
COMPLETED / ABORTED 否 不恢复（终态，见 10 章）

为何断线不解除暂停（说明）：暂停是显式的用户/策略意图， 网络抖动不是解除暂停的理由。若断线即自动恢复传输， 「暂停」将退化为「建议」—— 用户无法保证文件在暂停期间不被继续传输。 因此 PAUSED 会话在重连后必须仍处于 PAUSED， 由 resume_session / resume_ack 显式恢复。

  • 条目数上界（规范性）：resume_count 与 login_ack 的 sessions_count 必须 ≤ max_sessions_per_connection（64，见 09 章）。 该上界保证两者始终可编码： resume[] 最大 64 × 20 = 1,280 字节， 快照最大 64 × (42 + code_len) 字节， 均远小于 max_frame_len（1 MiB，见 06 章）。 （无该上界时，u16 的值域将超出帧长上限 —— 65,535 × 42 字节 ≈ 2.6 MiB > 1 MiB。）
  • login 的 resume[] 必须列出全部待恢复的会话。 二进制表示：定长区 resume_count（u16）给出条目数（无待恢复会话时为 0）， 变长区按顺序给出 resume_count 条 20 字节定长记录， 每条含 session_id（u64）/ next_chunk_id（u32）/ missing_count（u32）/ flags（u8：bit0 = next_chunk_id 有效，bit1 = missing_count 有效）； next_chunk_id 为块级续传起点，missing_count 为缺失 symbol 总数。
  • 续传起点来自接收方的位图，因此只有接收方才可能提供它：
  • 上传方向（接收方 = Server）：Client 必须不提供恢复提示 （记录 flags 的 bit0 / bit1 = 0，相应字段必须取 0）， 由 Server 用自己的位图计算。
  • 下载方向（接收方 = Client）：Client 必须依据自己的位图提供恢复提示 （记录 flags 的 bit0 / bit1 = 1）。
  • Server 必须在 login_ack 的 sessions[] 中为每一个待恢复会话给出一项， 标明 result（enum8：0 = fail，1 = success）与 code（失败原因，见 19 章）。 二进制表示：定长区 sessions_count（u16）给出条目数， 变长区按顺序给出 sessions_count 条快照记录，每条 = 42 字节定长（session_id(u64) / result(enum8) / direction(enum8) / state(enum8) / chunk_count(u32) / chunk_size(u32) / window(u32) / connection_window(u32) / next_chunk_id(u32) / missing_count(u32) / udp_port(u16) / tcp_port(u16) / code_len(u16)）+ 紧随其后的 code_len 字节内联 code 字符串。
  • 快照的权限边界（规范性）：Server 确定会话关联、协商参数和端口； 只有数据接收方的持久化位图决定块是否收到。两个计数不能表示稀疏位图， 不得用于重建或覆盖它。下载时 Server 必须回显 Client 提供的续传摘要； Client 保留本地 VERIFY / COMMIT 阶段。位图丢失且无法可靠重建时不得凭摘要续传。
  • 恢复成功后，发送方必须丢弃恢复前推导的在途量估计并重建（见 11 章判据第 3 条）。

上传方向（Client = 发送方，Server = 接收方）

  1. Client 重连 → 发送 login，其 resume[] 记录只带 session_id（u64）， next_chunk_id / missing_count 必须未携带（记录 flags 的 bit0 / bit1 = 0， 相应字段取 0）
  2. Server 加载自己的位图 → 计算缺失 → 在 login_ack 的 sessions[] 快照记录中给出 next_chunk_id / missing_count / udp_port
  3. 仅在快照允许传输且仍有缺块时继续发送；PAUSED 保持暂停， COMPLETED 停止数据传输并等待原回执。 （双方各自回到断线前状态；发送侧断线前不可能是 VERIFY / COMMIT）

下载方向（Client = 接收方，Server = 发送方）

Server 没有 Client 的位图，无从计算续传起点， 因此由 Client 在 login 的 resume[] 中提供恢复提示：

  1. Client 重连 → 发送 login，其 resume[] 记录携带 session_id（u64）/ next_chunk_id（u32）/ missing_count（u32）， 并置记录 flags 的 bit0 / bit1 = 1
  2. Server 在 login_ack 的 sessions[] 快照记录中回填权威状态 （含 udp_port、window、connection_window 与 state）
  3. 仅在可传输且仍有缺块时，Server 从 next_chunk_id 起继续向 Client 推送 chunk； Client 以 missing_chunks（mode=report）报告自己的缺失块
  4. 双方各自回到断线前状态（发送侧 = Server 回 TRANSFERRING； 接收侧 = Client 回断线前状态）

恢复失败

login_ack 的 sessions[] 中该会话的 result（enum8）= 0（fail）， 其记录内联 code 字符串取值为符号名：

code 含义
SESSION_NOT_FOUND 会话不存在（Server 重启且状态已丢弃，或从未存在）
SESSION_ABORTED 会话已进入终态（见 10 章），不可恢复
INVALID_STATE 当前状态不允许恢复

Client 必须把 result = 0（fail）的会话视为已终止， 不得继续使用其本地状态。

最终回执的交付（规范性）

完成交付不属于恢复数据传输。接收方以 (device_id, session_id, direction) 为键， 在提交前持久化提交意图（含目标、预分配的 asset_id 和预期哈希）。文件和素材记录提交 成功后持久化不可变的完整 upload_complete 或 download_complete，再发布回执。 进程若在提交与记录回执之间退出，必须先依据意图核对并幂等完成同一笔提交， 不得再次创建素材、分配新 asset_id 或在提交成功前公布成功。

  • 接收方保留待交付回执直到收到对应 complete_ack；60 秒活动超时只回收未完成传输， 不得清除待交付回执。回执不占活跃会话配额；存储不足时应限制新会话，而非驱逐未确认结果。
  • 每次成功登录后，双方必须在各自发送 login_ack 或收到成功 login_ack 后， 向已认证的原对端重发所有未确认回执（逐条普通控制帧，不塞入快照）。 发送方必须持久化会话与设备、方向的绑定，直到最终结果可确认； 传输超时本身不是对端提交失败的证明。
  • 上传时，若 Client 把本地仍在传输的会话列入 resume[]，Server 已有成功回执， 则快照返回 result=success, state=COMPLETED，next_chunk_id=chunk_count, missing_count=0， 随后交付原回执。Client 不再传数据，不得仅凭快照宣告成功。下载时，已提交的 Client 不将终态列入 resume[]，直接在握手后重发 download_complete。
  • 数据发送方核对设备、会话与消息方向，持久化完整结果后才发 complete_ack； 相同回执再次到达只重发确认，不重复业务操作。相同键但内容不一致不得覆盖既有结果或确认。 收到确认的一方可删除待交付副本，不得因重复确认重新打开会话。

下载超时后的结果：发送方的传输资源与业务结果分别记账。Server 超时后停止传输， 业务结果保持「未知」（本地记录，不新增线上状态）。已认证 Client 迟到的成功或失败 download_complete 仍必须按原会话绑定持久化并确认，不重建数据面、不改变已关闭的传输状态。 若 Client 请求恢复已过期的下载，Server 回失败快照 code=TIMEOUT_NO_ACTIVITY； 无提交意图的 Client 停止传输，持久化并交付同码的失败回执。已有提交意图的 Client 必须先核实提交，交付实际结果；恢复被拒不推翻已提交的文件。

暂停后恢复（连接存活）

  1. Client 发送 resume_session，其定长区携带 session_id（u64）/ next_chunk_id（u32）/ missing_count（u32）， 并以 flags 存在标志位表明恢复提示是否携带 （bit0 = next_chunk_id 有效，bit1 = missing_count 有效； 标志位为 0 时该字段必须为 0） —— 恢复提示的方向规则与断线重连相同： 上传方向必须不携带，下载方向必须携带。
  2. Server 回 resume_ack（含 result / code、 next_chunk_id / missing_count / udp_port / connection_window）
  3. 双方回到 TRANSFERRING（该路径的前提就是解除暂停）

resume_ack 语义

字段 语义
result / code 恢复是否成功（result 为 enum8，0 = fail、1 = success）；code 为 str，失败时的机器可判定错误码（见 19 章、06 章）
next_chunk_id 续传顺序起点：接收方位图中第一个尚未收全的 chunk_id；位图已全真时为 chunk_count（u32）
missing_count 接收方位图中尚未收到的 symbol 总数（精确值，u32）
udp_port 数据面端口（u16），可能因会话重建而变化，Client 必须使用回执中的端口

next_chunk_id 的定义（规范性）：接收方位图中第一个尚未收全的 chunk_id。

本协议显式支持乱序写与随机访问（见 01、17 章），位图可能出现空洞 —— 存在低于最大已收 id 的缺失块。若以 max_received_id + 1 作为续传起点， 空洞块将永远不会被重传，文件级 Blake3 校验必然失配并导致会话中止。 因此续传起点必须是第一个缺失块。

空洞块的补发

next_chunk_id 只决定顺序发送流从哪里继续；位图中低于当前发送位置的空洞 由周期下发的 missing_chunks（mode=report）负责指认：

  • 接收方必须在裁决中报告全部未收到的 symbol（完全缺失块 + 部分缺失掩码）， 而不只是从 next_chunk_id 开始的连续区间。
  • 发送方必须优先重传裁决报告的缺失块，优先级高于新数据。
  • 包级校验失败（crc32）的块同样计入「未收到」，并按本节的定点补发处理 （见 12 章「缺失块的定点补发」）。

复核轮与恢复

  • 复核轮的计数必须与位图一同持久化（见 09 章「持久化」）。
  • 摘要对帐的计数同样必须持久化：恢复后不得因连接重建而重新获得 一次对帐机会（见 12 章「上限」）。
  • 复核轮进行中发生断线时，恢复后必须继续该复核轮， 不得因连接重建而获得第二次复核轮机会。
  • 暂停恢复或重连后，可传输会话的接收方须先发一条普通 report（bit1=0），携带 已持久化的修复代号及精确 missing_count；发送方收到前不得发 DATA。 发送方按该报告重建 Sent = R = symbol_count − missing_count，从恢复起点续传。 若代号为 2，须重新打开源文件，但不得重新清位或从零启动第二次全量复核。 即使启动裁决在断线前未送达，首次恢复报告也足以确定当前代号。

失败与清理

  • 长时间未恢复可清理，删除临时文件/位图/元数据
  • 清理前应确认会话已进入 ABORTED 状态
  • 会话超时时长见 09 章「超时与回收」

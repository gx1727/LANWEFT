13 中断与恢复（Resume & Recovery）

本章要点：恢复有两条路径（断线重连 / 暂停后恢复），语义一致： 都返回接收方的权威续传位置与数据面端口，都使会话回到可传输状态； 区别只在于是否需要重建连接。

中断处理

  • 可随时中断
  • 保留已写入与位图
  • 中断不回滚已写入数据
  • 控制连接断开时，其上承载的全部会话一并进入中断（见 09 章）

快照的权限边界（规范性）：Server 确定会话关联、协商参数和端口； 只有数据接收方的持久化位图决定块是否收到。两个计数不能表示稀疏位图， 不得用于重建或覆盖它。下载时 Server 必须回显 Client 提供的续传摘要； Client 保留本地 VERIFY / COMMIT 阶段。位图丢失且无法可靠重建时不得凭摘要续传。

两条路径的语义一致：都返回接收方的权威续传位置与数据面端口，都使会话回到可传输状态。 恢复后各视角各自回到断线前状态（共享状态按快照，接收方本地校验与提交阶段按持久化记录）： PAUSED 保持 PAUSED（断线不解除显式暂停）， VERIFY / COMMIT 的接收侧回到原状态。

断线重连：通用规则（规范性）

login.resume[]必须列出全部待恢复的会话。条目数上界：resume_count 与 login_ack 的 sessions_count 必须 ≤ max_sessions_per_connection（64，见 09 章）—— 该上界保证两者始终可编码（64 × 20 = 1,280 B；64 × (42 + code_len) B，均远小于 max_frame_len = 1 MiB）。定长区 resume_count（u16）给出条目数（无待恢复会话时为 0），变长区给出 resume_count 条 20 字节定长记录：session_id(u64) / next_chunk_id(u32) / missing_count(u32) / flags(u8：bit0 = next_chunk_id 有效，bit1 = missing_count 有效)
恢复提示的来源续传起点来自接收方的位图，因此只有接收方才可能提供它
上传方向（接收方 = Server）Client 必须不提供恢复提示（flags bit0 / bit1 = 0，相应字段必须取 0），由 Server 用自己的位图计算
下载方向（接收方 = Client）Client 必须依据自己的位图提供恢复提示（flags bit0 / bit1 = 1）
login_ack.sessions[]Server 必须为每一个待恢复会话给出一项，标明 result（enum8：0 = fail，1 = success）与 code（失败原因，见 19 章）。定长区 sessions_count（u16）给出条目数，变长区按顺序给出 sessions_count 条快照记录，每条 = 42 字节定长（session_id(u64) / result(enum8) / direction(enum8) / state(enum8) / chunk_count(u32) / chunk_size(u32) / window(u32) / connection_window(u32) / next_chunk_id(u32) / missing_count(u32) / udp_port(u16) / tcp_port(u16) / code_len(u16)）+ 紧随其后的 code_len 字节内联 code 字符串
恢复成功后发送方必须丢弃恢复前推导的在途量估计并重建（见 11 章判据第 3 条）

两个方向的具体流程

上传方向（Client = 发送方）

  • Client 重连 → 发送 login，其 resume[] 记录只带 session_id，next_chunk_id / missing_count 必须未携带
  • Server 加载自己的位图 → 计算缺失 → 在 login_ack.sessions[] 中给出 next_chunk_id / missing_count / udp_port
  • Client 按快照重建本地状态 → 仅在快照允许传输且仍有缺块时继续发送；PAUSED 保持暂停，COMPLETED 停止数据传输并等待原回执

下载方向（Client = 接收方）

  • Server 没有 Client 的位图，无从计算续传起点 → 由 Client 在 login.resume[] 中提供恢复提示（flags bit0 / bit1 = 1）
  • Server 在 login_ack.sessions[] 中回填权威状态（含 udp_port 与 state）
  • Server 仅在可传输且仍有缺块时，从 next_chunk_id 起继续向 Client 推送 chunk；Client 以 missing_chunks（mode=report）报告自己的缺失块
  • 双方各自回到断线前状态（发送侧回 TRANSFERRING；接收侧回断线前状态）

恢复失败

code含义
SESSION_NOT_FOUND会话不存在（Server 重启且状态已丢弃，或从未存在）
SESSION_ABORTED会话已进入终态（见 10 章），不可恢复
INVALID_STATE当前状态不允许恢复
login_ack.sessions[] 中该会话的 result = 0（fail）时，其记录内联 code 取上述符号名； Client 必须把这类会话视为已终止，不得继续使用其本地状态。

最终回执的交付（规范性）

完成交付不属于恢复数据传输：接收方以 (device_id, session_id, direction) 为键， 在提交前持久化提交意图（含目标、预分配的 asset_id 和预期哈希）。 文件和素材记录提交成功后持久化不可变的完整 upload_complete 或 download_complete，再发布回执。
  • 进程若在提交与记录回执之间退出，必须先依据意图核对并幂等完成同一笔提交， 不得再次创建素材、分配新 asset_id 或在提交成功前公布成功。
  • 接收方必须保留待交付回执直到收到对应 complete_ack； 60 秒活动超时只回收未完成传输，不得清除待交付回执。 回执不占活跃会话配额；存储不足时应当限制新会话，而非驱逐未确认结果。
  • 每次成功登录后，双方必须在各自发送 login_ack 或收到成功 login_ack 后，向已认证的原对端重发所有未确认回执 （逐条普通控制帧，不塞入快照）。发送方必须持久化会话与设备、方向的绑定， 直到最终结果可确认；传输超时本身不是对端提交失败的证明。
  • 上传时，若 Client 把本地仍在传输的会话列入 resume[] 且 Server 已有成功回执， 则快照返回 result=success, state=COMPLETED， next_chunk_id=chunk_count, missing_count=0，随后交付原回执。 Client 不再传数据，不得仅凭快照宣告成功。 下载时，已提交的 Client 不将终态列入 resume[]， 直接在握手后重发 download_complete。
  • 数据发送方必须核对设备、会话与消息方向，持久化完整结果后才发 complete_ack； 相同回执再次到达只重发确认，不重复业务操作。 相同键但内容不一致不得覆盖既有结果或确认。 收到确认的一方可删除待交付副本，不得因重复确认重新打开会话。

resume_ack 语义

字段语义
result / code恢复是否成功（result 为 enum8，0 = fail、1 = success）；code 为 str，失败时的机器可判定错误码（见 19、06 章）
next_chunk_id续传顺序起点：接收方位图中第一个尚未收到的 chunk_id；位图已全真时为 chunk_count（u32）
missing_count接收方位图中尚未收到的 chunk 总数（精确值，u32）
udp_port数据面端口（u16），可能因会话重建而变化，Client 必须使用回执中的端口
next_chunk_id 的定义（规范性）：接收方位图中第一个尚未收到的 chunk_id。 本协议显式支持乱序写与随机访问，位图可能出现空洞 —— 若以 max_received_id + 1 作为续传起点，空洞块将永远不会被重传， 文件级 Blake3 校验必然失配并导致会话中止。因此续传起点必须是第一个缺失块。

空洞块的补发

  • next_chunk_id 只决定顺序发送流从哪里继续；位图中低于当前发送位置的空洞由周期下发的 missing_chunks（mode=report）负责指认
  • 接收方必须在裁决中报告全部未收到的 chunk_id，而不只是从 next_chunk_id 开始的连续区间
  • 发送方必须优先重传裁决报告的缺失块，优先级高于新数据

失败与清理

  • 长时间未恢复可清理，删除临时文件 / 位图 / 元数据
  • 清理前应确认会话已进入 ABORTED 状态
  • 会话超时时长见 09 章「超时与回收」

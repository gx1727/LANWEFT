20 安全模型（Security Model）

本章要点：安全模型以 lv1（默认） 的可信局域网为起点， lv2/lv3 可扩展到不可信网络。控制通道必须支持 TLS， lv2/lv3 必须在已认证的 TLS 控制连接上分发根秘密。 数据面按会话等级选择：lv1 CRC32、lv2 BLAKE3 keyed MAC、lv3 AEAD（AES-256-GCM / ChaCha20-Poly1305）。 PROBE 使用 probe_token 绑定端点；文件级 hash（Blake3）必须以 32 字节原始摘要承载。

假设

  • lv1 假设可信局域网；lv2/lv3 可用于不可信网络（含公网路径）。
  • Server 与客户端受控；Server 是认证与密钥分发的信任根。
  • 跨公网部署必须启用控制面 TLS，并不得将 security_min_level 配为 1。

控制面

  • 控制通道必须支持 TLS；应当启用（见 21 章）
  • 认证在连接握手阶段完成，绑定唯一 device_id （共享令牌或客户端证书，见 21 章）
  • 一条控制连接只承载一个 device_id； 跨 device_id 的会话在协议层无法表达
  • 凭据不得由 device_id 直接推导（见 23 章「隐私」）
  • 表示形式（规范性）：
  • 认证凭据由 login 的 token 字段承载，类型为 str （u16 长度 + UTF-8）；采用客户端证书时必须为空串（长度 0）
  • device_id 同样以 str 承载
  • 协议版本以三个 u8 承载（proto_major / proto_minor / proto_patch）， 载于 login 与 login_ack（见 06 章）
  • 错误码以符号名字符串承载（code / reason 字段，类型为 str）， 不得填写自由文本

数据面安全等级（规范性）

数据面支持三个会话级安全等级；默认 lv1。等级在会话建立时由 Server 选定， 会话生命周期内不可变；配置变更只影响新会话。

  • 等级隔离（规范性）：同一 link_token（即同一条控制连接）不得同时承载 lv1 会话与 lv2/lv3 会话。原因是 lv1 的 probe_token 就是根秘密本身，会明文 出现在数据面上；若与 lv2/lv3 会话共享同一根秘密，嗅探者即可据此派生 traffic_key。 实施方式：Server 必须按等级类别（lv1 与「lv2/lv3」两类）隔离根秘密 —— 一条控制连接上同时存在两类会话时，为它们分别签发不同的 link_token； 无法隔离时必须拒绝后到的会话（SECURITY_LEVEL_UNSUPPORTED）， 不得让 lv1 与 lv2/lv3 共用同一个根秘密。
等级 尾部 trailer 完整性 对端认证 机密性
lv1 CRC32（4B） 非密码学 无 无
lv2 BLAKE3 keyed MAC（16B） 密码学 有 无
lv3 AEAD tag（16B） 密码学 有 有
  • lv1 是兼容默认，只适用于可信 LAN；PROBE token 仍然启用。
  • lv2 用 BLAKE3-keyed 替换 CRC32，覆盖「16B 头 + payload」；不加密。
  • lv3 用 AES-256-GCM 或 ChaCha20-Poly1305（由 security_suite 选定）：
  • payload 为密文，长度与明文完全相等；
  • header 保持明文，作为 AAD；
  • tag 覆盖 AAD + 密文；
  • nonce = (generation, chunk_id, chunk_symbol, K) 的规范编码，固定 12 字节： 00 00 00 ‖ generation(u8) ‖ chunk_id(u32 小端) ‖ chunk_symbol(u16 小端) ‖ K(u16 小端)。
  • nonce 复用规则：该编码唯一确定一段载荷区间 (chunk_id, chunk_symbol, K)； 由于同一 generation 内源文件不可变，同一 nonce 必然对应字节完全相同的明文， 因此同代重传复用 nonce 不泄露信息。禁止在同一 traffic_key 下把不同明文 用同一 nonce 封装；K 参与编码，确保「同起点不同长度」得到不同 nonce。
  • 同一会话的 UDP 数据报与 TCP 数据面帧必须共用该会话的 traffic_key 与上述 nonce 规则；切换通道后重发的同一区间明文相同，nonce 随之相同。
  • AEAD/MAC 单元 = 数据报载荷（K 个 symbol），不是单个 symbol：
  • 允许信任模式 K > 1（一个 64KB 数据报一个 tag）；
  • 明文长度与 symbol 偏移映射均不变，接收方仍按 chunk_symbol + K 标位；
  • 丢包/坏 tag 的代价仍是该包覆盖的 K 个 symbol，可靠性模型不变。
  • 接收方必须按会话表选定的等级解析 trailer 长度；未知 session_id 直接丢弃， 不得猜测等级。TCP 数据面同理：lv1 无尾部，lv2/lv3 尾部 16B 且计入 frame_len。

密钥派生

  • 每个会话有且只有一个根秘密：
  • C↔S：login_ack.link_token（每控制连接 16B，成功时非零）；
  • C↔C：peer_accept.transfer_token（每 peer 会话 16B）。
  • probe_token：
  • lv1：根秘密直接作为 probe_token（PROBE 携带它；无数据密钥，泄露不危及数据）；
  • lv2/lv3：probe_token = KDF(root, "probe", 16)，不得在线上发送根秘密。
  • traffic_key（仅 lv2/lv3）：KDF(root, "data" ‖ session_id ‖ direction, 32)。
  • C↔S 的 link_token 每连接重新签发；重连后按新根秘密重新派生， 旧密钥的数据包自然失效并走重传。
  • C↔C 的 transfer_token 随 peer_accept 恢复重发；同一会话密钥稳定。
  • KDF 固定为 BLAKE3 derive-key 模式，唯一定义如下； 不得改用 HKDF 或其它 KDF 构造，不得保留多种等价选项：
  • KDF(root, label, n) = 以 context = "LANWEFT/" ‖ label（UTF-8 字节）为派生上下文、 以 root 为 key material、经 BLAKE3 derive-key 得到的 XOF，取前 n 字节。 等价伪码：blake3_derive_key(context).update(root).xof(n)。
  • 标签规范化（必须逐字节一致）：
    • probe_token = KDF(root, "probe", 16)；
    • traffic_key = KDF(root, "data" ‖ session_id(u64 小端) ‖ direction(u8), 32) —— direction：0 = upload、1 = download、2 = peer。
  • 标签必须参与派生；不同用途、不同 session_id、不同方向不得共用同一派生结果， 以避免密钥复用。
  • lv2/lv3 必须在已认证的控制连接上分发根秘密；因此 lv2/lv3 要求控制面 TLS。 Server 配置 security_min_level ≥ 2 而 TLS 未启用时，必须拒绝启动或拒绝会话。
  • Server 参与 C↔C 的密钥分发，因此 lv3 提供的是路径保护， 不是「对 Server 保密」；后者超出本规范范围。

协商与 Server 配置

Server 配置：

参数 含义 默认
security_min_level 允许的最低等级；低于它拒绝 1
security_default_level 双方都支持时优先选用的等级 1
security_max_level 允许的最高等级 3
security_suites lv3 允许套件及顺序 AES-256-GCM → ChaCha20-Poly1305
  • Client 在 login 中声明 max_security_level 与 security_suite_mask（见 06 章）。
  • C↔S：Server 为每个会话选择 chosen = clamp(security_default_level, security_min_level, min(client_max, security_max_level))； 若 client_max < security_min_level，以 SECURITY_LEVEL_UNSUPPORTED 拒绝。
  • C↔C：Server 取两端 max_security_level 的较小值，再按同一规则选择； 两端都必须支持选定等级。无交集且低于 security_min_level 时拒绝。
  • lv3 套件：从 security_suites 中选第一个同时被 Client security_suite_mask 支持的套件；无交集时必须降级到 lv2（若 security_min_level ≤ 2）， 否则拒绝。不得静默使用未协商的套件。
  • 选定结果写入 upload_accept / download_accept / delivery_offer / peer_offer / peer_accept 的 security_level / security_suite；快照记录的重启恢复用 security 字节（见 06、13 章）。
  • 禁止静默降级：协商在已认证控制面内完成；Server 不得因客户端能力不足 而选择低于 security_min_level 的等级。Client 不得接受低于自己声明下限的等级。

数据面通用约束

  • 文件级内容 hash（Blake3）：32 字节原始摘要（hash32）， 禁止以十六进制串承载；日志与 UI 展示时由实现自行转十六进制（见 06 章）。
  • 数据面地址必须做源地址校验：接收方必须校验 UDP 包的源地址:端口 与该会话经 PROBE 确认的对端地址一致，不一致即丢弃。 这不能替代认证（地址可伪造），但能挡住非定向的误发与扫描。
  • PROBE 端点绑定（规范性）：
  • C↔S：PROBE 载荷 = session_id + probe_token；Server 校验 token 属于该控制连接， 并把 PROBE 源地址:端口绑定为该会话端点（见 07 章）。
  • C↔C：PROBE 载荷 = session_id + probe_token；接收方校验后绑定发送端端点。
  • token 不匹配按 PEER_TOKEN_INVALID 丢弃，不得绑定或回 ACK。
  • lv1 的 token 是 bearer，on-path 嗅探后仍可重绑定；lv2/lv3 的派生 token 不暴露根秘密，但 PROBE 本身的认证仍应当在后续版本加 MAC。
  • 重放保护：接收方必须拒绝 chunk_id ≥ 该会话 chunk_count 的包（越界，见 08 章）， 且必须校验 session_id（u64）与本会话一致；DATA 的修复代号也必须匹配。 同一代内的重复由位图幂等性兜底（重复 chunk 静默丢弃）。 lv3 的 nonce 编码唯一确定载荷区间，重放只可能命中同一明文； 同一密钥下不同明文不会共用 nonce（见上「nonce 复用规则」）。
  • C↔C peer（规范性）：direction = peer 的直连数据面没有 C↔C 的 login； 身份与授权来自双方与 Server 的既有登录 + share grant（见 21 章）。
  • 直连：transfer_token 是根秘密；lv1 直接作为 PROBE token，lv2/lv3 派生 probe_token / traffic_key。
  • R2 中转：S 转发数据；lv2/lv3 的 tag 由 C1 生成、C2 校验，S 不修改载荷。 S 参与密钥分发，因此不提供「对 S 保密」。
  • R1：S 完整存储文件，按 Server 侧数据保护。
  • PROBE 可劫持、地址可伪造的既有风险同样适用于 peer；token 只提高门槛。
  • session_id 的唯一性是重放保护的前提（规范性）： session_id 必须跨 Server 进程重启不复用（见 09 章「创建规则」）—— 否则重启前仍在网络中飞行的数据包会命中重启后新建的会话， 把数据写入错误的文件。为此 session_id 必须为 u64 且采用时间有序的分配方式。
  • 复核轮的边界：复核轮是接收方主动发起的全量重传， 由 missing_chunks 的复核轮标志显式表达（见 12 章）； 它不是重放，发送方必须重新读取源文件。

主动投递的边界（规范性）

  • 主动投递只发生在已认证且存续的控制连接上（见 09 章「主动投递」）； Server 不得向离线设备投递。
  • 投递不携带任何认证凭据 —— 它复用控制连接已建立的身份边界。
  • Server 在收到 delivery_response（接受）后必须等到该会话的 UDP_PROBE 才可发送数据面数据包：不得向未经 PROBE 确认的地址发送 （见 07 章「端口与地址绑定」）。
  • 接收方可以拒绝投递；拒绝是正常的协议结果， 不得被当作错误或触发重试风暴。
  • 重复投递必须被幂等忽略：接收方不得因重复的 delivery_offer 而重复落盘同一内容。

资源消耗（规范性）

摘要对帐会诱导发送方反复读取源文件（见 12 章），因此必须设限：

  • 每会话的摘要对帐至多一次；
  • 单次请求的区间数 ≤ 64，单会话累计区间比较数 ≤ 8192，层级 ≤ 32；
  • 发送方必须拒绝超出上限的请求，不得无条件执行。

接收方不得通过反复发起对帐来消耗对端的磁盘与 CPU。

状态与权限

  • UDP 会话必须绑定到发起它的控制连接（及其 device_id）
  • Server 不向未知端口发送 UDP；目标地址必须来自 PROBE 报文（见 07 章）
  • TCP 数据面降级需重校验权限

审计

  • 认证失败尝试、跨 device_id 的会话操作与 session_abort 原因
完整性 ≠ 安全性（按等级）：lv1 的 CRC32 只能发现损坏，任何能发包的主机都能伪造； lv2 用 BLAKE3 keyed MAC 提供密码学完整性与对端认证；lv3 再用 AEAD 提供机密性。 Blake3 文件级摘要仍只负责内容一致性，不替代包级认证。
常见实现陷阱：把 lv1 的 CRC32 当作防伪手段；用十六进制串承载 Blake3 摘要； 在 lv2/lv3 下仍按单 symbol 追加 tag（应按数据报载荷整体计算）； 忽略 PROBE token 与源地址绑定；在未启用 TLS 的控制面上协商 lv2/lv3； 由 device_id 直接推导凭据（不得）。

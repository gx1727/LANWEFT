20 安全模型（Security Model）

本章要点：安全模型建立在可信局域网、Server 与客户端受控、不穿透公网三项假设之上。 控制通道必须支持 TLS、应当启用；认证在连接握手阶段完成并绑定唯一 device_id。 数据面使用 CRC32 只提供完整性而非安全性；文件级 hash（Blake3）必须以 32 字节原始摘要承载。

假设

前提说明
可信局域网网络环境被视为可信局域网
Server 与客户端受控Server 与客户端均处于受控之下
不穿透公网协议不用于穿透公网

控制面

  • 控制通道必须支持 TLS；应当启用（见 21 章）。
  • 认证在连接握手阶段完成，绑定唯一 device_id （共享令牌或客户端证书，见 21 章）。
  • 一条控制连接只承载一个 device_id； 跨 device_id 的会话在协议层无法表达。
  • 凭据不得由 device_id 直接推导（见 23 章「隐私」）。

表示形式（规范性）

项目 承载方式 约束
认证凭据 login 的 token 字段，类型为 str （u16 长度 + UTF-8） 采用客户端证书时必须为空串（长度 0）
device_id 同样以 str 承载 一条控制连接只承载一个 device_id
协议版本 三个 u8：proto_major / proto_minor / proto_patch 载于 login 与 login_ack（见 06 章）
错误码 以符号名字符串承载（code / reason 字段，类型为 str） 不得填写自由文本

数据面

  • UDP 使用 CRC32（完整性非安全性）：CRC32 无密钥，任何能发包的主机都能伪造合法包。
  • UDP 使用 chunk_digest（BLAKE3 8 字节，完整性非安全性）：摘要无密钥， 提供的是端到端完整性（可发现接收侧损坏），不是身份认证。
  • session_id（u64）跨 Server 进程重启不复用 —— 否则重启前仍在飞行中的数据包 会命中新建会话，把数据写入错误的文件（见 09 章）。
  • 文件级内容 hash（Blake3）：32 字节原始摘要（hash32）， 禁止以十六进制串承载；日志与 UI 展示时由实现自行转十六进制（见 06 章）。

数据加密

  • 数据加密由实现层自选。
  • 约束：应用层加密不得改变 chunk 与文件偏移的映射关系。 若加密改变了 payload 长度或边界，则 offset = chunk_id × chunk_size 的随机写盘语义失效。
  • 加密单元必须与 chunk 边界对齐，且密文长度必须恰好等于 chunk_size（末块除外）。
加密与写盘映射的约束（chunk 边界必须对齐）
chunk_id = 0
offset = 0 × chunk_size
chunk_id = 1
offset = 1 × chunk_size
chunk_id = 2
offset = 2 × chunk_size
密文长度 = chunk_size
密文长度 = chunk_size
末块（除外）
加密单元与 chunk 边界对齐、密文长度恰好等于 chunk_size（末块除外）时， offset = chunk_id × chunk_size 的随机写盘语义才不被破坏。

源地址校验

  • 数据面地址必须做源地址校验：接收方必须校验 UDP 包的源地址:端口 与该会话经 PROBE 确认的对端地址一致，不一致即丢弃。
  • 这不能替代认证（地址可伪造），但能挡住非定向的误发与扫描。

重放保护

  • 接收方必须拒绝 chunk_id ≥ 该会话 chunk_count 的包 （越界，见 08 章）。
  • 接收方必须校验 session_id 与本会话一致。
  • 两者之外的重放由位图幂等性兜底（重复 chunk 静默丢弃）。
完整性 ≠ 安全性：CRC32 与 Blake3 的作用是发现损坏 / 不一致， 并不提供防伪能力；任何能发包的主机都能伪造 CRC32 合法的包， 因此防伪依赖控制面的认证与 ACL（见 21 章）。

状态与权限

  • UDP 会话必须绑定到发起它的控制连接（及其 device_id）。
  • Server 不向未知端口发送 UDP；目标地址必须来自 PROBE 报文（见 07 章）。
  • TCP 数据面降级需重校验权限。

常见实现陷阱：把 CRC32 当作防伪手段；用十六进制串承载 Blake3 摘要； 加密改变了 chunk 边界导致 offset = chunk_id × chunk_size 失效； 跳过 UDP 源地址校验；由 device_id 直接推导凭据（不得）。

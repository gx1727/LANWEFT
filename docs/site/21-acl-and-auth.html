21 认证与访问控制（Authentication & Authorization）

本章要点：控制通道的认证在连接握手阶段完成，Server 必须在 login 中校验认证凭据， 失败必须以 login_ack（result = 0，即 fail）回应并关闭连接。 凭据必须与 device_id 绑定；令牌不得由 device_id 直接推导。 跨 device_id 的隔离由连接级 / Server 级 / 资源级 / 共享清单级四层承担。

四层访问控制

跨 device_id 隔离的四层（自协议层到资源记录）
1 · 连接级
一条控制连接只承载一个 device_id（见 06 章「会话与连接的关系」）；跨 device_id 的会话在协议层无法表达
2 · Server 级
Server 必须校验会话的 device_id 与连接绑定一致；不一致必须以 session_abort（reason = ACL_DENY）拒绝
3 · 资源级
素材记录（asset_id）的所有权由 Server 维护；asset_recall 必须校验发起方的 device_id 对该记录的所有权，越权时回 code = ACL_DENY（见 06 章）
4 · 共享清单级
预置素材记录的归属者是 Server；所有已认证设备都可以列举（material_list）与拉取（download_start），但不得撤回 —— 对预置素材记录发布 asset_recall 必须以 ACL_DENY 拒绝（见 09 章「预置素材与共享清单」）

目标

  • 多 Client 隔离
  • 防止跨 device_id 访问
  • 服务端裁决边界明确

认证（规范性）

控制通道的认证在连接握手阶段完成（见 06 章「连接生命周期」）。

  • Server 必须在 login 中校验认证凭据； 校验失败必须以 login_ack（result = 0，即 fail）回应并关闭连接。
  • 凭据必须与 device_id 绑定：认证通过后，连接即与该 device_id 绑定， 该连接上的一切会话必须属于该 device_id。
  • 认证方式必须至少支持以下其一：
方式 凭据 说明
共享令牌 login.token Server 侧存储 token → device_id 绑定；令牌必须随机生成
客户端证书 TLS Client Certificate 证书的 SAN / CN 必须携带 device_id；此时 login.token 必须为空串（长度 0）
  • 令牌不得由 device_id 直接推导 —— 设备标识不应等价于凭据 （见 23 章「隐私」）。
  • Server 必须对失败的认证尝试做速率限制与审计。
  • 认证失败必须通过 login_ack.code 上线路（19 章）： LOGIN_FAILED / CLIENT_ID_INVALID / PROTO_VERSION_UNSUPPORTED。

访问控制（规范性）

跨 device_id 的隔离由以下四层承担：

  1. 连接级：一条控制连接只承载一个 device_id。 跨 device_id 的会话默认无法表达；peer 会话是唯一例外： 它显式绑定两个 device_id，由 Server 通过 share grant 授权（见「C↔C peer 授权」）。
  2. Server 级：Server 必须校验会话的 device_id 与连接绑定一致； 对 peer 会话，必须校验 sender_device_id 与 receiver_device_id 各自与对应控制连接绑定一致。 不一致必须以 session_abort（reason = ACL_DENY）拒绝。
  3. 资源级：素材记录（asset_id）的所有权由 Server 维护； asset_recall 必须校验发起方的 device_id 对该记录的所有权， 越权时回 code = ACL_DENY（见 06 章）。
  4. 共享清单级：预置素材记录的归属者是 Server， 所有已认证设备都可以列举（material_list）与拉取（download_start）， 但不得撤回 —— 对预置素材记录发布 asset_recall 必须以 ACL_DENY 拒绝（见 09 章「预置素材与共享清单」）。

C↔C peer 授权（规范性）

  • peer 会话是唯一跨两个 device_id 的会话类型：sender_device_id 与 receiver_device_id 都必须各自绑定一条已认证控制连接；Server 必须同时校验两者。
  • share grant：(sender_device_id, receiver_device_id, file_hash, expiry)， 由 Server 维护。peer_start / peer_offer 必须落在该 grant 内，否则 ACL_DENY。
  • 接收方可以拒绝；拒绝经 peer_response（result = fail， code = PEER_DECLINED）表达，Server 以 session_abort 终止。
  • 没有 C↔C 的 login：peer 身份完全复用双方与 Server 的既有认证； 数据面使用 Server 签发的 transfer_token 做端点确认（Stage 1）。
  • R1 的中转素材/授权必须绑定 transfer_id 与 grant，完成后回收； 不得让接收方凭 file_hash 越权访问其他私有素材。
  • 私有素材归属不因 peer 传输改变；Server 侧归属仍按上传 device_id。

传输安全（规范性）

  • 控制通道必须支持 TLS；应当启用。
  • 未启用 TLS 时，认证凭据以明文传输 —— 不得在非受信网络（含公共 WiFi）中这样部署。
  • 控制通道与数据面相互独立： 数据面不复用控制连接的 TLS 会话；UDP 数据面不自带加密 （见 20 章）。

强约束

  • 一条连接必须绑定唯一 device_id
  • Server 不得在连接上接受与绑定身份不符的会话
  • 会话必须绑定唯一 device_id

审计

  • 记录认证失败尝试、跨 device_id 的会话操作与 session_abort 原因
常见实现陷阱：把 device_id 直接当作凭据（令牌不得由 device_id 直接推导）； 认证失败后仍然保持连接；用客户端证书时未把 login.token 置为空串； 在公共 WiFi 之类非受信网络上以明文凭据部署；把预置素材记录当作私有素材记录允许撤回。

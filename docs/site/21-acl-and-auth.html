21 访问控制与认证（ACL & Auth）

本章要点：控制通道的认证在连接握手阶段完成，Server 必须在 login 中校验认证凭据， 失败必须以 login_ack（result = 0）回应并关闭连接； 凭据必须与 device_id 绑定。 跨 device_id 的隔离由连接级、Server 级、资源级三层承担。

认证（规范性）

控制通道的认证在连接握手阶段完成（见 06 章「连接生命周期」）。

  • Server 必须在 login 中校验认证凭据； 校验失败必须以 login_ack（result = 0，即 fail）回应并关闭连接。
  • 凭据必须与 device_id 绑定：认证通过后，连接即与该 device_id 绑定， 该连接上的一切会话必须属于该 device_id。
  • 认证方式必须至少支持以下其一。
方式 凭据 说明
共享令牌 login.token Server 侧存储 token → device_id 绑定；令牌必须随机生成
客户端证书 TLS Client Certificate 证书的 SAN / CN 必须携带 device_id； 此时 login.token 必须为空串（长度 0）
  • 令牌不得由 device_id 直接推导 —— 设备标识不应等价于凭据 （见 23 章「隐私」）。
  • Server 必须对失败的认证尝试做速率限制与审计。
  • 认证失败必须通过 login_ack.code 上线路（19 章）： LOGIN_FAILED / CLIENT_ID_INVALID / PROTO_VERSION_UNSUPPORTED。

访问控制（规范性）

跨 device_id 的隔离由以下三层承担：

跨 device_id 隔离的三层
1 · 连接级
一条控制连接只承载一个 device_id（见 06 章「会话与连接的关系」）；跨 device_id 的会话在协议层无法表达
2 · Server 级
Server 必须校验会话的 device_id 与连接绑定一致；不一致必须以 session_abort（reason = ACL_DENY）拒绝
3 · 资源级
素材记录（asset_id）的所有权由 Server 维护；asset_recall 必须校验发起方的 device_id 对该记录的所有权，越权时回 code = ACL_DENY（见 06 章）
连接级 Server 级 资源级
层级 承担者 校验内容 拒绝时的表现
连接级 协议层 一条控制连接只承载一个 device_id 跨 device_id 的会话无法表达
Server 级 Server 会话的 device_id 与连接绑定一致 session_abort（reason = ACL_DENY）
资源级 Server 维护的素材记录 发起方的 device_id 对该记录（asset_id）的所有权 code = ACL_DENY（见 06 章）

传输安全（规范性）

  • 控制通道必须支持 TLS；应当启用。
  • 未启用 TLS 时，认证凭据以明文传输 —— 不得在非受信网络（含公共 WiFi）中这样部署。
  • 控制通道与数据面相互独立： 数据面不复用控制连接的 TLS 会话；UDP 数据面不自带加密（见 20 章）。

强约束

  • 一条连接必须绑定唯一 device_id。
  • Server 不得在连接上接受与绑定身份不符的会话。
  • 会话必须绑定唯一 device_id。

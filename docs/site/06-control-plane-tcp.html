06 控制面（TCP）

本章要点：控制面是会话状态推进与可靠性裁决的唯一通道，跑在 TCP 上， 一条连接可承载多个并发会话。控制帧 = 16 字节定长帧头 + 二进制消息体； 帧头 magic 恒为 0x574E414C（线上字节 4C 41 4E 57，小端序）， header_crc32 覆盖帧头中除自身外的 12 字节。 接收方必须先过 magic → header_crc32 → frame_len 三项校验再读帧体， 任一失败即失步：必须丢弃该连接上未解析的数据并关闭连接， 不得就地「跳过一帧继续解析」。frame_len 上界为 1 MiB； 定长区一旦发布即冻结，新增字段只能追加在扩展区，接收方必须忽略扩展区。

字段语义不重叠：result 字段（success / fail）用于「完成类」消息； code 字段用于「结果可能成功也可能失败」的消息；reason 字段用于「终止类」消息。 三者语义不重叠，实现不得混用。

控制面是会话状态推进与可靠性裁决的唯一通道。

  • 传输：TCP。Client 主动连接 Server，一条控制连接可承载多个并发会话。
  • 消息格式：定长帧头 + 二进制消息体（见「帧格式」与「消息体布局」）。
  • 连接即上下文：同一连接内的消息严格有序，因此不存在陈旧消息问题； 跨连接的状态由 login / login_ack 的权威快照一次性重建。

帧格式（规范性）

控制帧为小端序二进制结构，与 08 章的数据包格式采用同一端序约定。

偏移  大小  字段          说明
0-3   4     magic         u32，协议魔数，固定 0x574E414C（"LANW"）
4-7   4     frame_len     u32，本帧总字节数（含本帧头），见下
8-11  4     header_crc32  u32，帧头校验码，见「帧头校验码」
12    1     msg_type      u8，消息类型编号，见「消息类型编号」
13    1     flags         u8，帧级标志位；bit0-7 全部保留，接收方必须忽略
14    1     body_version  u8，消息体布局版本号；初值为 0
15    1     reserved      u8，保留字节
16..  N     body          消息体，长度 = frame_len − 16
  • FRAME_HEADER_SIZE = 16 字节（控制帧定长帧头长度）。
  • magic 必须为 0x574E414C；该常量不得随协议版本变更 （版本差异一律由 proto_version / body_version 表达，见 08 章「版本比较规则」）。 按小端序存放时，线路上的四个字节为 4C 41 4E 57（"LANW"）—— 抓包比对时必须按该字节序判断。
  • frame_len 必须 ≥ 16（最小帧长即帧头长度）。
  • frame_len 必须 ≤ 1 MiB（记为 max_frame_len）。 接收方读到 frame_len > max_frame_len 时必须丢弃该帧并关闭连接 —— 帧边界已不可信，无法继续解析。
  • 接收方必须按 frame_len 读满后再解析：
  • 不得假设一帧一次 recv 到达（TCP 是字节流，必须处理拆包）；
  • 不得按换行或任何字节模式切分。
  • 发送方必须写出完整帧；不得依赖多次 write 的边界。
  • body_version 由消息体布局的版本决定，与协议版本（proto_version）相互独立。 当前所有消息的 body_version 必须为 0。 接收方遇到不认识的 body_version 时，必须忽略该值， 按已知定长区尽力解析，并忽略变长区之后的尾部字节（见「扩展区」）。
  • 不携带载荷级 CRC32（说明）：TCP 自身提供字节流校验和与重传， 控制帧不重复载荷级 CRC32 —— 与 08 章数据面因 UDP 无可靠校验而携带 crc32 不同。 但帧头必须携带 header_crc32：其目的不是完整性校验，而是帧同步 （见「帧头校验码」与「帧同步与失步处理」）。

header_crc32 使用 CRC-32/ISO-HDLC（又称 CRC-32、zlib crc32）—— 与 08 章的 crc32 同一变体，本协议不存在第二个 CRC32 变体。

覆盖区间（规范性）：被校验的字节是帧头中除 header_crc32 字段自身之外的 12 字节，按下列顺序拼接（不是帧内的单一连续区间）：

magic(4) ‖ frame_len(4) ‖ msg_type(1) ‖ flags(1) ‖ body_version(1) ‖ reserved(1)
  • 上式对应帧内的两段连续区间：字节 0–7 与字节 12–15； 实现可直接对这两段拼接后的 12 字节计算 CRC32。
  • 发送方必须在写出帧头前计算并填入该值。
  • 接收方必须在解析帧头时校验该值；校验失败即判定失步（见下）。

为何校验帧头而不校验载荷（说明）：载荷完整性已由 TCP 保证， 帧头校验码解决的是另一个问题 —— 确认当前读到的字节确实是一个帧头。 实现一旦出现消费偏移（多读 / 少读一个字节）， 仅凭 frame_len ∈ [16, 1 MiB] 这一弱判据， 存在约 1e-5 ~ 1e-6 的概率把随机字节当成一帧合法控制消息执行 （例如伪造的 session_pause / session_abort）； 加上 magic（2⁻³² 误命中）与 header_crc32 后，该路径被消除。

magic 的字节序陷阱（规范性）：

  • magic 是 u32，按小端序存放 —— 线上字节为 4C 41 4E 57， 不是 57 41 4E 4C，也不是 ASCII 字符串 "LANW" 的十六进制串写法 4C 41 4E 57 之外的任何形式；
  • 换言之：抓包工具按字节显示时应当看到 4C 41 4E 57； 按 u32 解读时应当得到 0x574E414C。
  • 抓包比对必须按线上字节序 4C 41 4E 57 判断，不得按 0x574E414C 的字节序反推。

校验步骤（规范性）：接收方读到 16 字节帧头后必须依次执行：

  1. 比对线上字节 4C 41 4E 57（即 magic == 0x574E414C）；
  2. 计算 crc32(字节[0x8] ‖ 字节[0xC:0x10]) 并与 header_crc32 比对 （本例中被校验的 12 字节为 4C 41 4E 57 22 00 00 00 01 00 00 00）；
  3. 校验 frame_len ∈ [16, max_frame_len]；
  4. 以上全部通过后，才必须按 frame_len 读满 frame_len − 16 字节的帧体。

可复核性（说明）：本例的 header_crc32 由 CRC-32/ISO-HDLC（zlib crc32） 对上述 12 字节计算得出，实现必须能复核出 0xCCD5E3D3。

帧同步与失步处理（规范性）

接收方必须按下列顺序校验帧头，任一不通过即判定失步（desync）：

  1. magic == 0x574E414C；
  2. header_crc32 校验通过；
  3. frame_len ∈ [16, max_frame_len]。

失步的处置（规范性）：

  • 失步必须导致：丢弃该连接上尚未解析的全部数据、关闭连接、 并以 PROTOCOL 类错误码记录（MAGIC_MISMATCH / HEADER_CRC_INVALID / FRAME_LEN_INVALID，见 19 章）。
  • 失步后不得在本连接上继续解析任何帧，不得继续执行协议状态机。
  • 受影响会话必须按 13 章「断线重连」恢复 —— 重新建立控制连接， 经 login / login_ack 的权威快照重建状态。 不得在失步的连接上「跳过一帧继续解析」。

为何失步必须断连而非就地续解（说明）： 被跳过的帧中可能含状态转移消息（session_pause / session_abort / missing_chunks）。 一方跳过、一方不跳过时，双方对会话状态的认知已经分叉； 此时「看似同步、实则状态不一致」的连接比「已断开的连接」更危险 —— 断开的连接可以由权威快照无歧义地重建，分叉的连接不能。

有界扫描（推荐性，非规范性）： 实现可以在关闭连接前执行一次有界扫描以辅助定位失步点 （便于区分「对端不是本协议」与「本端消费偏移」）。 若实现提供该能力，其扫描范围、候选判据与扫描上限见下节「接收状态机」； 扫描结果仅用于诊断与日志；不得用于恢复协议状态机， 不得把扫描到的帧当作可信的控制消息执行。

接收状态机（规范性）

接收方必须以如下状态机驱动帧解析。状态机的内部实现方式自由 （同步阻塞读、异步回调、协程、事件循环均可）， 但其可观测行为必须满足本节的状态转移表与约束。

RESYNC 逐字节前移 命中满足「候选判据」的偏移 记录候选偏移（仅诊断）；必须关闭连接 CLOSED
RESYNC 逐字节前移 扫描量超过 resync_max_scan 必须关闭连接 CLOSED
任意 连接关闭 / 超时 / 对端 FIN — 关闭连接；会话进入 13 章「中断处理」 CLOSED

约束（规范性）：

  • 三项校验（magic → header_crc32 → frame_len）必须在解析帧体之前完成； 不得先解析再校验，不得在三项校验通过前读取帧体。
  • RESYNC 不得回到 SYNC；实现不得在 RESYNC 状态中执行任何协议消息， 不得把扫描到的帧当作可信的控制消息。
  • 校验失败时不得采用「跳过 16 字节继续同步」的做法 —— 该做法只会把失步延后， 且丢弃的可能是一整帧合法消息。
  • 帧体必须按 frame_len 一次性读满后再解析； 读不满即视为对端中断，必须关闭连接。

候选判据（规范性，用于 RESYNC 的有界扫描）： 候选偏移 p 必须同时满足：

  1. p 起的 FRAME_HEADER_SIZE 字节构成合法帧头（三项校验通过）；
  2. p 起的第一帧完整可读（可用字节数 ≥ 该帧 frame_len）；
  3. 第一帧之后紧邻的第二帧的帧头也完整可读，且其三项校验通过 （即「连续两帧自洽」）。

不满足第 3 条的候选不得采信 —— 消息体中偶然出现的 magic 几乎必然后跟非法帧头。

扫描上限（规范性）：resync_max_scan = 64 KiB。 实现可以取更小值，不得取更大值。

伪代码（说明性）：

常量：MAGIC = 0x574E414C
      HEADER_SIZE = 16
      MAX_FRAME_LEN = 1 MiB
      RESYNC_MAX_SCAN = 64 KiB

SYNC（控制面接收循环）
  loop:
    若 缓冲区字节数 < HEADER_SIZE:
        继续读取（阻塞；超时 → CLOSED）
        continue

    h = 缓冲区[0 : HEADER_SIZE]
    magic, frame_len, crc, msg_type, flags, body_version, reserved = 解析(h)

    若 magic != MAGIC:                              → 失步(MAGIC_MISMATCH)
    若 crc32(h[0:8] ‖ h[12:16]) != crc:             → 失步(HEADER_CRC_INVALID)
    若 frame_len < HEADER_SIZE 或 frame_len > MAX_FRAME_LEN:
                                                      → 失步(FRAME_LEN_INVALID)

    body = 精确读取(frame_len − HEADER_SIZE)   # 读不满 → CLOSED（对端中断）
    交给消息处理器(msg_type, body)             # 非法消息只丢帧，不断连
    消费缓冲区前 frame_len 字节
    continue

失步(code):
    记录错误码 code
    若 实现提供有界扫描:  转 RESYNC          # 仅诊断
    否则:                  关闭连接 → CLOSED

RESYNC（仅诊断，不恢复协议状态机）
  从当前偏移逐字节前移，最多 RESYNC_MAX_SCAN 字节:
    若 候选满足「候选判据」:  记录候选偏移;  break
  关闭连接 → CLOSED

实现提示（说明性）：缓冲区必须支持「读满一帧再消费」的滑动语义 —— 读帧体期间到达的字节必须留在缓冲区中供下一帧使用， 不得因一次 read 读到多帧而丢弃残余字节。

首帧锚点（规范性）

  • 一条控制连接上的第一帧必须是 login（msg_type = 0x01）。 接收方在收到 login 之前必须丢弃该连接上的一切消息（见「连接生命周期」）； 首帧不是 login 时必须关闭连接（CONTROL_ERROR）。
  • 该锚点的作用是在连接建立的第一时间确认帧同步： 首帧若连 magic 与 header_crc32 都过不了，说明本端或对端存在消费偏移， 继续读只会加深错位。

帧级错误处理（规范性）

header_crc32 校验失败 判定失步，丢弃并关闭连接（HEADER_CRC_INVALID）
frame_len == 0 判定失步，丢弃并关闭连接（FRAME_LEN_INVALID；读取指针无法推进）
frame_len > max_frame_len 判定失步，丢弃并关闭连接（FRAME_LEN_INVALID；帧边界不可信）

帧头三项校验全部通过 ⇒ 帧边界可信 ⇒ 其后的错误只丢帧、不断连 —— 单条畸形消息不得导致整条连接失效。 帧头三项校验任一失败 ⇒ 帧边界不可信 ⇒ 判定失步 ⇒ 必须断连。

扩展区（规范性）

  • 定长区与变长区之后若仍有剩余字节，该部分为扩展区。
  • 接收方必须忽略扩展区的全部内容，不得因扩展区非空而报错。
  • 扩展区是后续版本新增字段的落点：新增字段只能追加在扩展区， 既有字段的偏移与大小不得变更。
  • 因此同一 msg_type 的定长区一旦发布即冻结。

TCP 特有约束（规范性）

  • 控制连接必须启用 TCP_NODELAY（控制消息延迟敏感，禁止 Nagle 合并）。
  • 发送方应当把多个待发消息合并为一次 write（减少系统调用与报文段数）； 但不得为合并而延迟发送超过 50 ms（信用与裁决节奏，见 11 章）。
  • 接收方必须为每条连接维持独立的读缓冲与写队列； 不得在写队列阻塞时阻塞读循环（否则会与心跳超时相互放大）。

  • 定长可选字段（u32 计数类）：使用存在标志位。 标志位为 0 时该字段必须取 0，且接收方必须按「未携带」处理。

记录内联字符串（说明）

login_ack 的会话快照记录含一个可变的错误码字符串。 该字符串内联在记录的定长部分之后，长度由记录内的 code_len 给出， 记录总长 = 定长部分 + code_len。必须先读定长部分，再读 code_len 字节， 然后才是下一条记录。

连接生命周期（规范性）

  1. Client 主动连接 Server 的控制端口。
  2. Client 必须在连接建立后立即发送 login 帧。
  3. Server 必须校验 login（认证凭据、协议版本、设备身份）； 校验失败必须以 login_ack（result = fail）回应并关闭连接。
  4. Server 必须在收到 login 之前丢弃该连接上的一切消息。
  5. 校验通过后，Server 回 login_ack，其中携带被成功恢复会话的权威快照。
  6. 连接存续期间，双方必须按「心跳与超时」维持连接。
  7. 任一方关闭连接时，该连接承载的会话进入中断处理（见 13 章）。

握手超时（规范性）：Server 必须在连接建立后 10 秒内未收到 login 时 关闭该连接（防止半开连接占用资源）。 连接建立失败（如对端拒绝、地址不可达）按 CONNECTION_FAILED 记录 （见 19 章）；连接被任一方关闭按 CONNECTION_CLOSED 记录。

认证与身份（规范性）

  • 身份在连接握手阶段确定，不得依赖后续消息自证。
  • Server 必须把每条控制连接绑定到唯一 device_id； 该连接上的一切会话必须属于该 device_id。
  • device_id 必须与认证凭据绑定（见 21 章）； 不一致必须以 CLIENT_ID_INVALID 拒绝。
  • 在线状态由连接存续直接表达：连接存在即在线。 Server 必须维护连接表，并据此回答「某设备是否在线」。

会话与连接的关系（规范性）

  • 一条控制连接可以承载多个并发会话； 消息中的 session_id 用于区分会话，因此 session_id 在所有会话类消息中必须出现。
  • 控制通道不重放历史帧流；13 章规定的持久化完成回执可以幂等重发。同一连接内的消息严格有序， 跨连接的状态由 login 的权威快照一次性重建。
  • 数据面与控制面相互独立：控制连接承载 N 个会话时， 数据面端口可以被多个会话共用 —— UDP 包头中的 session_id 足以区分（见 08 章）。

心跳与超时（规范性）

消息 方向 周期
ping 双向 10 秒
pong 双向 收到 ping 后立即
  • 任一方必须每 10 秒发送一次 ping；收到 ping 必须立即回 pong。
  • 30 秒内未收到该连接的任何消息时，接收方必须关闭该连接 （按 TIMEOUT_HEARTBEAT 记录，见 19 章）。
  • 连接超时（30s）必须早于会话超时（60s，见 09 章）触发： 先断开连接，再由会话超时兜底清理。

0 4 chunk_id u32 部分缺失的逻辑块

两级缺失语义（规范性）：缺失以 symbol 为单位记账，以 chunk 为单位上报：

  • chunks：一个 symbol 都没收到的块（完全缺失）；这些块按 chunk_count 列出。
  • partial[]：收到了至少一个、但未收全的块；received_mask 精确指出收到了哪些 symbol （发送方取补集得到缺失）。

掩码语义统一（规范性）：块内位图、partial[].received_mask 与 chunk 完成判定 使用同一语义 —— bit i = 1 表示第 i 个 symbol 已收到。

  • 发送方必须按下式求缺失：missing = full_mask ^ received_mask， 其中 full_mask = (1 << S_chunk) − 1； S_chunk 为该块的 symbol 数，末块由 ceil((size − chunk_id × chunk_size) / symbol_size) 推出。
  • received_mask 必须非零，且不得等于 full_mask （等于 full_mask 时应作为已完成块，不进入 partial[]）。
  • bit i ≥ S_chunk 必须为 0；越界即按 SERIALIZATION_ERROR 丢弃该帧。
  • missing_count：二者合计的缺失 symbol 精确总数 = Σ(完全缺失块的 S) + Σ(S_chunk − popcount(partial[].received_mask))。 发送方据此推算对端已收数与在途量（见 11 章），因此该值不得是估计值。

chunks / partial[] 的语义（规范性）：二者恒为「发布方自己尚未收到的部分」， 而不是「我已有的部分」。

  • chunks：一个 symbol 都没收到的完全缺失块。
  • partial[]：收到了一部分、尚未收全的块；received_mask 指出收到了哪些 symbol。
  • 上传方向 Server→Client：Server 报告「我还缺这些 symbol」，Client 收到后重传。
  • 下载方向 Client→Server：Client 报告「我还缺这些 symbol」，Server 收到后重传。

两种方向下语义一致：接收方报告缺失，发送方补发。

mode 语义 载荷 收到方的处理
report 发布方报告自己尚未收到的 symbol chunks 与 partial[] 按两级列表重传；两者皆空 且未置复核轮标志时表示「我这边没有缺失，可继续推进」；置复核轮标志时表示「全部块」（见下）

按会话方向展开（direction 见 09 章）：

direction mode=report 的发布方 载荷含义 收到方的处理
upload Server（接收方） Server 尚未收到的 symbol Client 重传这些 symbol
download Client（接收方） Client 尚未收到的 symbol Server 重传这些 symbol

missing_count 的取值（规范性）：missing_count 必须是位图中尚未收到的 symbol 精确总数（不是 chunks 的条数，也不是 partial_count）。 发送方据此推算对端已收数与在途量（见 11 章），因此该值不得是估计值或近似值。 mode=request 时必须为 0。

复核轮标志 flags.bit1（规范性）：flags.bit1 = 1 表示本条裁决是复核轮 的启动裁决（见 12 章「复核轮」）。每条 report 都携带当前代号； bit1 置位时必须为代号 2。其后同轮普通裁决只带代号、不再置 bit1。 request 不声明代号（bit2–3 必须为 0）。恢复时先同步代号的规则见 13 章。

  • 该标志仅在 mode = report 时有意义；mode = request 时必须为 0。
  • 复核轮中，接收方必须已清空位图，必须要求发送方全量重发：
  • chunks 与 partial[] 必须为空（含义为「全部块」，而非「没有缺失」）；
  • missing_count 必须等于该会话的 symbol_count（flags.bit0 必须为 1）。
  • 发送方收到该标志时必须按 12 章「复核轮」执行： 重新打开源文件、从 chunk_id = 0 起全量重发，并重置顺序流与在途量基线。
  • 发送方必须对同一会话最多响应一次复核轮 （接收方的发起次数上限见 12 章「上限」；该上限按会话计，不随连接重建而重置）。

定点重读标志 flags.bit6（规范性）：flags.bit6 = 1 表示接收方在停滞升级时要求 发送方对 chunks 与 partial[] 涉及的 symbol 重新读取源文件后重发 （见 12 章「停滞检测与升级」）。

  • 该标志仅在 mode = report 时有意义；mode = request 时必须为 0。
  • 发送方收到置位本条时必须重新打开源文件并读取对应 symbol 区间， 不得复用页缓存或内存缓冲中的旧副本，然后重发这些 symbol。
  • 每会话的定点重读至多一次（计数与位图一同持久化，见 12 章）。
  • 定点重读与摘要对帐、复核轮是相互独立的机制，各有各的次数上限。

裁决与窗口推进（规范性）：窗口推进由信用完成 —— 接收方按 11 章 「窗口推进信用」在收到新块时下发 window_update；missing_chunks（mode=report） 携带的 missing_count 同样构成一次信用。发送方以两者中最新的计数推进窗口。 缺失列表为空时不承担周期性推进职责；活性由 11 章的 1000 ms 索要机制保证。

为什么需要 request：上传方向的发送方（Client）无法自行表达「我还缺什么」—— 它并不缺任何块。request 是它向接收方（Server）索要缺失裁决的唯一途径， 也是 11 章兜底索要机制与 12 章看门狗的载体。

空列表的两种含义（规范性）：chunks 与 partial[] 皆为空时，其含义由复核轮标志区分：

复核轮标志 含义 发送方动作
flags.bit1 = 0 本会话没有缺失 symbol 继续推进新数据
flags.bit1 = 1 复核轮：全部块都需要重发 按 12 章「复核轮」全量重读重发

立即裁决（推荐性）：接收方可以在检测到空洞的那一刻立即下发 mode=report， 不必等待 50ms 周期，以降低丢包恢复时延。 当本会话存在缺失时，每 50 ms 下发一次裁决仍为规范性要求（见 11 章）。

  • 周期：接收方约每 500ms 发布一次。

peer_transport_switch（0x23）

定长区（36 字节）

偏移 大小 字段 类型 说明
0 8 session_id u64 会话 ID
8 1 transport enum8 切换后的模式：0 = direct，1 = relay_r2
9 1 reason enum8 switch_reason
10 1 peer_addr_family u8 4 / 6；0 = 未知
11 1 reserved u8 保留
12 2 peer_udp_port u16 新数据面 UDP 端点（对端或 S 中转）

语义（规范性）：

  • 恒由 Server 发布给双方；切换不改变 session_id、sender_device_id、 receiver_device_id、generation 或会话状态。
  • 收到后双方必须： 1. 立即停用旧端点（旧端点上的包必须丢弃）； 2. 清空在途量估计并按对端最新裁决重建信用基线； 3. 保留接收方位图与临时文件，从第一个缺失 symbol 继续； 4. 按新端点重新绑定：direct 时重新 peer PROBE；relay_r2 时以 S 中转端点为对端。

  • 任一方未在超时内完成重绑定，Server 必须以 session_abort （reason = PEER_RELAY_UNAVAILABLE 或 TIMEOUT_NO_ACTIVITY）终止。

session_pause（0x0E）

定长区（8 字节）

偏移 大小 字段 类型 说明
0 8 session_id u64 会话 ID

语义（规范性）：暂停会话，双方停止发送数据面数据包， 会话转入 PAUSED 状态；位图与临时文件全部保留。

  • 无独立 ack：session_pause 本身即状态转移消息， 对端转入 PAUSED 后必须停止发送数据面数据包； 恢复见 10 章「暂停与恢复」。
  • 不表示「切换」：重复发布是幂等的（已处于 PAUSED 时不再产生状态变化）。 恢复一律通过 resume_session / resume_ack 表达。
  • 与 session_abort 的区别：暂停可恢复，中止不可恢复。
  • 与 resume_session 的区别：session_pause 是显式暂停， resume_session 是暂停后的恢复；两者的恢复动作相同。

asset_recall（0x10）

定长区（4 字节）

偏移 大小 字段 类型 说明

1 3 reserved — 保留

变长区（顺序固定）

  1. file_hash：hash32。要撤回的素材的 Blake3 摘要。
  2. asset_id：str，仅当 flags.bit0 = 1 时存在； 素材记录 ID，为空时按 file_hash 定位。

资产撤回请求：Client 请求 Server 删除已接收的素材记录。 本消息不关联 session，可独立于传输会话使用。

幂等：对同一 file_hash / asset_id 重复撤回必须是幂等的 —— 第二次撤回若记录已不存在，应回 deleted = false 且 code 为空串 （视作「已处于目标状态」），不得报错。

  • 本消息不得创建任何传输会话（见 09 章「发现」）。

material_list_ack（0x18）

定长区（16 字节）

偏移 大小 字段 类型 说明
0 8 max_seq u64 Server 侧当前的最大 seq
8 4 count u32 本批条目数
12 1 flags u8 bit0 = 末批（没有更多条目了）；bit1-7 保留
13 3 reserved — 保留

变长区（顺序固定）

  1. entries[]：count 条素材条目记录（格式见「素材条目记录」）。
  • 发布方恒为 Server。
  • 分页（规范性）：若 flags.bit0 = 0，Client 必须以本批最后一个条目的 seq 作为 since_seq 再次查询，直到 flags.bit0 = 1。
  • 增量（规范性）：Client 可以用已知的最大 seq 作为 since_seq， 只取新增条目；Server 必须只返回 seq > since_seq 的条目。
  • 水位的取法（规范性）：Client 必须以最后收到的条目的 seq 作为下一次查询的 since_seq；不得使用本应答的 max_seq —— max_seq 可能超前于本批已返回的条目，用它作水位会跳过条目。

delivery_offer（0x19）

定长区（48 字节）

偏移 大小 字段 类型 说明
0 8 session_id u64 Server 分配的会话 ID（见 09 章「创建规则」）
8 8 size u64 文件大小（字节）
16 8 mtime u64 文件修改时间戳（UTC 秒）
24 4 chunk_count u32 总块数 = ceil(size / chunk_size)
28 4 window u32 滑动窗口大小（会话级在途 symbol 上限），见 11 章
32 4 connection_window u32 连接级在途 symbol 上限，见 11 章
36 4 chunk_size u32 协商确定的逻辑块大小（symbol_size 的整数倍，1 ≤ S ≤ 64）
40 2 udp_port u16 数据面 UDP 端口；Client 必须向它发出 PROBE
42 2 tcp_port u16 数据面 TCP 降级通道端口；0 表示不支持。不是控制面端口
44 1 flags u8 bit0-7 保留（接收方必须忽略未知位）
45 1 security_level enum8 本会话选定的安全等级（1/2/3）
46 1 security_suite enum8 lv3 套件：0 = 无，1 = AES-256-GCM，2 = ChaCha20-Poly1305
47 1 reserved u8 保留

变长区（顺序固定）

  1. file_hash：hash32。待投递文件内容的 Blake3 摘要。
  2. file_name：str。文件名（UTF-8）。
  • 发布方恒为 Server。
  • 本消息携带全套会话参数：Client 接受后必须按这些参数工作， 不得自行改动 window / connection_window / chunk_size。
  • Client 必须校验 chunk_count == ceil(size / chunk_size)， 不一致即以 delivery_response（result = fail，code = SERIALIZATION_ERROR） 拒绝。
  • 本消息不携带任何认证凭据 —— 投递只可能发生在已认证的控制连接上。

delivery_response（0x1A）

定长区（12 字节）

偏移 大小 字段 类型 说明
0 8 session_id u64 对应 delivery_offer 的会话 ID
8 1 result enum8 0 = fail（拒绝）、1 = success（接受）
9 1 flags u8 bit0 = file_hash 有效；bit1-7 保留
10 2 reserved u16 保留

变长区（顺序固定）

  1. code：str。result = fail 时的机器可判定错误码（见 19 章，如 DELIVERY_DECLINED / STORAGE_FULL / ACL_DENY / SERIALIZATION_ERROR）； result = success 时必须为空串。
  2. file_hash：hash32，仅当 flags.bit0 = 1 时存在。 接受时必须携带，且必须与 delivery_offer.file_hash 一致。
  • 发布方恒为 Client。
  • result = success 时，Client 必须打开数据面 socket 并发出 PROBE （见 09 章「流程」、07 章「接收方 socket 生命周期」）。
  • result = fail 时，Client 不得发出 PROBE。

ping（0x12）/ pong（0x13）

定长区（8 字节）

偏移 大小 字段 类型 说明
0 8 ts u64 发送方的单调时钟毫秒值；仅用于日志与 RTT 统计，不得用于协议判断

非法行为

  • 在同一条连接上使用另一个 device_id 的会话
  • Server 发布 download_complete —— 下载方向的接收方是 Client， 完成消息只能由 Client 发布
  • Client 发布 upload_complete —— 上传方向的接收方是 Server， 完成消息只能由 Server 发布
  • 在同一连接上重复握手（第二个 login）

COMPLETED / VERIFY / COMMIT 状态下的应答义务（规范性）：会话处于 COMPLETED、VERIFY 或 COMMIT 状态时，接收方必须应答 missing_chunks（mode=request），应答内容为空列表的 mode=report （VERIFY / COMMIT 期间位图已全真；见 12 章「校验阶段的活性」）。

若最终回执尚未确认，接收方还必须重发该回执。空缺失列表只说明块已收齐， 不证明提交成功；断线后按 13 章交付原结果。

重要约束

  1. session_id: u64，由 Server 生成（见 09 章）；控制帧、UDP 数据包与 TCP 数据面帧必须使用同一取值域与同一字节序
  2. file_hash: 一律为 32 字节原始 Blake3 摘要；禁止用十六进制串或 u64 承载 （日志与 UI 展示时由实现自行转十六进制）
  3. Client 发送 upload_start / download_start 时 session_id 可为 0， 由 Server 生成并在 accept 中回填
  4. 未识别消息必须忽略，保持幂等性；重复投递不得改变协议语义 （TCP 本身提供可靠有序投递，重复只可能来自实现层重发）
  5. 一条控制连接只承载一个 device_id；连接与设备的绑定在握手时确定，不得在连接存续期间变更
  6. 完成消息由接收方发布：upload_complete 由 Server 发布，download_complete 由 Client 发布
  7. missing_chunks 的两级缺失：chunks 为完全缺失块、partial[] 为部分缺失块的 symbol 掩码， missing_count 为缺失 symbol 精确总数；请求对端缺失列表时用 mode=request
  8. 错误码必须上线路：19 章的错误码通过 session_abort.reason 与完成类消息的 code 字段承载
  9. 数据面端口必须出现在 accept 消息中：upload_accept 与 download_accept 必须携带 udp_port
  10. 控制消息必须幂等：实现可能因超时重发而重复投递控制消息， 重复投递不得改变协议语义
  11. 定长区一旦发布即冻结：新增字段只能追加在扩展区；既有字段的偏移与大小不得变更
  12. 连接级在途上限：同一控制连接上所有会话的数据面在途量之和必须不超过 connection_window（见 11 章）；Client 不得擅自修改该值
  13. 摘要对帐消息：reconcile_request 恒由接收方发布， reconcile_response 恒由发送方发布；每会话的摘要对帐至多一次 （见 12 章「上限」）
  14. 共享清单消息：material_available 与 material_list_ack 恒由 Server 发布，material_list 恒由 Client 发布；清单查询不得创建传输会话 （见 09 章）
  15. 投递消息：delivery_offer 恒由 Server 发布， delivery_response 恒由 Client 发布； Server 在收到接受后必须等到该会话的 PROBE 才可发送数据面数据包 （见 09 章、20 章）
  16. 待决请求唯一：Client 在同一控制连接上同一时刻必须只保留一个待决的 upload_start / download_start；因此 Server 对该请求的拒绝 （以 session_abort 表达，见 19 章 FILE_TOO_LARGE）必须能被 Client 唯一归属
  17. 帧同步三项校验：magic、header_crc32、frame_len 是帧边界可信的充分必要条件； 任一失败即判定失步并必须断连（见「帧同步与失步处理」）。 实现不得在未通过这三项校验的情况下解析帧体
  18. magic 恒定：0x574E414C 不得随版本变更； 协议演进只能通过 proto_version（会话级）与 body_version（消息体级）表达
  19. 首帧锚点：控制连接的首帧必须是 login（见「首帧锚点」）； 不满足必须关闭连接
  20. 失步必须断连：失步不得就地续解，必须按 13 章走断线重连恢复
  21. 窗口推进信用：window_update 恒由接收方发布，携带当前代号的 received_symbols 与 max_ok_payload；missing_chunks 的 missing_count 同样构成信用。发送方以两者中最新的计数推进窗口，二者在同一代号内必须一致 （见 11 章「窗口推进信用」）
  22. C↔C peer 会话：direction = peer 的会话绑定两个 Client （sender_device_id / receiver_device_id），两者各自有一条控制连接； Server 生成 session_id 并仲裁状态。没有 C↔C 的 login。
  23. peer 控制中继：peer 会话的缺失/信用/进度/完成/对帐消息 必须经 Server 在两条控制连接间转发；Server 校验发布方角色，越权按 ACL_DENY。
  24. R1 预选中转：peer_relay_plan 只做关联；实际传输是 upload（C1→S）与 download（S→C2）两段既有会话，参数以标准 accept 为准。
  25. peer 与 transport：transport 支持 direct 与 relay_r2；Server 可以在会话中途 通过 peer_transport_switch 切换（direct ⇄ relay_r2），切换不改变 session_id、 方向或 generation，位图/临时文件保留。

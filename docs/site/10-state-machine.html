10 Session 状态机

本章要点：本章定义传输会话的 8 个状态与合法状态转移，控制面（TCP）负责裁决与同步。 同一个会话在发送侧与接收侧各自持有一份状态视图：接收侧使用全部状态， 发送侧不存在 VERIFY 与 COMMIT。 ABORTED 是终态，没有出边；Server 是会话状态的唯一仲裁者。 状态在控制消息中以 state 字段承载（enum8）。

状态定义

状态编码说明
INIT0初始化状态 - 会话刚创建
NEGOTIATING1协商状态 - 正在协商传输参数
TRANSFERRING2传输状态 - 正在收发数据
PAUSED3暂停状态 - 会话被显式暂停，位图与临时文件保留
VERIFY4验证状态 - 正在做文件级完整性校验
COMMIT5提交状态 - 正在原子提交（重命名）
COMPLETED6完成状态 - 传输成功完成
ABORTED7中止状态 - 传输被终止；终态，无出边
状态的编码表示：状态在控制消息中以 state 字段承载，类型为 enum8（u8）， 取值 0 INIT、1 NEGOTIATING、2 TRANSFERRING、3 PAUSED、 4 VERIFY、5 COMMIT、6 COMPLETED、7 ABORTED（见 06 章「枚举」）。

视角定义（规范性）

同一个会话在发送侧与接收侧各自持有一份状态视图：

视角定义上传方向下载方向
发送侧发送数据的一方ClientServer
接收侧持有位图与临时文件的一方ServerClient
  • 接收侧使用全部状态（INIT / NEGOTIATING / TRANSFERRING / PAUSED / VERIFY / COMMIT / COMPLETED / ABORTED）。
  • 发送侧只使用 INIT / NEGOTIATING / TRANSFERRING / PAUSED / COMPLETED / ABORTED —— 发送侧不持有位图，不存在 VERIFY 与 COMMIT 状态：文件级校验与原子提交 天然发生在接收侧。
  • 「Server 为最终裁决者」指一般终止权（接收方在复核轮后可终止，见 12 章）：进入 ABORTED 的转换通常由 Server 通过 session_abort 发起（发送侧收到 session_abort 后同样转入 ABORTED）。

两个视角的合法路径（对比）

路径发送侧接收侧
常规传输 INIT → NEGOTIATING → TRANSFERRING → COMPLETED INIT → NEGOTIATING → TRANSFERRING → VERIFY → COMMIT → COMPLETED
秒传（file_exists = 1） INIT → NEGOTIATING → COMPLETED INIT → NEGOTIATING → VERIFY → COMMIT → COMPLETED
中止 任意状态 → ABORTED 任意状态 → ABORTED
ABORTED 是终态（规范性）：没有出边，也不存在 ABORTED → ABORTED。 清理动作（删除临时文件 / 位图 / 元数据）在进入 ABORTED 之后执行 （见 09 章「超时与回收」、13 章「失败与清理」）。
每个视角都必须能从 INIT 走到 COMPLETED（规范性）：转移表必须对两个视角 都给出完整路径。接收侧同样需要 NEGOTIATING → TRANSFERRING —— 否则它只能从 NEGOTIATING 直接跳到 VERIFY（秒传路径）， 常规传输的「位图全真 → VERIFY」在接收侧不可达。
两个视角的状态序列不同（规范性）：接收侧经过 VERIFY / COMMIT，发送侧不经过 （发送侧没有位图，无法做文件级校验）。把两侧日志对齐时， 发送侧的 TRANSFERRING → COMPLETED 与接收侧的 TRANSFERRING → VERIFY → COMMIT → COMPLETED 对应同一次完成， 中间的 VERIFY / COMMIT 对发送侧不可见。

终止权

  • Server 是会话状态的唯一仲裁者：会话参数、状态、超时的裁决都由 Server 做出。
  • session_abort 的发布方有两类：
    • Server —— 可因任意原因终止会话（超时、ACL、状态非法、资源不足等）；
    • 接收侧 —— 仅限检测到不可恢复的数据完整性失败 （reason = FILE_HASH_MISMATCH），且必须已在复核轮之后。 这是接收侧唯一有权发起的终止（见 12 章「复核轮」）。
  • 发送侧不得主动发布 session_abort（除非它也是该会话的接收侧）。 发送侧需要终止时，必须发布 session_pause 或等待 Server 的裁决。
  • session_abort 的 reason 以 str 承载 19 章的错误码符号名 （如 FILE_HASH_MISMATCH），不得填写自由文本（见 06 章「session_abort」）。

推进规则

  • 发送侧状态仅由收到的控制面消息推进。UDP 数据包不得改变发送侧状态。
  • 接收侧状态由本地事件推进（位图全真 / Blake3 校验通过 / 原子重命名完成）， 但接收侧每一次推进必须紧接着通过控制通道向发送侧发布一条控制消息：
接收侧推进必须发布的控制消息
位图出现缺失missing_chunks（mode=report），携带缺失 chunk 列表
位图全真 → VERIFY无需单独消息；随后的 upload_complete / download_complete 隐含告知
VERIFY → COMMIT无需单独消息
COMMIT → COMPLETEDupload_complete（上传方向）/ download_complete（下载方向）
missing_chunks 的 mode 为 enum8（0 = report、1 = request）； chunks 为 chunk_list（u32 条数 + u32 chunk_id 数组，升序）， 接收方在 mode=report 时给出的是自己尚未收到的块 （见 06 章「missing_chunks」）。
  • 数据面（UDP）只能更新位图，不得直接触发状态转移。 位图变化是接收侧推进的输入，不是状态转移本身。
  • 状态转换必须符合上述转移规则；任何实现都不得进入表外的状态组合。

秒传路径（file_exists）

当 Server 侧已存在相同 file_hash 的完整文件时：

  • Server 必须在生成 upload_accept 之前完成既有文件的校验： 对已存在的同 file_hash 文件重新计算 Blake3 并与 upload_start.file_hash 比对。
  • 校验通过时，Server 在 upload_accept 中置 file_exists = 1（bool）； 校验不通过时不得置该标志，按常规传输路径下发 file_exists = 0。 （file_exists 是单向发布的消息字段，一旦上线即不可撤回 —— 因此校验必须发生在发布之前。）
  • 发送侧：NEGOTIATING → COMPLETED（不发送任何数据，直接等待完成通知）。
  • 接收侧：NEGOTIATING → VERIFY → COMMIT → COMPLETED → 发布 upload_complete。
秒传路径不产生位图，因此「bitmap 全真」这一完成条件不适用于秒传路径； 它的完成条件是「既有文件校验通过并原子提交」。 这与常规路径的完成条件是同一件事，只是数据来源不同。

暂停与恢复

  • session_pause 使会话进入 PAUSED；位图、临时文件与已传输数据全部保留。
  • PAUSED 状态下双方必须停止发送数据面数据包。
  • 恢复只有一条路径：发送侧发布 resume_session，对端回 resume_ack （含续传起点与数据面端口），双方回到 TRANSFERRING。
  • session_pause 不是切换开关：重复发布是幂等的 （已处于 PAUSED 时不产生状态变化）。
  • session_pause 与 session_abort 的区别：暂停可恢复，中止不可恢复。
  • session_pause 与 resume_session 的区别：session_pause 是显式暂停， resume_session 是异常中断后的恢复。两者的恢复动作相同（回到 TRANSFERRING）。

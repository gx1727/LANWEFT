10 Session 状态机

本章要点：本章定义传输会话的 8 个状态与合法状态转移，控制面（TCP）负责裁决与同步。 同一个会话在发送侧与接收侧各自持有一份状态视图：接收侧使用全部状态， 发送侧不存在 VERIFY 与 COMMIT。 ABORTED 是终态，没有出边；Server 是会话状态的唯一仲裁者。 状态在控制消息中以 state 字段承载（enum8）。

定义传输会话的状态与合法状态转移。控制面（TCP）负责裁决与同步。

状态定义

INIT → NEGOTIATING → TRANSFERRING → VERIFY → COMMIT → COMPLETED
          │              │  ↑                        │
          │              │  └────────────────────────┘
          │              ↓
          │           PAUSED  ←─────────────────────────┘
          ↓
       ABORTED （从任意状态可到达）
状态 说明
INIT 初始化状态 - 会话刚创建
NEGOTIATING 协商状态 - 正在协商传输参数
TRANSFERRING 传输状态 - 正在收发数据
PAUSED 暂停状态 - 会话被显式暂停，位图与临时文件保留
VERIFY 验证状态 - 正在做文件级完整性校验
COMMIT 提交状态 - 正在原子提交（重命名）
COMPLETED 完成状态 - 传输成功完成
ABORTED 中止状态 - 传输被终止；终态，无出边

状态的编码表示：状态在控制消息中以 state 字段承载，类型为 enum8（u8）， 取值 0 INIT、1 NEGOTIATING、2 TRANSFERRING、3 PAUSED、4 VERIFY、 5 COMMIT、6 COMPLETED、7 ABORTED（见 06 章「枚举」）。

视角定义（规范性）

同一个会话在发送侧与接收侧各自持有一份状态视图：

视角 定义 上传方向 下载方向
发送侧 发送数据的一方 Client Server
接收侧 持有位图与临时文件的一方 Server Client
  • 接收侧使用全部状态（INIT / NEGOTIATING / TRANSFERRING / PAUSED / VERIFY / COMMIT / COMPLETED / ABORTED）。
  • 发送侧只使用 INIT / NEGOTIATING / TRANSFERRING / PAUSED / COMPLETED / ABORTED —— 发送侧不持有位图，不存在 VERIFY 与 COMMIT 状态：文件级校验与原子提交 天然发生在接收侧。
  • 终止原因与发布方必须符合本章「终止权」。

合法状态转移

每个状态对每个视角都要有合法转移。下表逐视角列出：

从状态 到状态 视角 触发
INIT NEGOTIATING 发送侧 upload_start / download_start
INIT NEGOTIATING 接收侧 upload_start / download_start（收到传输请求）
INIT NEGOTIATING 发送侧 delivery_offer（发出投递提议，见 09 章）
INIT NEGOTIATING 接收侧 delivery_offer（收到投递提议）
INIT ABORTED 双方 session_abort
NEGOTIATING TRANSFERRING 发送侧 upload_accept / download_accept
NEGOTIATING TRANSFERRING 接收侧 upload_accept / download_accept（发送 accept 后进入常规传输）
NEGOTIATING TRANSFERRING 双方 delivery_response（接受投递，见 09 章）
NEGOTIATING VERIFY 接收侧 秒传：accept 携带 file_exists = 1（bool），跳过数据传输
NEGOTIATING TRANSFERRING 发送侧 秒传：不发送数据，仅等待 upload_complete
NEGOTIATING ABORTED 双方 session_abort
NEGOTIATING ABORTED 发送侧 delivery_response（拒绝投递，见 09 章）
TRANSFERRING VERIFY 接收侧 位图全真，进入文件级校验
TRANSFERRING PAUSED 双方 session_pause
TRANSFERRING COMPLETED 发送侧 持久化成功的 upload_complete / download_complete，回复 complete_ack
TRANSFERRING ABORTED 发送侧 持久化失败的完成回执，回复 complete_ack
TRANSFERRING ABORTED 双方 session_abort
PAUSED TRANSFERRING 双方 Client 发 resume_session；Server 接受并回 resume_ack
PAUSED ABORTED 双方 session_abort
VERIFY COMMIT 接收侧 文件级 Blake3 校验通过
VERIFY TRANSFERRING 接收侧 恢复阶梯：文件级 Blake3 失配 —— 摘要对帐或复核轮（见 12 章）
VERIFY ABORTED 接收侧 session_abort（见下方终止权）
COMMIT COMPLETED 接收侧 原子重命名完成，发布 upload_complete / download_complete
COMMIT ABORTED 双方 session_abort

ABORTED 是终态（规范性）：没有出边，也不存在 ABORTED → ABORTED。 清理动作（删除临时文件 / 位图 / 元数据）在进入 ABORTED 之后执行 （见 09 章「超时与回收」、13 章「失败与清理」）。 传输状态与最终回执分开保存：下载发送侧因超时关闭传输后，仍必须按 13 章 处理迟到的 download_complete。记录提交结果不是从 ABORTED 恢复数据传输。

每个视角都必须能从 INIT 走到 COMPLETED（规范性）：转移表必须对两个视角 都给出完整路径。接收侧同样需要 NEGOTIATING → TRANSFERRING —— 否则它只能从 NEGOTIATING 直接跳到 VERIFY（秒传路径）， 常规传输的「位图全真 → VERIFY」在接收侧不可达。

两个视角的状态序列不同（规范性）：接收侧经过 VERIFY / COMMIT，发送侧不经过 （发送侧没有位图，无法做文件级校验）。把两侧日志对齐时， 发送侧的 TRANSFERRING → COMPLETED 与接收侧的 TRANSFERRING → VERIFY → COMMIT → COMPLETED 对应同一次完成， 中间的 VERIFY / COMMIT 对发送侧不可见。

终止权

  • Server 是会话状态的唯一仲裁者：会话参数、状态、超时的裁决都由 Server 做出。
  • session_abort 的发布方有两类：
  • Server —— 可因任意原因终止会话（超时、ACL、状态非法、资源不足等）；
  • 非 Server 的接收侧仅可使用：FILE_HASH_MISMATCH（复核轮后仍失配）、 SOURCE_FILE_MISMATCH（根区间一致但请求摘要不符）、 TRANSFER_STALLED（停滞升级后仍无缺失块到达，见 12 章）、 FILESYSTEM_ERROR / STORAGE_FULL（读写或提交失败）、 DATABASE_ERROR（会话元数据或位图无法持久化）。本地存储失败必须立即报告，不得触发内容重传。
  • 非 Server 的发送侧仅在源文件读取失败时可以主动发布 session_abort， reason 限于 SOURCE_READ_ERROR / FILESYSTEM_ERROR；其他原因下发送侧不得 主动终止，必须发布 session_pause 或等待 Server 的裁决。
  • session_abort 的 reason 以 str 承载 19 章的错误码符号名 （如 FILE_HASH_MISMATCH），不得填写自由文本（见 06 章「session_abort」）。

推进规则

  • 发送侧状态仅由收到的控制面消息推进。UDP 数据包不得改变发送侧状态。
  • 接收侧状态由本地事件推进（位图全真 / Blake3 校验通过 / 原子重命名完成）， 但接收侧每一次推进必须紧接着通过控制通道向发送侧发布一条控制消息：
接收侧推进 必须发布的控制消息
位图出现缺失 missing_chunks（mode=report），携带缺失 chunk 列表
位图全真 → VERIFY 无需单独消息；随后的 upload_complete / download_complete 隐含告知
VERIFY → TRANSFERRING（摘要对帐） 无需单独消息；随后的 reconcile_request 隐含告知
VERIFY → TRANSFERRING（复核轮） 无需单独消息；随后的 missing_chunks（复核轮标志）隐含告知
VERIFY → COMMIT 无需单独消息
COMMIT → COMPLETED upload_complete（上传方向）/ download_complete（下载方向）

missing_chunks 的 mode 为 enum8（0 = report、1 = request）； chunks 为 chunk_list（u32 条数 + u32 chunk_id 数组，升序）， 接收方在 mode=report 时给出的是自己尚未收到的块 （见 06 章「missing_chunks」）。

  • 恢复阶梯（规范性）：接收侧在 VERIFY 阶段检测到文件级失配时， 必须回到 TRANSFERRING 并进入恢复阶梯（摘要对帐 → 复核轮，见 12 章）； 发送侧无 VERIFY 状态，收到 reconcile_request 时必须应答， 收到带复核轮标志的裁决时必须全量重发。
  • 数据面（UDP）只能更新位图，不得直接触发状态转移。 位图变化是接收侧推进的输入，不是状态转移本身。
  • 状态转换必须符合上述转移规则；任何实现都不得进入表外的状态组合。

秒传路径（file_exists）

秒传仅适用于上传方向（规范性）：秒传的前提是「Server 侧已存在相同 file_hash 的完整文件」，因此只可能发生在上传方向（Client → Server）。 下载方向的 download_accept.file_exists 必须为 0（假，见 06 章）， 不得走秒传路径。

当当前设备有权引用该内容且 Server 已有完整文件时（授权见 09 章「创建规则」）：

  1. Server 必须在生成 upload_accept 之前完成既有文件的校验： 对已存在的同 file_hash 文件重新计算 Blake3 并与 upload_start.file_hash 比对。
  2. 校验通过时，Server 在 upload_accept 中置 file_exists = 1（bool）； 校验不通过时不得置该标志，按常规传输路径下发 file_exists = 0。 （file_exists 是单向发布的消息字段，一旦上线即不可撤回 —— 因此校验必须发生在发布之前。）
  3. 发送侧：NEGOTIATING → TRANSFERRING，仅等待回执，不发送数据；持久化成功回执后才进入 COMPLETED。
  4. 接收侧：NEGOTIATING → VERIFY → COMMIT → COMPLETED → 发布 upload_complete。

秒传路径不产生位图，因此「bitmap 全真」这一完成条件不适用于秒传路径； 它的完成条件是「既有文件校验通过并原子提交」。 这与常规路径的完成条件是同一件事，只是数据来源不同。

暂停与恢复

  • session_pause 使会话进入 PAUSED；位图、临时文件与已传输数据全部保留。
  • PAUSED 状态下双方必须停止发送数据面数据包。
  • 连接存活时恢复只有一条路径：Client 发布 resume_session，Server 回成功的 resume_ack （含续传起点与数据面端口），双方回到 TRANSFERRING（前提是显式暂停已被解除）。
  • session_pause 不是切换开关：重复发布是幂等的 （已处于 PAUSED 时不产生状态变化）。
  • session_pause 与 session_abort 的区别：暂停可恢复，中止不可恢复。
  • session_pause 与 resume_session 的区别：session_pause 是显式暂停， resume_session 用于显式暂停后的恢复；断线时使用 13 章的登录恢复流程。

典型触发消息

消息 视角 状态效果
upload_start / download_start 发送侧 INIT → NEGOTIATING
upload_accept / download_accept 发送侧 NEGOTIATING → TRANSFERRING；秒传只等待完成回执
missing_chunks（mode=report） 接收侧 维持 TRANSFERRING，触发补发
reconcile_request / reconcile_response 接收侧发布请求 / 发送侧发布应答 VERIFY → TRANSFERRING（恢复阶梯：摘要对帐，见 12 章）
session_pause 双方 TRANSFERRING ⇄ PAUSED
resume_session / resume_ack 发送侧 PAUSED → TRANSFERRING（或恢复中断的会话）
complete_ack 数据发送方 确认已持久化接收方的完成回执（持久化成功后）
upload_complete / download_complete 发送侧 TRANSFERRING → COMPLETED
session_abort 双方 任意状态 → ABORTED

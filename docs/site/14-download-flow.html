14 下载流程（Server → Client）

本章要点：下载方向由 Client 主动发起，Server 不得向未知端口推送 UDP；客户端端口由 download_accept.udp_port 与 UDP 探测共同确定。数据面端口的取用顺序是规范性的：Client 必须按 login_ack 快照 > resume_ack > udp_ready > download_accept 的优先级取用最新端口值， 且 不得自行推断。控制面与可靠性机制与上传一致， 完成消息一律由接收方发布。

原则

  • Client 主动发起
  • Server 不向未知端口推送 UDP（客户端端口由 download_accept.udp_port 与 UDP 探测确定）
  • 控制面与可靠性机制与上传一致
  • 会话类型：Upload（C→S）、Download（S→C）

下载控制消息

消息方向用途
download_start Client→Server 请求下载文件
download_accept Server→Client 接受下载请求，下发会话参数与数据面端口
missing_chunks 双向 缺失 chunk 列表报告 / 索要（mode=report / mode=request）
download_complete Client→Server 下载完成（由接收方 Client 发布）

下载流程时序

下载流程时序：Server → Client，6 个阶段
1 会话建立Client → Server → Client
2 UDP 探测Client → Server → Client
3 数据传输Server → Client
4 缺失重传Server ⇄ Client
5 进度上报Client → Server
6 完成与终止Client → Server
1 会话建立：Client 发送 download_start → Server 返回 download_accept（含 session_id（u64）/ chunk_count（u32）/ window（u32）/ connection_window（u32）/ udp_port（u16）/ tcp_port（u16））
2 UDP 探测：Client 发送 UDP_PROBE → Server 返回 UDP_PROBE_ACK → Server 发送 udp_ready； Server 以 PROBE 报文的源地址:端口作为该会话的对端数据面地址
3 数据传输：Server 按 window 连续发送 UDP chunk（批量发送，节奏见 11 章）
4 缺失重传：Server 每 50ms 下发 missing_chunks（mode=report）裁决； Client 收到后按 11 章补发缺失块。收到 Client 的 missing_chunks（mode=request）时， Server 必须在 50ms 内应答
5 进度上报：Client 每 500ms 发布 progress_update（received / total 为 chunk 数，均为 u64），Server 据此估算链路丢包率并驱动 AIMD（见 11 章）
6 完成与终止：Client 检测位图全真 → 校验 hash → 原子重命名 → 发送 download_complete（接收方发布完成消息，见 06 章）
阶段 1 会话建立 阶段 2 UDP 探测 阶段 3 数据传输 阶段 4 缺失重传 阶段 5 进度上报 阶段 6 完成与终止

阶段 2 细节：UDP 探测

  • Client 发送 UDP_PROBE → Server 返回 UDP_PROBE_ACK → Server 发送 udp_ready
  • Server 以 PROBE 报文的源地址:端口作为该会话的对端数据面地址

阶段 4 细节：missing_chunks 载荷

  • mode 为 enum8（0 = report、1 = request）
  • chunks 为 chunk_list（u32 条数 + u32 chunk_id 数组，升序）
  • 恒为「发布方自己尚未收到的块」（见 06 章「missing_chunks」）

阶段 5 细节：进度消息由接收方发布

  • 下载方向的接收方是 Client，只有它知道本端已接收的 chunk 数

数据面端口的优先级（规范性）

Client 必须按以下顺序取用最新的端口值：

优先级来源生效时机
1（最高） login_ack 的 sessions[] 快照记录中的 udp_port 断线重连后的权威快照
2 resume_ack.udp_port 暂停后恢复的应答
3 udp_ready.udp_port 探测完成时（最新的探测结果）
4 download_accept.udp_port 参数协商时（初始值）
  • 四者的 udp_port 均为 u16（见 06 章各消息的定长区布局）
  • 四者不一致时必须取优先级最高者
  • 端口变更必须通过上述消息显式下发，Client 不得自行推断
权威 vs 增量：优先级 1、2 是权威快照（整体替换本地会话状态，见 13 章）， 优先级 3、4 是同一连接内的增量通知。快照到达时必须以其覆盖本地保存的端口， 不得与旧值并存。

与上传对称性

阶段上传（C→S）下载（S→C）
会话建立 upload_start download_start
参数下发 upload_accept download_accept
数据方向 Client→Server Server→Client
完成通知 upload_complete（Server 发布） download_complete（Client 发布）
缺失报告 Server→Client（Server 报告自己缺的块） Client→Server（Client 报告自己缺的块）
缺失索要 Client→Server（mode=request） Server→Client（mode=request）
裁决节奏 接收方（Server）每 50ms 下发 接收方（Client）每 50ms 下发
进度上报 Server→Client（Server 发布 received） Client→Server（Client 发布 received）
恢复提示来源 Server 自有位图（Client 不携带） Client 自有位图（Client 必须携带）
完成消息一律由接收方发布（规范性）：接收方持有位图与临时文件， 只有它能完成「校验 hash → 原子重命名」并判定成败。

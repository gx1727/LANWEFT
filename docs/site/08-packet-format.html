08 UDP 数据包格式规范（Packet Format）

本章要点：数据面数据包为小端序定长头 + 载荷 + CRC32； 头部 16 字节，尾部 4 字节 CRC（覆盖头 + 载荷，不含 CRC 自身）。 CRC 变体固定为 CRC-32/ISO-HDLC（zlib crc32），两端各选一种会导致 所有包校验失败，故本规范不留实现选择空间。 payload_len 受 chunk_size 约束（上限 1400 字节，避免 IP 分片）； 校验失败的包不得写入位图 —— 代价是一个块，与文件大小无关。

数据包结构（小端序 Little-Endian）

端序约定（规范性）：本协议所有多字节整数字段一律采用 小端序（Little-Endian）。 该约定同时适用于控制帧（见 06 章）、TCP 数据面帧（见 07 章）与数据面数据包， 各通道之间不得出现端序分歧。

字段 偏移 大小 类型 说明
session_id 0-7 8 u64 会话唯一标识，由 Server 生成（见 09 章）
chunk_id 8-11 4 u32 逻辑位置（从 0 开始）
payload_len 12-13 2 u16 载荷长度（不含头部与 CRC）
flags 14-15 2 u16 标志位
payload 16.. N bytes 文件数据
crc32 16+N 4 u32 CRC32 校验码（覆盖 header+payload）

头部大小

HEADER_SIZE = 8 + 4 + 2 + 2 = 16 字节
CRC_SIZE    = 4 字节

包长核算：以 chunk_size = 1200 为例，一个数据包的线上长度为 16 + 1200 + 4 = 1220 字节；叠加 IPv4 + UDP 的 28 字节头部为 1248 字节， 小于 1500 字节的以太网 MTU，不会产生 IP 分片。

载荷长度上限

  • payload_len ≤ chunk_size
  • 建议 chunk_size 取 1024–1350 字节，上限 1400 字节，避免 IP 分片
  • 推荐 chunk_size 取 1200 字节
  • 接收端必须校验：payload_len ≤ 1400 且 payload_len ≤ 本会话协商的 chunk_size； 越界即按 INVALID_PACKET 丢弃，不得写入位图
  • 对 FLAG_DATA，先检查 chunk_id < chunk_count，再要求 payload_len == min(chunk_size, size - chunk_id × chunk_size)（按宽整数计算）。 非末块必须满长；空文件没有 DATA 块。UDP 报文总长必须恰为 16 + payload_len + 4。 长度不符按 INVALID_PACKET 丢弃，不写盘、不标位。PROBE / ACK 使用 07 章的独立长度。

CRC32 变体（规范性）

本协议的 crc32 字段使用 CRC-32/ISO-HDLC（又称 CRC-32、zlib crc32）：

参数 取值
宽度 32
多项式 0x04C11DB7（反射形式 0xEDB88320）
初值 0xFFFFFFFF
输入反射 是
输出反射 是
末尾异或 0xFFFFFFFF
校验值 "123456789" → 0xCBF43926

覆盖区间（规范性）：被校验的字节是数据包的 第 0 字节到第 16 + payload_len - 1 字节， 即 16 字节头部 + payload， 不含尾部 4 字节 crc32 字段本身。

为何必须固定变体（说明）：CRC-32/ISO-HDLC 与 CRC-32C（Castagnoli， 多项式 0x1EDC6F41 / 反射 0x82F63B78）互不兼容 —— 两端各选一种会导致 所有包校验失败；而按 12 章「校验失败直接丢弃」的策略， 该故障表现为「传输永远无法完成」，极难定位。 因此本协议显式固定变体，不留实现选择空间。

包级校验与块级补救（规范性）

  • 接收端必须在写盘前校验 crc32；校验失败即丢弃该包， 不得写入位图（见 12 章「包级校验」）。
  • 该包对应的块因此保持「未收到」状态，会在随后的缺失裁决中被精确报告， 发送方只补发该块。 单次校验失败的代价是一个块，与文件大小无关（见 12 章）。

Flags 位定义

位 常量 值 说明
bit0 FLAG_DATA 0x0001 数据包标志
bit1 FLAG_RESEND 0x0002 重传包标志；接收方无需区别处理（重传是幂等的）
bit2 FLAG_LAST_CHUNK 0x0004 最后一个 chunk 标志，置位时该包的 chunk_id = chunk_count - 1；可选，接收方不得依赖它判断完成（完成以位图为准）
bit3 FLAG_PROBE 0x0008 探测包标志；PROBE 与 PROBE_ACK 共用，以 payload_len 区分（8 / 9）
bit4-5 DATA_GENERATION 0x0030 DATA 修复代号：(flags >> 4) & 3，0 初传、1 摘要对帐后的定点修复、2 全量复核；3 非法。非 DATA 帧必须为 0
bit6 FLAG_BIND 0x0040 仅用于 TCP 数据面帧的绑定帧（见 07 章）；UDP 包必须为 0
bit7-15 RESERVED 0x0000 保留位；接收方必须忽略未知标志位

数据包示例

普通数据包:

session_id: 0x0000000000000001
chunk_id:   0x00000010
payload_len: 1024
flags:      0x0001 (FLAG_DATA)
payload:    [1024 bytes data]
crc32:      [4 bytes checksum]

探测包（PROBE）:

session_id: 0x0000000000000001
chunk_id:   0x00000000
payload_len: 8
flags:      0x0008 (FLAG_PROBE)
payload:    [session_id in little-endian, 8 bytes]
crc32:      [4 bytes checksum]

探测包 payload 为 session_id（u64）的 8 字节小端编码。

探测应答包（PROBE_ACK）:

session_id: 0x0000000000000001
chunk_id:   0x00000000
payload_len: 9
flags:      0x0008 (FLAG_PROBE)
payload:    [session_id in little-endian, 8 bytes][status: 0x00]
crc32:      [4 bytes checksum]

PROBE_ACK 的 payload 为 9 字节：8 字节 session_id + 1 字节状态码 （0 = 成功，1 = 失败）。 PROBE 与 PROBE_ACK 共用 flags.bit3，以 payload_len 区分（8 / 9）。

错误处理

任一关键字段不匹配或校验失败均丢弃。校验失败的数据包不得标记位图。

  • payload_len 越界（> 1400 或 > 协商 chunk_size）→ INVALID_PACKET，丢弃
  • 该 chunk_id 已收到（重复包）→ 幂等丢弃，不重复写盘 （CHUNK_ALREADY_RECEIVED，见 19 章）
  • chunk_id 越界（≥ chunk_count）→ INVALID_CHUNK，丢弃
  • session_id 不匹配 → SESSION_ID_MISMATCH，丢弃
  • CRC32 校验失败 → CRC32_INVALID，丢弃

扩展

  • flags 预留位（bit7–15）；接收方必须忽略未知保留位。DATA 代号须与接收方持久化的当前代号相等；不符在写盘和标位前丢弃，见 12 章。
  • 不兼容扩展通过控制通道的协议版本协商：login 携带 proto_version， Server 在 login_ack 中回填选定的版本；Client 不支持该版本时必须关闭连接 （见 06 章）
  • 数据面格式与协议版本绑定（规范性）：数据包格式的任何不兼容变更 必须伴随 proto_major 的提升；Server 不得向仅支持旧 major 的对端 建立使用新格式的数据面会话
  • 版本比较规则（规范性）：版本号在控制面上编码为 三个 u8 （major / minor / patch，见 06 章 login）， 按 major → minor → patch 逐段数值比较。
  • Client 声明其最高支持的版本；Server 应当回填两者都支持的最高版本。
  • Server 回填的版本其 major 必须等于 Client 声明的 major —— major 不同即不兼容，Client 必须关闭连接， 并以 login_ack.code = PROTO_VERSION_UNSUPPORTED 报告。
  • major 相同、minor 或 patch 不同即视为兼容：新增字段一律可选， 接收方必须忽略不认识的字段。
  • 0.x 例外（规范性）：本规范处于 0.x 阶段， minor 变更可能是不兼容的 —— 例如 v0.3.0 相对 v0.2 的控制面即不兼容 （传输层、帧格式、消息集均已改变）。 因此 minor 不同不得作为「可互通」的充分依据； 实现必须以 06 章的消息集为准判断实际兼容性。 版本策略见 26 章。

# 实现映射（非规范性）

> **非规范性（Non-Normative）**：本文件不定义协议，也不构成互操作要求。
> 它只规定「如何把规范章节映射到实现成熟度」，避免把代码里存在的方法误报成产品能力。
> 规范正文与本文冲突时，以 `docs/spec/` 为准（见 25 章）。

## 为什么需要这张表

一个能力从「代码里有」到「产品可用」之间至少有四道门：

```
有消息模型  →  有算法  →  已接入服务  →  已通过端到端测试
```

任何一道门都不能由前一道门代替：

- crate 里存在 `PeerSession::apply_offer()` **不等于** peer 会话已接入服务；
- 有 `missing_chunks` 编解码器 **不等于**接收方真的会裁决；
- 单测里 bitmap 全绿 **不等于**两端真实 socket 能传完一个文件；
- `cargo test` 通过 **不等于**产品能力，除非测试本身覆盖端到端路径。

因此本表**按能力逐行填写**，不得用「协议章节已实现」这种整章结论代替。

## 四层定义（判定口径）

| 层级 | 名称 | 判定证据（必须可复核） | 不能据此宣称 |
|------|------|------------------------|--------------|
| **M** | **有消息模型** | 消息/字段类型、编解码、字段布局与规范一致；有 round-trip / 负例测试 | 不能说明状态机、流控或持久化可用 |
| **A** | **有算法** | 纯逻辑已实现：状态转移、位图、缺失裁决、窗口/信用、K 选择、恢复、加密等；有单元测试或仿真 | 不能说明服务已注册 handler、可被线上消息触发 |
| **S** | **已接入服务** | Server/Client 运行时已注册 handler 或路由；配置/开关可开启；可观测（日志/指标）；真实进程能收到并处理该消息 | 不能说明两端跑通、失败路径正确、可发布 |
| **E** | **已通过端到端测试** | 自动化测试用真实 socket / 进程 / 至少两端（C↔S 或 C1↔S↔C2）；覆盖成功、失败、重连/恢复；CI 可重复 | 仍不能说明性能、规模或全部平台 |

**产品能力口径（建议）**：对外说「支持 X」至少要求该行达到 **E**。
只到 **S** 应表述为「已接入 / 实验性」；只到 **A** 或 **M** 只能表述为「库内已有实现」。
不得把 crate 中存在的方法、类型或测试，直接写成产品能力。

## 证据规则（规范性，针对本表）

1. **逐能力填写**：一行一个可验证能力（如「上传完成回执交付」），不要合并成「13 章已实现」。
2. **每格必须有证据**：`✓` 必须附文件路径 / PR / 测试名；没有证据就填 `—` 或「未评估」。
3. **不得跨层推断**：`M` 有测试不能自动填 `A`；`A` 有测试不能自动填 `S`；`S` 能手工跑不能自动填 `E`。
4. **E2E 必须真实**：使用 mock 的「端到端」只能算 `A` 或 `S`，不能算 `E`。
5. **能力回退要显式**：如果重构后 handler 未注册、E2E 被禁用，应把状态降回实际层，而不是保留历史 `✓`。

## 规范与实施顺序（建议）

1. **先定消息模型**：字段布局、枚举、长度与错误码进入规范；实现只做编解码与 round-trip。
2. **再定算法**：状态机、位图、裁决、窗口、恢复、加密在纯逻辑层可测；
   此阶段可以用仿真脚本（如 `scripts/verify-peer.py`、`scripts/verify-security.py`）。
3. **再接服务**：Server/Client 注册 handler、持久化、配置与观测；能手工跑通。
4. **最后 E2E**：真实两端/三方、成功与失败、断线/恢复、版本与安全等级组合；进 CI。
5. **只有第 4 步完成**，才在 README / 发布说明 / 对外文档中写「支持」。

## 当前结论

- 本仓库是**规范仓库**，不包含 crate、Server 或 Client 实现。
- 因此本文不主张任何能力已实现；上表的「未评估」不是「未实现」，
  而是「本仓库没有证据」。
- 任何实现仓库引用本表时，必须附上对应证据；否则不得把该能力计入产品能力。

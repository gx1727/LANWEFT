## 待决问题的方案选项

### F1 帧长与恢复列表的冲突 —— 已定案：采用选项 ①

数据：`login.resume_count`（u16）× 20 字节 = 1,310,700 B；
`login_ack.sessions_count`（u16）× 42 字节 = 2,752,470 B；
`max_frame_len` = 1 MiB = 1,048,576 B。
1 MiB 实际容得下 52,428 条 `resume` 或 24,966 条快照。

**定案**：新增 `max_sessions_per_connection` = **64**（09 章），
两个计数器**必须** ≤ 64（06、13 章），超限以 `session_abort`
（`reason` = `TOO_MANY_SESSIONS`）拒绝新会话。
64 条快照最大 2,688 字节、64 条恢复列表最大 1,280 字节，**远小于** 1 MiB。

| 选项 | 结论 |
|------|------|
| ① **限制并发会话数** | ✅ **采纳** —— 不改线格式，覆盖现实规模 |
| ② `login_ack` 分批 | 未采纳；留作将来「大集群 / 多租户」形态的预案 |
| ③ 提高 `max_frame_len` | 未采纳；治标，且未给条目数硬上限 |

### F5 / F6 默认值 —— 已定案

- F5：`window` 规范默认值 = **8192**，`connection_window` = **16384**；
- F6：`burst_size` 初值 = **min(256, `window`)**，与 `window` 解耦；
- 代价：单会话在途上限 8192 个 chunk（约 9.4 MB @ 1200 B）——
  该在途量是协议层计数，大部分块接收方已落盘，不等量占用内存。

### F8 `FILE_ID_MISMATCH` —— 已定案：删除

「发错了文件」在协议层**不可判定**：文件标识即内容摘要，
服务端只有 `file_hash`，无法区分「发错文件」与「内容不符」。
`FILE_HASH_MISMATCH`（内容层不符）与 `SOURCE_FILE_MISMATCH`（源文件已变更）
已覆盖全部**可判定**的不符场景，故删除该错误码
（19 章定义与终止类清单、12 章判定点、站点页面同步删除）。

## 走查中确认无误的部分

- **周期口径**：50 ms 裁决 / 1000 ms 索要 / 500 ms 进度 / 10 s 心跳 /
  30 s 连接超时 / 60 s 会话超时 —— 跨 6 章一致；11 与 12 章的
  「保底轮询 / 看门狗」已统一为单一 1000 ms 规则。
- **恢复阶梯**：摘要对帐 → 复核轮 → 中止，每级至多一次，计数随位图持久化，重启后不重新获得机会。
- **秒传的发布顺序**：`file_exists` 是单向字段，因此既有文件校验**必须**发生在 `upload_accept` 之前 —— 规范此处比多数同类协议严谨。
- **主动投递**：先 PROBE 后推送，与 07、20 章一致。
- **对称性**：14 章的上传/下载对照表双向自洽；空列表裁决的强制性表述正确。
- **数据面端口优先级**：快照 > `resume_ack` > `udp_ready` > accept，四者语义不冲突。
- **结构性一致性**：19 项自动检查全绿（帧头常量、字段表布局、状态机覆盖度、错误码闭合、默认值、交叉引用、站点同步）。

## 走查方法

1. 先跑 `python3 scripts/check-spec-consistency.py` 排除结构性矛盾；
2. 按链路手工走查，逐跳核对「谁发、谁收、什么状态、什么错误码」；
3. 对每个跨章引用做**双向**核对（A 章说 X，B 章是否也这么写）；
4. 发现的问题分三类：**已修**（纯条文补充，不改线格式）、
   **待决**（涉及默认值或线格式，需拍板）、**误报**（检查器规则缺陷，顺手修检查器）。

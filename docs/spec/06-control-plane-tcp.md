# 06 控制面（TCP）

控制面是会话状态推进与可靠性裁决的**唯一**通道。

- **传输**：TCP。Client 主动连接 Server，一条控制连接可承载**多个并发会话**。
- **消息格式**：定长帧头 + 二进制消息体（见「帧格式」与「消息体布局」）。
- **连接即上下文**：同一连接内的消息**严格有序**，因此**不存在**陈旧消息问题；
  跨连接的状态由 `login` / `login_ack` 的**权威快照**一次性重建。

## 帧格式（规范性）

控制帧为**小端序**二进制结构，与 08 章的数据包格式采用**同一端序约定**。

```
偏移  大小  字段          说明
0-3   4     magic         u32，协议魔数，固定 0x574E414C（"LANW"）
4-7   4     frame_len     u32，本帧总字节数（含本帧头），见下
8-11  4     header_crc32  u32，帧头校验码，见「帧头校验码」
12    1     msg_type      u8，消息类型编号，见「消息类型编号」
13    1     flags         u8，帧级标志位；bit0-7 全部保留，接收方必须忽略
14    1     body_version  u8，消息体布局版本号；初值为 0
15    1     reserved      u8，保留字节
16..  N     body          消息体，长度 = frame_len − 16
```

- `FRAME_HEADER_SIZE` = **16 字节**（控制帧定长帧头长度）。
- `magic` **必须**为 `0x574E414C`；该常量**不得**随协议版本变更
  （版本差异一律由 `proto_version` / `body_version` 表达，见 08 章「版本比较规则」）。
  按小端序存放时，线路上的**四个字节**为 `4C 41 4E 57`（"LANW"）——
  抓包比对时**必须**按该字节序判断。
- `frame_len` **必须** ≥ **16**（最小帧长即帧头长度）。
- `frame_len` **必须** ≤ **1 MiB**（记为 `max_frame_len`）。
  接收方读到 `frame_len > max_frame_len` 时**必须**丢弃该帧并**关闭连接**
  —— 帧边界已不可信，无法继续解析。
- 接收方**必须**按 `frame_len` **读满**后再解析：
  - **不得**假设一帧一次 `recv` 到达（TCP 是字节流，**必须**处理拆包）；
  - **不得**按换行或任何字节模式切分。
- 发送方**必须**写出完整帧；**不得**依赖多次 `write` 的边界。
- `body_version` 由**消息体布局**的版本决定，与协议版本（`proto_version`）相互独立。
  当前所有消息的 `body_version` **必须**为 `0`。
  接收方遇到**不认识**的 `body_version` 时，**必须**忽略该值，
  按已知定长区尽力解析，并忽略变长区之后的尾部字节（见「扩展区」）。
- **不携带载荷级 CRC32（说明）**：TCP 自身提供字节流校验和与重传，
  控制帧**不**重复**载荷级** CRC32 —— 与 08 章数据面因 UDP 无可靠校验而携带 `crc32` 不同。
  但帧头**必须**携带 `header_crc32`：其目的**不是**完整性校验，而是**帧同步**
  （见「帧头校验码」与「帧同步与失步处理」）。

### 帧头校验码（规范性）

`header_crc32` 使用 **CRC-32/ISO-HDLC**（又称 CRC-32、zlib `crc32`）——
与 08 章的 `crc32` **同一变体**，本协议**不**存在第二个 CRC32 变体。

| 参数 | 取值 |
|------|------|
| 宽度 | 32 |
| 多项式 | 0x04C11DB7（反射形式 0xEDB88320） |
| 初值 | 0xFFFFFFFF |
| 输入反射 | 是 |
| 输出反射 | 是 |
| 末尾异或 | 0xFFFFFFFF |
| 校验值 | `"123456789"` → 0xCBF43926 |

**覆盖区间（规范性）**：被校验的字节是帧头中**除 `header_crc32` 字段自身之外**的
**12 字节**，按下列顺序拼接（**不是**帧内的**单一**连续区间）：

```
magic(4) ‖ frame_len(4) ‖ msg_type(1) ‖ flags(1) ‖ body_version(1) ‖ reserved(1)
```

- 上式对应帧内的**两段连续区间**：字节 `0–7` 与字节 `12–15`；
  实现可直接对这两段拼接后的 12 字节计算 CRC32。
- 发送方**必须**在写出帧头前计算并填入该值。
- 接收方**必须**在解析帧头时校验该值；校验失败即判定**失步**（见下）。

**为何校验帧头而不校验载荷（说明）**：载荷完整性已由 TCP 保证，
帧头校验码解决的是**另一个**问题 —— 确认当前读到的字节**确实是一个帧头**。
实现一旦出现消费偏移（多读 / 少读一个字节），
仅凭 `frame_len ∈ [16, 1 MiB]` 这一弱判据，
存在约 1e-5 ~ 1e-6 的概率把随机字节**当成一帧合法控制消息执行**
（例如伪造的 `session_pause` / `session_abort`）；
加上 `magic`（2⁻³² 误命中）与 `header_crc32` 后，该路径被消除。

### 帧头字节示例（规范性）

下例是一个**完整可复核**的控制帧（`login`，`msg_type` = `0x01`）的线上字节。
本例用于**锁定字节序与校验区间**；实现**必须**与之逐字节一致。

```
线上偏移  00 01 02 03 | 04 05 06 07 | 08 09 10 11 | 12 13 14 15
────────  ───────────  ───────────  ───────────  ───────────
字节      4C 41 4E 57 | 22 00 00 00 | D3 E3 D5 CC | 01 00 00 00
          └─ magic ──┘ └ frame_len ┘ └header_crc32┘ └ msg_type ┘ flags body_ver rsvd
```

| 线上偏移 | 字节 | 字段 | 取值 |
|---------|------|------|------|
| `0x00–0x03` | `4C 41 4E 57` | `magic` | 协议魔数；**位于线上最前 4 字节**；小端序解读的 u32 值为 `0x574E414C` |
| `0x04–0x07` | `22 00 00 00` | `frame_len` | 34 = 16（帧头）+ 18（消息体） |
| `0x08–0x0B` | `D3 E3 D5 CC` | `header_crc32` | 小端序解读的 u32 值为 `0xCCD5E3D3` |
| `0x0C` | `01` | `msg_type` | `0x01` = `login` |
| `0x0D` | `00` | `flags` | 保留位 |
| `0x0E` | `00` | `body_version` | 0 |
| `0x0F` | `00` | `reserved` | 保留字节 |
| `0x10–0x21` | `00 03 00 00 00 00 00 00 06 00 64 65 76 2D 41 31 00 00` | `body` | 18 字节：`login` 定长区 8 字节 ‖ `device_id`（`06 00` + "dev-A1"）‖ `token`（`00 00`，空串） |

**`magic` 的字节序陷阱（规范性）**：

- `magic` 是 **u32**，按**小端序**存放 —— 线上字节为 `4C 41 4E 57`，
  **不是** `57 41 4E 4C`，也**不是** ASCII 字符串 "LANW" 的十六进制串写法 `4C 41 4E 57` 之外的任何形式；
- 换言之：抓包工具按字节显示时应当看到 `4C 41 4E 57`；
  按 u32 解读时应当得到 `0x574E414C`。
- 抓包比对**必须**按**线上字节序** `4C 41 4E 57` 判断，**不得**按 `0x574E414C` 的字节序反推。

**校验步骤（规范性）**：接收方读到 16 字节帧头后**必须**依次执行：

1. 比对线上字节 `4C 41 4E 57`（即 `magic` == `0x574E414C`）；
2. 计算 `crc32(字节[0x8] ‖ 字节[0xC:0x10])` 并与 `header_crc32` 比对
   （本例中被校验的 12 字节为 `4C 41 4E 57 22 00 00 00 01 00 00 00`）；
3. 校验 `frame_len` ∈ `[16, max_frame_len]`；
4. 以上**全部通过**后，才**必须**按 `frame_len` 读满 `frame_len − 16` 字节的帧体。

> **可复核性（说明）**：本例的 `header_crc32` 由 **CRC-32/ISO-HDLC**（zlib `crc32`）
> 对上述 12 字节计算得出，实现**必须**能复核出 `0xCCD5E3D3`。

### 帧同步与失步处理（规范性）

接收方**必须**按下列顺序校验帧头，**任一**不通过即判定**失步**（desync）：

1. `magic` == `0x574E414C`；
2. `header_crc32` 校验通过；
3. `frame_len` ∈ `[16, max_frame_len]`。

**失步的处置（规范性）**：

- 失步**必须**导致：**丢弃**该连接上尚未解析的全部数据、**关闭连接**、
  并以 PROTOCOL 类错误码记录（`MAGIC_MISMATCH` / `HEADER_CRC_INVALID` /
  `FRAME_LEN_INVALID`，见 19 章）。
- 失步后**不得**在本连接上继续解析任何帧，**不得**继续执行协议状态机。
- 受影响会话**必须**按 13 章「断线重连」恢复 —— 重新建立控制连接，
  经 `login` / `login_ack` 的**权威快照**重建状态。
  **不得**在失步的连接上「跳过一帧继续解析」。

**为何失步必须断连而非就地续解（说明）**：
被跳过的帧中**可能**含状态转移消息（`session_pause` / `session_abort` /
`missing_chunks`）。
一方跳过、一方不跳过时，双方对会话状态的认知已经分叉；
此时「看似同步、实则状态不一致」的连接比「已断开的连接」更危险 ——
断开的连接可以由权威快照**无歧义**地重建，分叉的连接不能。

**有界扫描（推荐性，非规范性）**：
实现**可以**在关闭连接前执行一次**有界扫描**以辅助定位失步点
（便于区分「对端不是本协议」与「本端消费偏移」）。
若实现提供该能力，其**扫描范围、候选判据与扫描上限**见下节「接收状态机」；
扫描结果**仅用于诊断与日志**；**不得**用于恢复协议状态机，
**不得**把扫描到的帧当作可信的控制消息执行。

### 接收状态机（规范性）

接收方**必须**以如下状态机驱动帧解析。状态机的**内部实现方式自由**
（同步阻塞读、异步回调、协程、事件循环均可），
但其**可观测行为必须**满足本节的状态转移表与约束。

**状态定义（规范性）**：

| 状态 | 含义 |
|------|------|
| `SYNC` | 帧边界可信；按 `frame_len` 正常解析帧 |
| `RESYNC` | 已判定失步；**仅**用于有界扫描与诊断，**不得**回到 `SYNC` |
| `CLOSED` | 连接已关闭；承载的会话按 13 章处理（终结状态） |

**状态转移表（规范性）**：

| 当前状态 | 事件 | 条件 | 动作 | 下一状态 |
|---------|------|------|------|---------|
| `SYNC` | 读入字节 | 缓冲区字节数 < `FRAME_HEADER_SIZE` | 继续等待；**不得**解析 | `SYNC` |
| `SYNC` | 帧头读满 | `magic` 不匹配 | 记 `MAGIC_MISMATCH`；**必须**关闭连接 | `CLOSED`（实现有界扫描时先转 `RESYNC`） |
| `SYNC` | 帧头读满 | `header_crc32` 不匹配 | 记 `HEADER_CRC_INVALID`；**必须**关闭连接 | `CLOSED`（同上） |
| `SYNC` | 帧头读满 | `frame_len` ∉ `[16, max_frame_len]` | 记 `FRAME_LEN_INVALID`；**必须**关闭连接 | `CLOSED`（同上） |
| `SYNC` | 帧头读满 | 三项校验**全部**通过 | 按 `frame_len` **读满**帧体 | `SYNC` |
| `SYNC` | 帧体就绪 | `msg_type` 未知，或定长区 / 变长区非法 | 丢弃该帧（`SERIALIZATION_ERROR` 或「未识别消息必须忽略」）；连接保持 | `SYNC` |
| `SYNC` | 帧体就绪 | 消息合法 | 交给消息处理器 | `SYNC` |
| `SYNC` | 读帧体失败 | 对端中断 / 超时 | 关闭连接；会话进入 13 章「中断处理」 | `CLOSED` |
| `RESYNC` | 逐字节前移 | 命中满足「候选判据」的偏移 | 记录候选偏移（**仅诊断**）；**必须**关闭连接 | `CLOSED` |
| `RESYNC` | 逐字节前移 | 扫描量超过 `resync_max_scan` | **必须**关闭连接 | `CLOSED` |
| 任意 | 连接关闭 / 超时 / 对端 FIN | — | 关闭连接；会话进入 13 章「中断处理」 | `CLOSED` |

**约束（规范性）**：

- 三项校验（`magic` → `header_crc32` → `frame_len`）**必须**在**解析帧体之前**完成；
  **不得**先解析再校验，**不得**在三项校验通过前读取帧体。
- `RESYNC` **不得**回到 `SYNC`；实现**不得**在 `RESYNC` 状态中执行任何协议消息，
  **不得**把扫描到的帧当作可信的控制消息。
- 校验失败时**不得**采用「跳过 16 字节继续同步」的做法 —— 该做法只会把失步**延后**，
  且丢弃的可能是一整帧合法消息。
- 帧体**必须**按 `frame_len` **一次性读满**后再解析；
  读不满即视为对端中断，**必须**关闭连接。

**候选判据（规范性，用于 `RESYNC` 的有界扫描）**：
候选偏移 `p` **必须**同时满足：

1. `p` 起的 `FRAME_HEADER_SIZE` 字节构成**合法帧头**（三项校验通过）；
2. `p` 起的**第一帧**完整可读（可用字节数 ≥ 该帧 `frame_len`）；
3. 第一帧**之后紧邻**的第二帧的**帧头**也完整可读，且其三项校验通过
   （即「**连续两帧自洽**」）。

不满足第 3 条的候选**不得**采信 —— 消息体中偶然出现的 `magic` 几乎必然后跟非法帧头。

**扫描上限（规范性）**：`resync_max_scan` = **64 KiB**。
实现**可以**取更小值，**不得**取更大值。

**伪代码（说明性）**：

```
常量：MAGIC = 0x574E414C
      HEADER_SIZE = 16
      MAX_FRAME_LEN = 1 MiB
      RESYNC_MAX_SCAN = 64 KiB

SYNC（控制面接收循环）
  loop:
    若 缓冲区字节数 < HEADER_SIZE:
        继续读取（阻塞；超时 → CLOSED）
        continue

    h = 缓冲区[0 : HEADER_SIZE]
    magic, frame_len, crc, msg_type, flags, body_version, reserved = 解析(h)

    若 magic != MAGIC:                              → 失步(MAGIC_MISMATCH)
    若 crc32(h[0:8] ‖ h[12:16]) != crc:             → 失步(HEADER_CRC_INVALID)
    若 frame_len < HEADER_SIZE 或 frame_len > MAX_FRAME_LEN:
                                                      → 失步(FRAME_LEN_INVALID)

    body = 精确读取(frame_len − HEADER_SIZE)   # 读不满 → CLOSED（对端中断）
    交给消息处理器(msg_type, body)             # 非法消息只丢帧，不断连
    消费缓冲区前 frame_len 字节
    continue

失步(code):
    记录错误码 code
    若 实现提供有界扫描:  转 RESYNC          # 仅诊断
    否则:                  关闭连接 → CLOSED

RESYNC（仅诊断，不恢复协议状态机）
  从当前偏移逐字节前移，最多 RESYNC_MAX_SCAN 字节:
    若 候选满足「候选判据」:  记录候选偏移;  break
  关闭连接 → CLOSED
```

> **实现提示（说明性）**：缓冲区**必须**支持「读满一帧再消费」的滑动语义 ——
> 读帧体期间到达的字节**必须**留在缓冲区中供下一帧使用，
> **不得**因一次 `read` 读到多帧而丢弃残余字节。

### 首帧锚点（规范性）

- 一条控制连接上的**第一帧必须**是 `login`（`msg_type` = `0x01`）。
  接收方在收到 `login` 之前**必须**丢弃该连接上的一切消息（见「连接生命周期」）；
  首帧不是 `login` 时**必须**关闭连接（`CONTROL_ERROR`）。
- 该锚点的作用是**在连接建立的第一时间确认帧同步**：
  首帧若连 `magic` 与 `header_crc32` 都过不了，说明本端或对端存在消费偏移，
  继续读只会加深错位。

### 帧级错误处理（规范性）

| 情况 | 处理 |
|------|------|
| `magic` != `0x574E414C` | 判定**失步**，丢弃并**关闭连接**（`MAGIC_MISMATCH`） |
| `header_crc32` 校验失败 | 判定**失步**，丢弃并**关闭连接**（`HEADER_CRC_INVALID`） |
| `frame_len == 0` | 判定**失步**，丢弃并**关闭连接**（`FRAME_LEN_INVALID`；读取指针无法推进） |
| `frame_len > max_frame_len` | 判定**失步**，丢弃并**关闭连接**（`FRAME_LEN_INVALID`；帧边界不可信） |
| `frame_len < 16` | 判定**失步**，丢弃并**关闭连接**（`FRAME_LEN_INVALID`；帧长不足以容纳帧头） |
| `msg_type` 未知 | 按「未识别消息必须忽略」丢弃该帧，**连接保持** |
| 定长区长度不足（`frame_len − 16 < 定长区长度`） | 按 `SERIALIZATION_ERROR` 丢弃该帧，**连接保持** |
| 变长区长度越界（字符串/数组长度超出本帧剩余字节） | 按 `SERIALIZATION_ERROR` 丢弃该帧，**连接保持** |
| 保留字节（`reserved`、记录内 reserved）非 0 | **必须忽略**，**不得**视为错误，**连接保持** |
| 定长区数值违反该消息的取值约束（如 `mode = request` 但 `chunk_count > 0`） | 按 `SERIALIZATION_ERROR` 丢弃该帧，**连接保持** |

> **帧头三项校验全部通过** ⇒ 帧边界可信 ⇒ 其后的错误**只丢帧、不断连** ——
> 单条畸形消息**不得**导致整条连接失效。
> **帧头三项校验任一失败** ⇒ 帧边界不可信 ⇒ 判定失步 ⇒ **必须断连**。

### 扩展区（规范性）

- 定长区与变长区之后若仍有剩余字节，该部分为**扩展区**。
- 接收方**必须**忽略扩展区的全部内容，**不得**因扩展区非空而报错。
- 扩展区是后续版本新增字段的落点：**新增字段只能追加在扩展区**，
  既有字段的偏移与大小**不得**变更。
- 因此**同一 `msg_type` 的定长区一旦发布即冻结**。

### TCP 特有约束（规范性）

- 控制连接**必须**启用 `TCP_NODELAY`（控制消息延迟敏感，禁止 Nagle 合并）。
- 发送方**应当**把多个待发消息合并为一次 `write`（减少系统调用与报文段数）；
  但**不得**为合并而延迟发送超过 **50 ms**（裁决周期，见 11 章）。
- 接收方**必须**为每条连接维持独立的读缓冲与写队列；
  **不得**在写队列阻塞时阻塞读循环（否则会与心跳超时相互放大）。

## 消息体编码约定（规范性）

每条消息体由**定长区**与**变长区**两部分组成：

```
body := 定长区（长度与偏移见各消息表） ‖ 变长区（按各消息规定的顺序排列）
```

### 基本类型

| 类型 | 编码 |
|------|------|
| `u8` / `u16` / `u32` / `u64` | 小端序定长整数 |
| `bool` | `u8`，`0` = 假，`1` = 真；其他取值视为非法 |
| `enum8` | `u8`，取值见「枚举」 |
| `str` | `u16` 长度 + UTF-8 字节（**不含**结尾 NUL）；长度 `0` 表示**无值**（null） |
| `hash32` | **32 字节原始 Blake3 摘要**（非十六进制串） |
| `chunk_list` | `u32` 条数 + 条数 × `u32` `chunk_id`（**必须**升序） |
| `record[]` | `u16` 条数 + 条数 × 定长记录（记录布局见表） |

### 可选字段的表示（规范性）

- **定长可选字段**（`u32` 计数类）：使用**存在标志位**。
  标志位为 `0` 时该字段**必须**取 `0`，且接收方**必须**按「未携带」处理。
- **变长可选字段**（字符串类）：长度 `0` 即表示未携带。
- `hash32` 类可选字段：使用存在标志位；标志位为 `0` 时**不得**出现该字段的 32 字节。

> **为什么不用哨兵值**：早期草案曾用 `0xFFFFFFFF` 表示「未知」。
> 该写法把「值域上界」与「无值」混为一谈，且 `chunk_count` 的理论上界与哨兵接近时会产生歧义。
> 本规范统一改用**存在标志位**。

### 枚举

| 枚举 | 取值 |
|------|------|
| `result` | `0` = fail，`1` = success |
| `direction` | `0` = upload，`1` = download |
| `state` | `0` INIT、`1` NEGOTIATING、`2` TRANSFERRING、`3` PAUSED、`4` VERIFY、`5` COMMIT、`6` COMPLETED、`7` ABORTED（见 10 章） |
| `missing_chunks.mode` | `0` = report，`1` = request |
| `proto_version` | 三个 `u8`：`major` / `minor` / `patch`，按 major → minor → patch 逐段数值比较（见 08 章「版本比较规则」） |

### 记录内联字符串（说明）

`login_ack` 的会话快照记录含一个可变的错误码字符串。
该字符串**内联**在记录的定长部分之后，长度由记录内的 `code_len` 给出，
记录总长 = 定长部分 + `code_len`。**必须**先读定长部分，再读 `code_len` 字节，
然后才是下一条记录。

## 连接生命周期（规范性）

1. Client 主动连接 Server 的控制端口。
2. Client **必须**在连接建立后**立即**发送 `login` 帧。
3. Server **必须**校验 `login`（认证凭据、协议版本、设备身份）；
   校验失败**必须**以 `login_ack`（`result` = fail）回应并**关闭连接**。
4. Server **必须**在收到 `login` 之前**丢弃**该连接上的一切消息。
5. 校验通过后，Server 回 `login_ack`，其中携带被成功恢复会话的**权威快照**。
6. 连接存续期间，双方**必须**按「心跳与超时」维持连接。
7. 任一方关闭连接时，该连接承载的会话进入**中断**处理（见 13 章）。

**握手超时（规范性）**：Server **必须**在连接建立后 **10 秒**内未收到 `login` 时
关闭该连接（防止半开连接占用资源）。
连接建立失败（如对端拒绝、地址不可达）按 `CONNECTION_FAILED` 记录
（见 19 章）；连接被任一方关闭按 `CONNECTION_CLOSED` 记录。

## 认证与身份（规范性）

- 身份在**连接握手**阶段确定，**不得**依赖后续消息自证。
- Server **必须**把每条控制连接**绑定到唯一 `device_id`**；
  该连接上的一切会话**必须**属于该 `device_id`。
- `device_id` **必须**与认证凭据绑定（见 21 章）；
  不一致**必须**以 `CLIENT_ID_INVALID` 拒绝。
- **在线状态由连接存续直接表达**：连接存在即在线。
  Server **必须**维护连接表，并据此回答「某设备是否在线」。

## 会话与连接的关系（规范性）

- 一条控制连接**可以**承载**多个并发会话**；
  消息中的 `session_id` 用于区分会话，因此 `session_id`
  在所有会话类消息中**必须**出现。
- 控制通道**不重放历史帧流**；13 章规定的持久化完成回执可以幂等重发。同一连接内的消息**严格有序**，
  跨连接的状态由 `login` 的**权威快照**一次性重建。
- 数据面与控制面**相互独立**：控制连接承载 N 个会话时，
  数据面端口**可以**被多个会话共用 —— UDP 包头中的 `session_id`
  足以区分（见 08 章）。

## 心跳与超时（规范性）

| 消息 | 方向 | 周期 |
|------|------|------|
| `ping` | 双向 | **10 秒** |
| `pong` | 双向 | 收到 `ping` 后**立即** |

- 任一方**必须**每 **10 秒**发送一次 `ping`；收到 `ping` **必须**立即回 `pong`。
- **30 秒**内未收到该连接的任何消息时，接收方**必须**关闭该连接
  （按 `TIMEOUT_HEARTBEAT` 记录，见 19 章）。
- 连接超时（30s）**必须**早于会话超时（60s，见 09 章）触发：
  **先**断开连接，**再**由会话超时兜底清理。

## 消息类型编号

| 编号 | 消息 | 方向 | 用途 |
|------|------|------|------|
| `0x01` | login | Client→Server | 连接握手、认证与恢复请求 |
| `0x02` | login_ack | Server→Client | 握手结果与权威快照 |
| `0x03` | upload_start | Client→Server | 发起上传 |
| `0x04` | upload_accept | Server→Client | 接受上传，返回会话参数 |
| `0x05` | download_start | Client→Server | 发起下载 |
| `0x06` | download_accept | Server→Client | 接受下载，返回会话参数 |
| `0x07` | missing_chunks | 双向 | 缺失 chunk 列表报告 / 索要；**报告方恒为接收方** |
| `0x08` | resume_session | Client→Server | 恢复会话（显式暂停后的恢复） |
| `0x09` | resume_ack | Server→Client | 恢复确认与权威状态 |
| `0x0A` | progress_update | 双向 | 传输进度更新；**发布方恒为接收方** |
| `0x0B` | udp_ready | Server→Client | UDP 可用性通知 |
| `0x0C` | upload_complete | Server→Client | 上传完成（接收方 Server 上报） |
| `0x0D` | download_complete | Client→Server | 下载完成（接收方 Client 上报） |
| `0x0E` | session_pause | 双向 | 暂停会话 |
| `0x0F` | session_abort | 双向 | 终止会话；**发布方受限**，见下方说明 |
| `0x10` | asset_recall | Client→Server | 请求撤回（删除）已上传的素材记录 |
| `0x11` | asset_recall_complete | Server→Client | 撤回处理结果回执 |
| `0x12` | ping | 双向 | 心跳 |
| `0x13` | pong | 双向 | 心跳应答 |
| `0x14` | reconcile_request | 双向 | 摘要对帐请求（**发布方恒为接收方**） |
| `0x15` | reconcile_response | 双向 | 摘要对帐应答（**发布方恒为发送方**） |
| `0x16` | material_available | Server→Client | 共享清单变更通知（预置素材） |
| `0x17` | material_list | Client→Server | 查询共享清单（预置素材） |
| `0x18` | material_list_ack | Server→Client | 共享清单查询应答 |
| `0x19` | delivery_offer | Server→Client | 主动投递提议（携带全套会话参数） |
| `0x1A` | delivery_response | Client→Server | 投递应答（接受 / 拒绝） |
| `0x1B` | complete_ack | 双向 | 数据发送方确认已持久化接收方的完成回执 |
| `0x00`、`0x1C`–`0xFF` | — | — | **保留**，接收方必须按「未识别消息必须忽略」处理 |

> **方向标注约定**：标记为「双向」的消息，其**发布方由会话方向决定**：
> `missing_chunks`（`mode=report`）与 `progress_update` 由**接收方**发布；
> `session_pause` 双方均可发布；`mode=request` 的 `missing_chunks` 由**发送方**发布。
> 见 10 章「视角定义」。

> **投递消息的发布方（规范性）**：`delivery_offer` 恒由 **Server** 发布，
> `delivery_response` 恒由 **Client** 发布（见 09 章「主动投递」）。
>
> **共享清单消息的发布方（规范性）**：`material_available` 与 `material_list_ack`
> 恒由 **Server** 发布，`material_list` 恒由 **Client** 发布
> （见 09 章「预置素材与共享清单」）。
>
> **摘要对帐消息的发布方（规范性）**：`reconcile_request` 恒由**接收方**发布，
> `reconcile_response` 恒由**发送方**发布。
> 上传方向为 Server → Client；下载方向为 Client → Server（见 12 章）。
>
> **`session_abort` 的发布方（规范性）**：仅 **Server** 与**接收方**有权发布。
> 非 Server 的接收方仅可使用 10 章「终止权」列明的原因；非 Server 的发送方不得发布。
> 详见 10 章「终止权」。

> **断线重连的恢复不走** `resume_session` / `resume_ack`，
> 而是走 `login` 的恢复列表与 `login_ack` 的权威快照（见「连接生命周期」与 13 章）。

## 消息体布局

各消息体的偏移均**相对于消息体首字节**（即帧内偏移 16）。
定长区之外的变长区按表中「变长区顺序」依次排列。

### login（`0x01`）

**定长区（8 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 1 | proto_major | u8 | Client 支持的**最高**协议版本 major |
| 1 | 1 | proto_minor | u8 | 同上 minor |
| 2 | 1 | proto_patch | u8 | 同上 patch |
| 3 | 1 | reserved | u8 | 保留 |
| 4 | 2 | resume_count | u16 | 待恢复会话条目数；**无待恢复会话时为 0**；**必须** ≤ `max_sessions_per_connection`（64，见 09 章） |
| 6 | 2 | reserved | u16 | 保留 |

**变长区（顺序固定）**

1. `device_id`：`str`。设备标识；**必须**与认证凭据绑定的身份一致（见 21、23 章）。
2. `token`：`str`。认证凭据；采用客户端证书时**必须**为空串（长度 0）。
3. `resume[]`：`resume_count` 条记录，每条 **20 字节定长**：

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 4 | next_chunk_id | u32 | 恢复提示（**仅接收方提供**）；`flags.bit0 = 0` 时**必须**为 0 |
| 12 | 4 | missing_count | u32 | 恢复提示（**仅接收方提供**）；`flags.bit1 = 0` 时**必须**为 0 |
| 16 | 1 | flags | u8 | bit0 = `next_chunk_id` 有效，bit1 = `missing_count` 有效；bit2-7 保留 |
| 17 | 3 | reserved | — | 保留 |

**恢复列表的方向规则（规范性）**：续传起点来自**接收方**的位图，
因此**只有接收方才可能提供**它：

| direction | 恢复列表的提供方 | `next_chunk_id` / `missing_count` |
|-----------|-----------------|-----------------------------------|
| `upload` | Client（**发送方**） | **必须**未携带（`flags.bit0` / `flags.bit1` = 0；Server 用自己的位图计算） |
| `download` | Client（**接收方**） | **必须**携带（`flags.bit0` / `flags.bit1` = 1；Server 没有 Client 的位图） |

**幂等（规范性）**：同一连接上重复的 `login` **必须**被 Server 忽略
（一条连接**只**能握手一次）；Client **不得**在同一连接上重复握手。

### login_ack（`0x02`）

**定长区（10 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 1 | result | enum8 | `0` = fail，`1` = success |
| 1 | 1 | reserved | u8 | 保留 |
| 2 | 1 | proto_major | u8 | Server 选定的协议版本 major |
| 3 | 1 | proto_minor | u8 | 同上 minor |
| 4 | 1 | proto_patch | u8 | 同上 patch |
| 5 | 1 | reserved | u8 | 保留 |
| 6 | 2 | sessions_count | u16 | 权威快照条目数；**无待恢复会话时为 0**；**必须** ≤ `max_sessions_per_connection`（64，见 09 章） |
| 8 | 2 | reserved | u16 | 保留 |

**变长区（顺序固定）**

1. `code`：`str`。失败时的机器可判定错误码（取值见 19 章，如 `LOGIN_FAILED` /
   `PROTO_VERSION_UNSUPPORTED` / `CLIENT_ID_INVALID`）；成功时**必须**为空串。
2. `sessions[]`：`sessions_count` 条快照记录，每条 = **42 字节定长** + `code_len` 字节内联字符串。

**快照记录定长区（42 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 1 | result | enum8 | 该会话的恢复结果 |
| 9 | 1 | direction | enum8 | 会话方向 |
| 10 | 1 | state | enum8 | 会话当前状态（见 10 章）；`result` = fail 时**必须**为 ABORTED |
| 11 | 1 | reserved | u8 | 保留 |
| 12 | 4 | chunk_count | u32 | 会话参数 |
| 16 | 4 | chunk_size | u32 | 会话参数 |
| 20 | 4 | window | u32 | 会话参数 |
| 24 | 4 | connection_window | u32 | **连接级**在途上限（见 11 章） |
| 28 | 4 | next_chunk_id | u32 | **续传顺序起点**：**接收方**位图中第一个尚未收到的 `chunk_id` |
| 32 | 4 | missing_count | u32 | **接收方**位图中尚未收到的 chunk 总数（精确值） |
| 36 | 2 | udp_port | u16 | 数据面端口；**可能因会话重建而变化** |
| 38 | 2 | tcp_port | u16 | 数据面 TCP 降级端口；`0` 表示不支持 |
| 40 | 2 | code_len | u16 | 该会话失败时的错误码长度；成功时为 0 |

紧随记录定长区之后是 `code_len` 字节的 ASCII 错误码（见「记录内联字符串」）。

- `result` = fail 时保留请求的 `session_id`、`state = ABORTED` 与实际 `code_len`；无效的参数字段置 0。
- **快照的帧长边界（规范性）**：权威快照**必须**在一帧内下发完毕
  （不引入分页）。由于 `sessions_count` **必须** ≤ `max_sessions_per_connection`
  （64，见 09 章），快照的最大体积为 64 × (42 + `code_len`) 字节，
  **远小于** `max_frame_len`（1 MiB）——
  因此「快照必须一帧内完整」**始终可编码**。
- **权威快照的效力（规范性）**：快照确定会话关联、协商参数和端口；续传字段是接收方持久化位图的摘要，**不得**据此覆盖位图或接收方的本地提交阶段。`state = COMPLETED` 的回执交付见 13 章。
- Client 若不支持 Server 选定的 `proto_version`，**必须**关闭连接（见 08 章版本比较规则）。

### upload_start（`0x03`）

**定长区（28 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 可为 0；由 Server 生成并在 `upload_accept` 中回填 |
| 8 | 8 | size | u64 | 文件大小（字节）；**必须**满足 09 章的「文件大小上限」 |
| 16 | 8 | mtime | u64 | 文件修改时间戳（UTC 秒）；Server 依此记录素材时间属性 |
| 24 | 1 | flags | u8 | bit0 = `session_id` 有效；bit1-7 保留 |
| 25 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `file_hash`：`hash32`。文件内容的 Blake3 摘要。
2. `file_name`：`str`。文件名（UTF-8）。

### upload_accept（`0x04`）

**定长区（32 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | Server 生成的会话 ID |
| 8 | 4 | chunk_count | u32 | 总 chunk 数量 = ceil(size / chunk_size) |
| 12 | 4 | window | u32 | 滑动窗口大小（**在途上限**），由 Server 下发；**Client 不得擅自修改**；**规范默认 8192**（见 11 章） |
| 16 | 4 | connection_window | u32 | **连接级**在途上限；由 Server 下发；**Client 不得擅自修改**；**规范默认 16384**（见 11 章） |
| 20 | 4 | chunk_size | u32 | 协商确定的 chunk 大小 |
| 24 | 2 | udp_port | u16 | 数据面 UDP 端口；Client **必须**以该端口作为数据面目的端口 |
| 26 | 2 | tcp_port | u16 | **数据面** TCP 降级通道端口；**0 表示不支持 TCP 降级**。**不是**控制面端口 |
| 28 | 1 | file_exists | bool | 秒传标志：当前设备有引用权且既有内容校验通过时为 `1`（见 09、10 章） |
| 29 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `file_hash`：`hash32`。回显请求中的文件哈希，Client 据此关联 `session_id` 与文件。

### download_start（`0x05`）

**定长区（28 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 可为 0；由 Server 生成并在 `download_accept` 中回填 |
| 8 | 8 | size | u64 | 文件大小（字节）；**必须**满足 09 章的「文件大小上限」 |
| 16 | 4 | chunk_size | u32 | 期望的 chunk 大小（字节） |
| 20 | 1 | flags | u8 | bit0 = `session_id` 有效；bit1-7 保留 |
| 21 | 7 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `file_hash`：`hash32`。要下载的文件的 Blake3 摘要。
2. `file_name`：`str`。文件名（UTF-8）。

### download_accept（`0x06`）

**定长区（32 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | Server 生成的会话 ID |
| 8 | 4 | chunk_count | u32 | 总 chunk 数量 = ceil(size / chunk_size) |
| 12 | 4 | window | u32 | 滑动窗口大小（**在途上限**），由 Server 下发；**Client 不得擅自修改**；**规范默认 8192**（见 11 章） |
| 16 | 4 | connection_window | u32 | **连接级**在途上限；由 Server 下发；**Client 不得擅自修改**；**规范默认 16384**（见 11 章） |
| 20 | 4 | chunk_size | u32 | 协商确定的 chunk 大小；Client **必须**用它核算 `chunk_count` |
| 24 | 2 | udp_port | u16 | 数据面 UDP 端口；Server 向该端口推送 chunk，Client **必须**以它作为数据面端口 |
| 26 | 2 | tcp_port | u16 | **数据面** TCP 降级通道端口；**0 表示不支持 TCP 降级**。**不是**控制面端口 |
| 28 | 1 | file_exists | bool | 秒传标志；下载方向**必须**为 0（假） |
| 29 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `file_hash`：`hash32`。回显请求中的文件哈希。

**与 `upload_accept` 的字段对称性（规范性）**：`upload_accept` 与 `download_accept` **必须**携带
同构的字段集合 —— `file_hash` / `session_id` / `chunk_count` / `window` /
`connection_window` / `udp_port` / `tcp_port` / `chunk_size` / `file_exists`；
下载方向的 `file_exists` **必须**为 0。
数据面端口与 `chunk_size` **必须**出现在两个 accept 消息中：
缺端口则数据通路无法建立（Server 不得向未知端口发送 UDP，见 20 章），
缺 `chunk_size` 则接收方无法核算 `chunk_count = ceil(size / chunk_size)`。

### missing_chunks（`0x07`）

**定长区（20 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 1 | mode | enum8 | `0` = report，`1` = request |
| 9 | 1 | flags | u8 | bit0 = `missing_count` 有效；bit1 = 启动全量复核；bit2–3 = 修复代号（0/1/2，见 08、12 章）；bit4–7 保留 |
| 10 | 2 | reserved | u16 | 保留 |
| 12 | 4 | missing_count | u32 | 位图中**尚未收到**的 chunk **总数**（精确值）；`flags.bit0 = 0` 时**必须**为 0 |
| 16 | 4 | chunk_count | u32 | 本批 `chunks` 条目数 |

**变长区（顺序固定）**

1. `chunks`：`chunk_list`，条目**必须**按 `chunk_id` 升序；单条**不得超过 4096 条**（见 18 章）。

**`chunks` 的语义（规范性）**：`chunks` 恒为「**发布方自己尚未收到的块**」，
而不是「我已有的块」。

- 上传方向 Server→Client：Server 报告「我还缺这些块」，Client 收到后**重传**这些块。
- 下载方向 Client→Server：Client 报告「我还缺这些块」，Server 收到后**重传**这些块。

两种方向下语义一致：**接收方报告缺失，发送方补发**。

| mode | 语义 | chunks | 收到方的处理 |
|------|------|--------|--------------|
| `report` | **发布方**报告自己尚未收到的 chunk | 非空或空列表 | 按 `chunks` 重传这些块；条数为 0 **且未置复核轮标志**时表示「我这边没有缺失，可继续推进」；置复核轮标志时空列表表示「全部块」（见下） |
| `request` | 发送方索要对端的缺失列表 | **必须**为空列表 | 对端**必须**在 50ms 内以 `mode=report` 的 `missing_chunks` 应答 |

**按会话方向展开**（`direction` 见 09 章）：

| direction | `mode=report` 的发布方 | `chunks` 的含义 | 收到方的处理 |
|-----------|------------------------|-----------------|--------------|
| `upload` | **Server**（接收方） | Server 尚未收到的块 | Client 重传这些块 |
| `download` | **Client**（接收方） | Client 尚未收到的块 | Server 重传这些块 |

发送方（上传方向 Client / 下载方向 Server）**不得**发布 `mode=report`。
发送方要了解对端的缺失情况，**必须**使用 `mode=request` 索要。

**`missing_count` 的取值（规范性）**：`missing_count` **必须**是位图中**尚未收到**的
chunk **精确总数**（**不是**本批 `chunks` 的长度）。发送方据此推算对端已收数与在途量
（见 11 章），因此该值**不得**是估计值或近似值。`mode=request` 时**必须**为 0。

**复核轮标志 `flags.bit1`（规范性）**：`flags.bit1` = 1 表示本条裁决是**复核轮**
的启动裁决（见 12 章「复核轮」）。每条 report 都携带当前代号；
bit1 置位时必须为代号 2。其后同轮普通裁决只带代号、不再置 bit1。
request 不声明代号（bit2–3 必须为 0）。恢复时先同步代号的规则见 13 章。

- 该标志**仅**在 `mode = report` 时有意义；`mode = request` 时**必须**为 0。
- 复核轮中，接收方**必须**已清空位图，**必须**要求发送方**全量重发**：
  - `chunks` **必须**为空列表（含义为「全部块」，而非「没有缺失」）；
  - `missing_count` **必须**等于该会话的 `chunk_count`（`flags.bit0` **必须**为 1）。
- 发送方收到该标志时**必须**按 12 章「复核轮」执行：
  重新打开源文件、从 `chunk_id` = 0 起全量重发，并重置顺序流与在途量基线。
- 发送方**必须**对同一会话**最多响应一次**复核轮
  （接收方的发起次数上限见 12 章「上限」；该上限按会话计，**不随连接重建而重置**）。

**裁决即推进（规范性）**：接收方**必须**周期性下发 `mode=report` 的 `missing_chunks`
（含空列表），发送方据此推进窗口。详见 11 章「窗口推进判据」。

> **为什么需要 `request`**：上传方向的发送方（Client）无法自行表达「我还缺什么」——
> 它并不缺任何块。`request` 是它向接收方（Server）索要缺失裁决的唯一途径，
> 也是 11 章兜底索要机制与 12 章看门狗的载体。

**空列表的两种含义（规范性）**：`chunks` 为空列表时，其含义由**复核轮标志**区分：

| 复核轮标志 | 含义 | 发送方动作 |
|-----------|------|-----------|
| `flags.bit1` = 0 | 本会话**没有缺失块** | 继续推进新数据 |
| `flags.bit1` = 1 | **复核轮**：全部块都需要重发 | 按 12 章「复核轮」全量重读重发 |

**立即裁决（推荐性）**：接收方**可以**在**检测到空洞的那一刻**立即下发 `mode=report`，
不必等待 50ms 周期，以降低丢包恢复时延。
该优化**不改变**协议语义 —— 周期下发（空列表亦须下发）仍为**规范性**要求。

### resume_session（`0x08`）

**定长区（20 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 4 | next_chunk_id | u32 | 恢复提示（**仅接收方提供**）；`flags.bit0 = 0` 时**必须**为 0 |
| 12 | 4 | missing_count | u32 | 恢复提示（**仅接收方提供**）；`flags.bit1 = 0` 时**必须**为 0 |
| 16 | 1 | flags | u8 | bit0 = `next_chunk_id` 有效，bit1 = `missing_count` 有效；bit2-7 保留 |
| 17 | 3 | reserved | — | 保留 |

**恢复提示的方向规则（规范性）**：`resume_session` **恒由 Client 发起**。
Client 是会话对端，Server 不主动发起恢复。

| direction | Client 的身份 | 恢复提示 |
|-----------|---------------|---------|
| `upload` | **发送方** | `next_chunk_id` 与 `missing_count` **必须**未携带（Server 用自己的位图计算） |
| `download` | **接收方** | `next_chunk_id` 与 `missing_count` **必须**携带（Server 没有 Client 的位图） |

> `resume_session` 用于**显式暂停后的恢复**（同一连接内）；
> 断线重连的恢复走 `login` 的恢复列表（见 13 章）。

### resume_ack（`0x09`）

**定长区（28 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 1 | result | enum8 | `0` = fail，`1` = success |
| 9 | 3 | reserved | — | 保留 |
| 12 | 4 | next_chunk_id | u32 | **续传顺序起点**：**接收方**位图中**第一个尚未收到的 chunk_id**；位图已全真时为 `chunk_count` |
| 16 | 4 | missing_count | u32 | **接收方**位图中尚未收到的 chunk 总数（精确值） |
| 20 | 2 | udp_port | u16 | 数据面 UDP 端口；会话重建后端口可能变化，**Client 必须使用回执中的端口** |
| 22 | 2 | tcp_port | u16 | 数据面 TCP 降级端口；`0` 表示不支持 |
| 24 | 4 | connection_window | u32 | **连接级**在途上限；由 Server 下发（见 11 章） |

**变长区（顺序固定）**

1. `code`：`str`。失败时的机器可判定错误码（见 19 章）；成功时**必须**为空串。
   取值包括 `SESSION_NOT_FOUND`、`SESSION_ABORTED`、`INVALID_STATE`。

**`next_chunk_id` 的定义（规范性）**：**接收方**位图中**第一个尚未收到**的 `chunk_id`。

本协议显式支持乱序写与随机访问，位图可能出现「空洞」——即存在低于最大已收 id 的缺失块。
若以 `max_received_id + 1` 作为续传起点，**空洞块将永远不会被重传**，
文件级 Blake3 校验必然失配。因此续传起点**必须**是**第一个缺失块**。
空洞块的精确集合以周期下发的 `missing_chunks`（`mode=report`）为准，
两者互补：前者决定顺序发送流从哪里继续，后者决定哪些块需要补发。

### progress_update（`0x0A`）

**定长区（24 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 8 | received | u64 | 已接收的 chunk **数量**（不是字节数） |
| 16 | 8 | total | u64 | 本会话的 `chunk_count` |

**发布方（规范性）**：`progress_update` 由**接收方**发布 ——
上传方向是 Server，下载方向是 Client。
原因：`received` 表达的是**本端已接收**的 chunk 数，只有持有位图的接收方才知道该值；
发送方需要它来估算链路丢包率并驱动 AIMD（见 11 章）。

- 周期：接收方约每 **500ms** 发布一次。

`progress_update` 与 `missing_chunks` 是**两种不同的周期消息**，不得混淆：

| 消息 | 周期 | 作用 | 方向 |
|------|------|------|------|
| `missing_chunks`（`mode=report`） | **50ms** | 缺失裁决，驱动窗口推进 | 接收方 → 发送方 |
| `progress_update` | 500ms | 进度统计，供 AIMD 估算丢包率 | 接收方 → 发送方 |

### udp_ready（`0x0B`）

**定长区（12 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 2 | udp_port | u16 | 本次 PROBE 确认的 Server 端口，必须匹配当前待探测的端口；不得以就绪消息改写端口（见 14 章） |
| 10 | 2 | reserved | u16 | 保留 |

### upload_complete（`0x0C`）

**定长区（12 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 1 | result | enum8 | `0` = fail，`1` = success |
| 9 | 1 | flags | u8 | bit0 = `file_hash` 有效；bit1-7 保留 |
| 10 | 2 | reserved | u16 | 保留 |

**变长区（顺序固定）**

1. `code`：`str`。失败时的错误码（见 19 章）；成功时**必须**为空串。
2. `file_hash`：`hash32`，**仅当** `flags.bit0 = 1` 时存在。
3. `asset_id`：`str`。Server 为本次素材分配的记录 ID，用于后续 `asset_recall`；

### download_complete（`0x0D`）

**定长区（12 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 1 | result | enum8 | `0` = fail，`1` = success |
| 9 | 1 | flags | u8 | bit0 = `file_hash` 有效；bit1-7 保留 |
| 10 | 2 | reserved | u16 | 保留 |

**变长区（顺序固定）**

1. `code`：`str`。失败时的错误码（见 19 章）；成功时**必须**为空串。
2. `file_hash`：`hash32`，**仅当** `flags.bit0 = 1` 时存在。

**完成消息由接收方发布（规范性）**：

- 上传方向接收方是 Server → Server 发布 `upload_complete`；
- 下载方向接收方是 Client → Client 发布 `download_complete`。

原因：只有接收方持有位图与临时文件，能完成「校验 hash → 原子重命名」，
也只有接收方能判定完成与否。发送方通过收到该消息得知会话已提交。

### complete_ack（`0x1B`）

**定长区（8 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 已持久化最终结果的会话 |

无变长区。上传由 Client 应答 `upload_complete`，下载由 Server 应答
`download_complete`。只确认结果已记录，不表示传输成功；重发与清理规则见 13 章。

### session_pause（`0x0E`）

**定长区（8 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |

**语义（规范性）**：暂停会话，双方停止发送数据面数据包，
会话转入 `PAUSED` 状态；位图与临时文件全部保留。

- **无独立 ack**：`session_pause` 本身即状态转移消息，
  对端转入 `PAUSED` 后**必须**停止发送数据面数据包；
  恢复见 10 章「暂停与恢复」。
- **不表示「切换」**：重复发布是幂等的（已处于 `PAUSED` 时不再产生状态变化）。
  恢复一律通过 `resume_session` / `resume_ack` 表达。
- 与 `session_abort` 的区别：暂停**可恢复**，中止**不可恢复**。
- 与 `resume_session` 的区别：`session_pause` 是**显式暂停**，
  `resume_session` 是**暂停后的恢复**；两者的恢复动作相同。

### session_abort（`0x0F`）

**定长区（12 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 2 | reserved | u16 | 保留 |
| 10 | 2 | reserved | u16 | 保留 |

**变长区（顺序固定）**

1. `reason`：`str`。机器可判定的错误码，取值见 19 章（如 `FILE_HASH_MISMATCH`）；
   **不得**填写自由文本。**必须**非空。
2. `detail`：`str`。可读补充说明，仅用于日志与 UI，不得被用于逻辑判断；无则为空串。

**错误码上线路（规范性）**：19 章定义的错误码**必须**通过本消息的 `reason` 字段上线路。
发送方与接收方**必须**按错误码做分支判断，不得解析自由文本。

`result` 字段（`success` / `fail`）用于「完成类」消息；
`code` 字段（19 章错误码）用于「结果可能成功也可能失败」的消息；
`reason` 字段（19 章错误码）用于「终止类」消息。
三者语义不重叠，实现**不得**混用。

### asset_recall（`0x10`）

**定长区（4 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 1 | flags | u8 | bit0 = `asset_id` 有效；bit1-7 保留 |
| 1 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `file_hash`：`hash32`。要撤回的素材的 Blake3 摘要。
2. `asset_id`：`str`，**仅当** `flags.bit0 = 1` 时存在；
   素材记录 ID，为空时按 `file_hash` 定位。

资产撤回请求：Client 请求 Server 删除已接收的素材记录。
本消息不关联 session，可独立于传输会话使用。

**`asset_id` 语义**：Server 为每条已接收素材分配的**记录标识**，
由 Server 分配并在 `asset_recall_complete` 中回填
（新建素材时经 `upload_complete.asset_id` 交付）。
Client 可用 `file_hash` 单独定位，也可用 `asset_id` 精确定位到某一条记录。

**撤回语义**：删除的是 Server 侧的**素材记录**（索引条目及其引用），
不删除已被其他会话引用的物理文件；物理文件的回收策略由实现决定。

**幂等**：对同一 `file_hash` / `asset_id` 重复撤回**必须**是幂等的 ——
第二次撤回若记录已不存在，应回 `deleted = false` 且 `code` 为空串
（视作「已处于目标状态」），**不得**报错。

**权限**：Server **必须**校验发起方的 `device_id` 对该素材记录的所有权，
越权时回 `code = ACL_DENY`（见 19 章）。

### asset_recall_complete（`0x11`）

**定长区（4 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 1 | flags | u8 | bit0 = `asset_id` 有效，bit1 = `code` 有效，bit2 = `detail` 有效；bit3-7 保留 |
| 1 | 1 | deleted | bool | 是否已删除素材记录 |
| 2 | 2 | reserved | u16 | 保留 |

**变长区（顺序固定）**

1. `file_hash`：`hash32`。被撤回素材的 Blake3 摘要。
2. `asset_id`：`str`，**仅当** `flags.bit0 = 1` 时存在；未建立记录时为空串。
3. `code`：`str`，**仅当** `flags.bit1 = 1` 时存在；未删除时的机器可判定错误码
   （见 19 章）；成功删除时**必须**为空串。
4. `detail`：`str`，**仅当** `flags.bit2 = 1` 时存在；可读补充说明，仅用于日志与 UI。

资产撤回完成通知：Server 处理撤回后的回执。
`deleted` 表达成功与否，`code` 表达失败原因，**不再重复提供语义重叠的 `result` 字段**。

### reconcile_request（`0x14`）

**定长区（16 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 4 | range_count | u32 | 本次请求比较的区间数；**必须** ≤ 64（见 12 章「上限」） |
| 12 | 1 | flags | u8 | bit0 = **根轮**（本次携带的是覆盖整个文件的根区间）；bit1-7 保留 |
| 13 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `ranges[]`：`range_count` 条记录，每条 **8 字节定长**：

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 4 | first_chunk | u32 | 区间起始 `chunk_id`（含） |
| 4 | 4 | chunk_count | u32 | 区间包含的 chunk 数 |

- 区间**必须**按 `first_chunk` **升序**排列。
- 区间的字节范围与摘要定义见 12 章「对帐区间」。
- **发布方恒为接收方**（见「消息与方向」）。

### reconcile_response（`0x15`）

**定长区（16 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 会话 ID |
| 8 | 4 | range_count | u32 | 本应答覆盖的区间数；**必须**等于对应请求的 `range_count` |
| 12 | 1 | flags | u8 | bit0 = **源文件已变更**；bit1 = **请求超限**（拒绝执行）；bit2-7 保留 |
| 13 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `digests[]`：`range_count` 条记录，每条 **40 字节定长**：

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 4 | first_chunk | u32 | 与请求中对应区间一致 |
| 4 | 4 | chunk_count | u32 | 与请求中对应区间一致 |
| 8 | 32 | digest | hash32 | 该区间字节在**发送方侧**的 BLAKE3 摘要 |

- `flags.bit0`（源文件已变更）置位时，`digests[]` **必须**为空列表，
  `range_count` **必须**为 0。
- `flags.bit1`（请求超限）置位时同样**不**返回摘要。
- **发布方恒为发送方**（见「消息与方向」）。

### 素材条目记录（共享清单用）

共享清单的每个条目由**定长区 + 变长区**组成，
在 `material_available` 与 `material_list_ack` 中**共用**同一格式。

**条目定长区（32 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | seq | u64 | 单调递增序号；Client 的增量水位与分页游标 |
| 8 | 8 | size | u64 | 文件大小（字节） |
| 16 | 8 | mtime | u64 | 文件修改时间戳（UTC 秒） |
| 24 | 2 | name_len | u16 | `file_name` 字节数（UTF-8，不含 NUL） |
| 26 | 2 | asset_id_len | u16 | `asset_id` 字节数（UTF-8，不含 NUL） |
| 28 | 4 | reserved | — | 保留 |

紧随定长区之后依次是：`file_hash`（`hash32`，32 字节）、
`file_name`（`name_len` 字节）、`asset_id`（`asset_id_len` 字节）。

- `seq` **必须**在 Server 侧**全局单调递增**且**不复用**（见 09 章）。
- `asset_id` 长度**必须**为 0 或大于 0（空串表示无素材记录标识）。

### material_available（`0x16`）

**定长区（8 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 4 | count | u32 | 本条消息携带的条目数 |
| 4 | 1 | flags | u8 | bit0 = **末条**（本次通知的条目到此为止）；bit1-7 保留 |
| 5 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `entries[]`：`count` 条素材条目记录（格式见「素材条目记录」）。

- **发布方恒为 Server**。
- 本消息是**至少一次**的提示，**不保证送达**；Client **不得**仅凭通知
  维护完整清单，**必须**另行查询 `material_list`（见 09 章「发现」）。

### material_list（`0x17`）

**定长区（16 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | since_seq | u64 | `0` = 全量；否则只要 `seq > since_seq` 的条目 |
| 8 | 4 | max_count | u32 | 本次期望的条目数上限；`0` = 规范默认 256 |
| 12 | 4 | reserved | — | 保留 |

- **发布方恒为 Client**。
- 本消息**不得**创建任何传输会话（见 09 章「发现」）。

### material_list_ack（`0x18`）

**定长区（16 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | max_seq | u64 | Server 侧当前的最大 `seq` |
| 8 | 4 | count | u32 | 本批条目数 |
| 12 | 1 | flags | u8 | bit0 = **末批**（没有更多条目了）；bit1-7 保留 |
| 13 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `entries[]`：`count` 条素材条目记录（格式见「素材条目记录」）。

- **发布方恒为 Server**。
- **分页（规范性）**：若 `flags.bit0` = 0，Client **必须**以本批**最后一个**条目的
  `seq` 作为 `since_seq` 再次查询，直到 `flags.bit0` = 1。
- **增量（规范性）**：Client **可以**用已知的最大 `seq` 作为 `since_seq`，
  只取新增条目；Server **必须**只返回 `seq > since_seq` 的条目。
- **水位的取法（规范性）**：Client **必须**以**最后收到的条目**的 `seq`
  作为下一次查询的 `since_seq`；**不得**使用本应答的 `max_seq`
  —— `max_seq` 可能超前于本批已返回的条目，用它作水位会**跳过**条目。

### delivery_offer（`0x19`）

**定长区（48 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | Server 分配的会话 ID（见 09 章「创建规则」） |
| 8 | 8 | size | u64 | 文件大小（字节） |
| 16 | 8 | mtime | u64 | 文件修改时间戳（UTC 秒） |
| 24 | 4 | chunk_count | u32 | 总 chunk 数量 = ceil(size / chunk_size) |
| 28 | 4 | window | u32 | 滑动窗口大小（**会话级在途上限**），见 11 章 |
| 32 | 4 | connection_window | u32 | **连接级**在途上限，见 11 章 |
| 36 | 4 | chunk_size | u32 | 协商确定的 chunk 大小 |
| 40 | 2 | udp_port | u16 | 数据面 UDP 端口；Client **必须**向它发出 PROBE |
| 42 | 2 | tcp_port | u16 | **数据面** TCP 降级通道端口；`0` 表示不支持。**不是**控制面端口 |
| 44 | 1 | flags | u8 | bit0-7 保留（接收方**必须**忽略未知位） |
| 45 | 3 | reserved | — | 保留 |

**变长区（顺序固定）**

1. `file_hash`：`hash32`。待投递文件内容的 Blake3 摘要。
2. `file_name`：`str`。文件名（UTF-8）。

- **发布方恒为 Server**。
- 本消息**携带全套会话参数**：Client 接受后**必须**按这些参数工作，
  **不得**自行改动 `window` / `connection_window` / `chunk_size`。
- Client **必须**校验 `chunk_count == ceil(size / chunk_size)`，
  不一致即以 `delivery_response`（`result` = fail，`code` = `SERIALIZATION_ERROR`）
  拒绝。
- 本消息**不携带**任何认证凭据 —— 投递只**可能**发生在已认证的控制连接上。

### delivery_response（`0x1A`）

**定长区（12 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | session_id | u64 | 对应 `delivery_offer` 的会话 ID |
| 8 | 1 | result | enum8 | `0` = fail（拒绝）、`1` = success（接受） |
| 9 | 1 | flags | u8 | bit0 = `file_hash` 有效；bit1-7 保留 |
| 10 | 2 | reserved | u16 | 保留 |

**变长区（顺序固定）**

1. `code`：`str`。`result` = fail 时的机器可判定错误码（见 19 章，如
   `DELIVERY_DECLINED` / `STORAGE_FULL` / `ACL_DENY` / `SERIALIZATION_ERROR`）；
   `result` = success 时**必须**为空串。
2. `file_hash`：`hash32`，**仅当** `flags.bit0` = 1 时存在。
   接受时**必须**携带，且**必须**与 `delivery_offer.file_hash` 一致。

- **发布方恒为 Client**。
- `result` = success 时，Client **必须**打开数据面 socket 并发出 PROBE
  （见 09 章「流程」、07 章「接收方 socket 生命周期」）。
- `result` = fail 时，Client **不得**发出 PROBE。

### ping（`0x12`）/ pong（`0x13`）

**定长区（8 字节）**

| 偏移 | 大小 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 8 | ts | u64 | 发送方的单调时钟毫秒值；**仅用于**日志与 RTT 统计，**不得**用于协议判断 |

## 非法行为

- 在同一条连接上使用**另一个** `device_id` 的会话
- Server 发布 `download_complete` —— 下载方向的接收方是 Client，
  完成消息只能由 Client 发布
- Client 发布 `upload_complete` —— 上传方向的接收方是 Server，
  完成消息只能由 Server 发布
- 在同一连接上重复握手（第二个 `login`）

**COMPLETED 状态下的应答义务（规范性）**：会话处于 COMPLETED 状态时，
接收方**必须**应答 `missing_chunks`（`mode=request`），
应答内容为**空列表**的 `mode=report`。

若最终回执尚未确认，接收方还必须重发该回执。空缺失列表只说明块已收齐，
**不证明提交成功**；断线后按 13 章交付原结果。

## 重要约束

1. **session_id**: **u64**，由 Server 生成（见 09 章）；控制帧、UDP 数据包与
   TCP 数据面帧**必须**使用同一取值域与同一字节序
2. **file_hash**: 一律为 **32 字节原始 Blake3 摘要**；**禁止**用十六进制串或 u64 承载
   （日志与 UI 展示时由实现自行转十六进制）
3. **Client 发送 upload_start / download_start 时 session_id 可为 0**，
   由 Server 生成并在 accept 中回填
4. **未识别消息必须忽略，保持幂等性**；重复投递**不得**改变协议语义
   （TCP 本身提供可靠有序投递，重复只可能来自实现层重发）
5. **一条控制连接只承载一个 `device_id`**；连接与设备的绑定在握手时确定，**不得**在连接存续期间变更
6. **完成消息由接收方发布**：`upload_complete` 由 Server 发布，`download_complete` 由 Client 发布
7. **`missing_chunks.chunks` 恒为「发布方自己尚未收到的块」**；请求对端缺失列表时用 `mode=request`
8. **错误码必须上线路**：19 章的错误码通过 `session_abort.reason` 与完成类消息的 `code` 字段承载
9. **数据面端口必须出现在 accept 消息中**：`upload_accept` 与 `download_accept` **必须**携带 `udp_port`
10. **控制消息必须幂等**：实现可能因超时重发而重复投递控制消息，
    重复投递**不得**改变协议语义
11. **定长区一旦发布即冻结**：新增字段只能追加在扩展区；既有字段的偏移与大小不得变更
12. **连接级在途上限**：同一控制连接上所有会话的数据面在途量之和**必须**不超过
    `connection_window`（见 11 章）；Client **不得**擅自修改该值
13. **摘要对帐消息**：`reconcile_request` 恒由**接收方**发布，
    `reconcile_response` 恒由**发送方**发布；每会话的摘要对帐**至多一次**
    （见 12 章「上限」）
14. **共享清单消息**：`material_available` 与 `material_list_ack` 恒由 **Server**
    发布，`material_list` 恒由 **Client** 发布；清单查询**不得**创建传输会话
    （见 09 章）
15. **投递消息**：`delivery_offer` 恒由 **Server** 发布，
    `delivery_response` 恒由 **Client** 发布；
    Server 在收到接受后**必须**等到该会话的 PROBE 才可发送数据面数据包
    （见 09 章、20 章）
16. **待决请求唯一**：Client 在同一控制连接上同一时刻**必须**只保留一个待决的
    `upload_start` / `download_start`；因此 Server 对该请求的拒绝
    （以 `session_abort` 表达，见 19 章 `FILE_TOO_LARGE`）**必须**能被 Client 唯一归属
17. **帧同步三项校验**：`magic`、`header_crc32`、`frame_len` 是帧边界可信的**充分必要条件**；
    任一失败即判定失步并**必须断连**（见「帧同步与失步处理」）。
    实现**不得**在未通过这三项校验的情况下解析帧体
18. **`magic` 恒定**：`0x574E414C` **不得**随版本变更；
    协议演进**只能**通过 `proto_version`（会话级）与 `body_version`（消息体级）表达
19. **首帧锚点**：控制连接的首帧**必须**是 `login`（见「首帧锚点」）；
    不满足**必须**关闭连接
20. **失步必须断连**：失步**不得**就地续解，**必须**按 13 章走断线重连恢复

## 与状态机关系

- 映射以 10-state-machine 为准
- 状态转换必须符合合法状态转移规则

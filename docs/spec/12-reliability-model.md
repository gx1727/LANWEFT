# 12 可靠性模型（Reliability）

## 分层保障

- 控制面统计缺失并下发 `missing_chunks`（`mode=report`）；接收端乱序写盘与位图
- crc32 包级完整性；**`chunk_digest` 逐块端到端完整性**（见 08 章）；
  文件级内容 hash 校验（Blake3）
- 重传：UDP 不即时重传；聚合缺失后统一下发；重传优先级高于新数据
- 中断与恢复：不回滚已写入；恢复后加载位图并补传缺失
- 完成与提交：bitmap 全真 → 校验 hash → 原子重命名 → 发布完成消息

**裁决是唯一的推进依据（规范性）**：接收方**必须**至少每 50ms 下发一次 `missing_chunks`
（`mode=report`），**包括缺失列表为空的情况**；发送方据此推进窗口。
详见 11 章「窗口推进判据」。

`missing_chunks` 的 `mode` 为 `enum8`（`0` = report、`1` = request）；
`chunks` 为 `chunk_list`（`u32` 条数 + `u32` `chunk_id` 数组，**升序**），
「缺失列表为空」即 `chunk_list` 的条数为 `0`；`missing_count` 为位图中
**尚未收到**的 chunk **精确总数**（`u32`），**不是**本批 `chunks` 的长度。
见 06 章「missing_chunks」。

## 保底轮询（Keep-Alive Polling）

- Client 发送完全部数据后，若 Server 持续返回 `missing_chunks`（`mode=report`）
  且 `chunks` 为空、**未置复核轮标志**（即「没有缺失」而非「全部重发」），
  但**始终未下发** `upload_complete`，Client 进入保底轮询状态。
- 保底轮询**使用** 11 章判据第 4 条的**同一个 1000 ms 索要规则**：
  Client **必须**按该周期发布 `missing_chunks`（`mode=request`）
  持续索要缺失列表，直至收到 `upload_complete` 或触发超时。
- 目的：防止对端状态机卡死导致的会话悬挂。

## 连接断开的语义（规范性）

控制连接断开时，该连接承载的**全部**会话**必须**视为**中断**（可恢复），
**不得**直接置为 ABORTED：

- 断连**不**回滚已写入的数据，位图与临时文件**必须**保留。
- Client 重连后通过 `login` 的恢复列表恢复（见 13 章）。
- 只有会话活动超时（60 秒，见 09 章）才把会话置为 ABORTED 并清理资源。

## 看门狗（Watchdog）

看门狗的职责与 11 章判据第 4 条的索要规则**完全一致**：
发送方每 **1000 ms** 至少索要一次裁决，直到收到 `mode=report` 为止。
重复的 `mode=request` 是幂等的，与幂等要求兼容
（见 06 章「未识别消息必须忽略，保持幂等性」）。

## 完整性校验

### 包级

- 每个 UDP 数据包尾部携带 CRC32，校验失败直接丢弃，**不得**写入位图。
  该块随即保持「未收到」状态，由缺失裁决**定点补发**该块 ——
  单次校验失败的代价是**一个块**，不是整个文件（见「缺失块的定点补发」）。
- 会话协商启用逐块摘要时，每个 `FLAG_DATA` 包（以及 TCP 数据面的 `FLAG_DATA` 帧）
  携带 `chunk_digest`（8 字节 BLAKE3，见 08 章）；校验失败直接丢弃，**不得**写入位图。
- **摘要关闭时**：载荷的完整性由**包级 CRC32** 单独承担
  （此时 CRC32 的覆盖区间扩大到「头 + payload」，见 08 章）。
- TCP 数据面帧**不**携带 CRC32 —— TCP 已提供字节流校验（见 07 章）。

### 缺失块的定点补发（规范性）

`crc32` 与 `chunk_digest` 检出的都是「内容与发送方发出时不一致」，
但两者覆盖的对象与层次不同（见 08 章「`crc32` 与 `chunk_digest` 的分工」）：
`crc32` 覆盖**整个包**、只证明**这一跳**的比特未变，只能判定「这个包不可信」；
`chunk_digest` 只覆盖**块载荷**、是**端到端**校验，且**可定位到块**。

因此：

- 接收方**必须**在**写盘前**校验 `chunk_digest`（若本包携带）；
  失配即按 `CHUNK_DIGEST_MISMATCH` 丢弃该包，**不得**写入位图。
  摘要未启用时，块级损坏由 `crc32` 失配发现，处置路径**完全相同**。
- 该块随即成为位图中的「未收到」，接收方**必须**通过**常规缺失裁决**
  （`missing_chunks`，`mode=report`）请求该块；
  发送方**必须**按 11 章的「重传优先级高于新数据」补发它。
- 该路径**不**触发复核轮（见下）：单块损坏的修复代价是**一个块**，
  而不是整个文件。
- **写盘之后**才发生的损坏（磁盘写入错误）**不在**包级校验的覆盖范围内 ——
  包级校验在写盘前即已完成，**无法**发现这类错误。
  它们只能由**文件级**校验捕获，并按**复核轮**处理。
  接收方**可以**在写盘后回读该块并重新校验摘要以提前发现
  （推荐性，见 17 章「写盘后回读校验」）。

### 文件级

- 传输完成后，接收方计算全文件 Blake3 哈希，与请求中的 `file_hash` 比对
  （`file_hash` 为 **32 字节原始 Blake3 摘要**，`hash32` 类型，非十六进制串）；
  一致才进入 COMMIT 并发布完成消息（上传方向 `upload_complete`，
  下载方向 `download_complete`）
- **文件级校验失败**：`FILE_HASH_MISMATCH` **必须**进入**复核轮**，
  **不得**直接终止会话（见下）。

### 复核轮（Re-verify Round）

文件级失配意味着「收到的字节整体不等于源文件」。由于逐块摘要已确认
**每一个收到的块都与发送方发出的字节一致**，失配只可能来自
**发送侧读出了错误的内容**（例如源文件所在扇区读取异常）。

因此修复手段只有一条：**重新读取源文件并全量重发**。

**接收方（规范性）**：

1. 接收方**必须**进入复核轮，**不得**立即发布 `session_abort`。
2. 接收方**必须**清空位图（全部块置为「未收到」），临时文件**保留**
   （复核轮将覆盖写入相同偏移）。
3. 接收方**必须**发布 `missing_chunks`（`mode=report`）并置**复核轮标志**
   （`flags.bit1` = 1）；该条裁决的 `chunks` **必须**为空列表，
   `missing_count` **必须**等于 `chunk_count`（见 06 章）。
4. 接收方**必须**记录复核轮计数，并**必须**将其与位图一同**持久化**
   （见 09 章「持久化」），使进程重启后不得重复使用复核轮。
5. 复核轮结束后，接收方**必须**重新计算文件级 Blake3 并再次比对。

**发送方（规范性）**：

1. 收到带复核轮标志的裁决时，发送方**必须**按 11 章判据第 3 条
   「复核轮」条目重置顺序流与在途量基线。
2. 发送方**必须**重新打开源文件并**重新读取**内容 ——
   **不得**复用先前已读入内存或页缓存的旧副本；
   发送方**应当**绕过操作系统页缓存重新读取（实现建议）。
3. 发送方**必须**从 `chunk_id` = 0 起全量重发，并**必须**为每一块
   重新计算 `chunk_digest`。
4. 发送方**必须**对同一会话**最多响应一次**复核轮。

**终止条件（规范性）**：

- 复核轮结束后文件级校验**仍**失配 → 接收方**必须**发布
  `session_abort`（`reason` = `FILE_HASH_MISMATCH`）终止会话。
  此时源文件确实不可读或已被改动，已无可恢复的手段。
- 复核轮**至多一次**：接收方**不得**对同一会话发起第二次复核轮。

> **为何不立即终止（说明）**：包级 CRC32 只有 32 位，其未检出概率随文件增大而线性上升
> （100 GiB 文件约 2.1%，1 TiB 文件约 20.8%，见 08 章「摘要的代价与适用边界」）。
> 会话协商启用逐块摘要时，该概率降至 2⁻⁶⁴ 量级，复核轮成为极少见的兜底路径。
> 若文件级失配一律立即终止，一个刚传完的百 GB 文件会因一次未被检出的
> 位翻转而被丢弃；复核轮把它降级为「一次重传」而非「全部重来」。
> 复核轮**至多一次**的约束保证了最坏情况下的代价上界是**两次**传输，
> 而不是无限重试。

### 秒传路径

- 跳过数据传输时没有位图，完成条件为「既有文件校验通过并原子提交」
  （见 10 章「秒传路径」）。

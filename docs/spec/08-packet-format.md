# 08 UDP 数据包格式规范（Packet Format）

## 数据包结构（小端序 Little-Endian）

**端序约定（规范性）**：本协议所有多字节整数字段一律采用 **小端序（Little-Endian）**。
该约定**同时适用于控制帧**（见 06 章）、**TCP 数据面帧**（见 07 章）与数据面数据包，
各通道之间**不得**出现端序分歧。

| 字段 | 偏移 | 大小 | 类型 | 说明 |
|------|------|------|------|------|
| session_id | 0-7 | 8 | u64 | 会话唯一标识，由 Server 生成（见 09 章） |
| chunk_id | 8-11 | 4 | u32 | 逻辑位置（从 0 开始） |
| payload_len | 12-13 | 2 | u16 | 载荷长度（不含头部与 CRC） |
| flags | 14-15 | 2 | u16 | 标志位 |
| payload | 16.. | N | bytes | 文件数据 |
| chunk_digest | 16+N | 8 | bytes | 逐块摘要（**可选字段**：仅当本会话协商了逐块摘要且本包为 `FLAG_DATA` 时携带，见下） |
| crc32 | 24+N | 4 | u32 | CRC32 校验码（**覆盖区间取决于本包是否携带 `chunk_digest`**，见「CRC32 覆盖区间」） |

## 头部大小

```
HEADER_SIZE = 8 + 4 + 2 + 2 = 16 字节
DIGEST_SIZE = 8 字节（可选字段）
CRC_SIZE    = 4 字节
```

**包长核算**（`chunk_size = 1200`）：

| 会话协商 | 数据包线上长度 | 叠加 IPv4 + UDP（28 字节） |
|----------|----------------|--------------------------|
| 逐块摘要**启用** | `16 + 1200 + 8 + 4 = 1228` 字节 | 1256 字节 |
| 逐块摘要**关闭** | `16 + 1200 + 4 = 1220` 字节 | 1248 字节 |

两者均**小于** 1500 字节的以太网 MTU，**不会**产生 IP 分片。

## 载荷长度上限

- `payload_len ≤ chunk_size`
- 建议 `chunk_size` 取 1024–1350 字节，**上限 1400 字节**，避免 IP 分片
- 推荐 `chunk_size` 取 **1200** 字节
- **接收端必须校验**：`payload_len ≤ 1400` 且 `payload_len ≤ 本会话协商的 chunk_size`；
  越界即按 `INVALID_PACKET` 丢弃，**不得**写入位图
- 最后一个 chunk 的 `payload_len` **必须**等于 `size - chunk_id × chunk_size`；
  不等即按 `INVALID_PACKET` 丢弃

## 逐块摘要 `chunk_digest`（可选字段，规范性）

`chunk_digest` 是**每个数据块**的端到端摘要，长度固定 **8 字节**。

- **是否启用由会话协商决定**（见 09 章「逐块摘要的协商」）：
  `chunk_digest` = `1`（启用）时，`FLAG_DATA` 包**必须**携带它（`flags.bit5` = 1）；
  `chunk_digest` = `0`（关闭）时，`FLAG_DATA` 包**不得**携带它（`flags.bit5` = 0）。
- `PROBE` / `PROBE_ACK` **一律不携带**摘要（`flags.bit5` 必须为 0），
  无论会话是否协商启用。
- 算法：**BLAKE3**，输出长度 **8 字节**（XOF 模式）。
- 覆盖区间（规范性）：**仅覆盖该 chunk 的 `payload` 字节**，
  **不**覆盖包头、**不**覆盖 `crc32`。
- **发送方必须**对**实际发出的字节**计算摘要 —— 即摘要与 payload 必须取自同一次读取。
- **接收方必须**独立计算摘要并与包内携带值比对：
  - 一致 → 按正常路径写盘并标记位图；
  - **不一致** → 按 `CHUNK_DIGEST_MISMATCH` **丢弃该包**，**不得**写入位图，
    并按**常规缺失路径**请求该块（见 12 章「缺失块的定点补发」）。
- **校验顺序（规范性）**：接收方**必须**先校验 `crc32`，再校验 `chunk_digest`，
  最后才写盘并标记位图。
  `crc32` 只需覆盖 24 字节即可先行判定包头（含 `chunk_id`）是否可信，
  从而避免对无效包做 1200 字节的摘要计算。

### 摘要的代价与适用边界（说明）

**代价**：每块一次 BLAKE3（1200 字节约 1.2–1.6 µs）。
以 1 Gbps（约 10.4 万块/秒）计，单端约占 **17% 单核**；10 Gbps 时超过一个核。
该开销在 1 Gbps 局域网内**被 I/O 掩盖**，但在高速链路或弱 CPU 设备上会显现。
（带宽开销另计：每块 8 字节，约 0.67%。）

**收益**：把包级 CRC32 的未检出概率从 2⁻³² 降到 2⁻⁶⁴。
CRC32 只有 32 位，其**未检出**的损坏概率约为 2⁻³²，随块数线性增长：

| 文件大小 | 块数（1200 B） | 至少一处未检出的概率 |
|----------|---------------|----------------------|
| 1 GiB | 8.9×10⁵ | ≈ 0.02% |
| 10 GiB | 8.9×10⁶ | ≈ 0.21% |
| 100 GiB | 8.9×10⁷ | ≈ **2.1%** |
| 1 TiB | 8.9×10⁸ | ≈ **20.8%** |

未检出的损坏会一路存活到**文件级**校验，从而触发**复核轮**（整文件重传，见 12 章）。
以 100 GiB、1 Gbps 为例：期望额外带宽约 **2.1%**（≈ 2.2 GiB），
折合约 **18 秒**额外传输；而摘要的 CPU 代价约 **143 CPU-秒/端** ——
**仅从「省带宽」角度看，摘要是净亏损（约 8 倍）**。

**因此摘要的实际价值在另一处**：摘要绑定的是**块内容**，
因此可以在写盘后**回读该块**重新校验（见 17 章「写盘后回读校验」），
把磁盘写入错误就地退回「未收到」，而不必等文件级校验才发现、
代价是整文件重传。这一项是摘要的**主要价值**，但它**依赖接收方实际做回读**。

**结论与适用边界**：

- 摘要**默认启用**（`chunk_digest` = 1），因为它使回读校验成为可能，
  并把「2.1% 概率走整文件重传」压到可忽略；
- Server **可以**关闭它（`chunk_digest` = 0），条件是：
  文件较小或一次性传输、双方存储可靠性已知、且**不启用**回读校验；
- 关闭摘要时，**载荷**的完整性由 `crc32` 单独承担
  （见「CRC32 覆盖区间」），协议行为仍然正确，
  只是未检出概率回到 2⁻³² 量级。

> `chunk_digest` 提供的是**端到端完整性**，**不是**身份认证：
> 任何能发包的主机都能构造出摘要自洽的包（见 20 章）。

## `crc32` 与 `chunk_digest` 的分工（说明）

两者都用于检测「收到的字节与发出的字节不一致」，但**不是同一功能**：

| 维度 | `crc32` | `chunk_digest` |
|------|----------|---------------|
| 覆盖对象 | **整个包**：16 字节头 + payload + 摘要本身 | **仅块载荷**（不含包头、不含 `crc32`） |
| 校验层次 | **逐跳**：只在收到时验证一次，此后**不可重验** | **端到端**：可对**已落盘的内容**随时重新验证（回读校验，见 17 章） |
| 强度 | 32 位，随机损坏的漏检概率约 2⁻³² / 包 | 64 位 BLAKE3，漏检概率约 2⁻⁶⁴ / 块 |
| 包头保护 | **覆盖**包头（`session_id` / `chunk_id` / `flags` 的完整性） | **不覆盖**包头 |
| 校验失败后的修复 | 丢弃该包 → 该块仍为「未收到」→ 裁决后**定点补发该块** | 同左 |

**两者的修复粒度相同（都是「一个块」），差别在于覆盖范围、强度与可重验性**。
因此二者**不可互相替代**，与文件级 Blake3 共同构成分层保障：

- **只有 `crc32`**：漏检率随文件增大线性上升（100 GiB 约 2.1%）。
  漏检的损坏会一路存活到**文件级**校验，从而触发**复核轮**（整文件重传，见 12 章）——
  这才是 `crc32` 单独使用的真实代价。
- **只有 `chunk_digest`**：**包头不受保护** —— 被篡改的 `session_id` /
  `chunk_id` / `flags` 摘要照样自洽，而这些字段决定的是
  「写到哪个偏移」「属于哪个会话」，属于**协议语义**而非文件内容。
- **只有文件级 Blake3**：能发现失配，但**无法定位**，
  修复代价是整个文件重传。

### 为什么单次校验失败不等于整文件重传（说明）

本协议**不采用逐包 ACK**，而采用「**位图 + 缺失裁决**」。
任何一次校验失败（`crc32` 或 `chunk_digest`）都只是让**对应的那一个块**
保持「未收到」状态；该块会在下一次裁决（≤ 50 ms）中被精确报告，
发送方按缺失列表**只补发该块**。

因此单次校验失败的代价是**一个块的重传**，与文件大小无关。
包头被损坏导致该包的 `chunk_id` 不可信时，归属由位图裁决自动恢复：
真正丢失的块本来就未被标记，裁决必然把它报出来。

只有**文件级**校验失配才需要整个文件重传（**复核轮**，见 12 章）。

> 二者都**不提供**身份认证：任何能发包的主机都能构造出 CRC 与摘要自洽的包
> （见 20 章）。

## CRC32 变体（规范性）

本协议的 `crc32` 字段使用 **CRC-32/ISO-HDLC**（又称 CRC-32、zlib `crc32`）：

| 参数 | 取值 |
|------|------|
| 宽度 | 32 |
| 多项式 | 0x04C11DB7（反射形式 0xEDB88320） |
| 初值 | 0xFFFFFFFF |
| 输入反射 | 是 |
| 输出反射 | 是 |
| 末尾异或 | 0xFFFFFFFF |
| 校验值 | `"123456789"` → 0xCBF43926 |

**覆盖区间（规范性）**：覆盖区间**取决于本包是否携带 `chunk_digest`**：

| 本包 | CRC32 覆盖的字节 | 长度 |
|------|-------------------|------|
| 携带 `chunk_digest`（`flags.bit5` = 1） | **16 字节头部 + 8 字节摘要**（第 0..23 字节） | 24 字节 |
| 不携带 `chunk_digest`（`flags.bit5` = 0） | **16 字节头部 + payload**（第 0..15+N 字节） | 16+N 字节 |

两种情形都**不含**尾部 4 字节 `crc32` 字段本身。

> **为何载荷不重复计算（说明）**：携带摘要时，**载荷的完整性已由 `chunk_digest` 保护**
> （64 位 BLAKE3），CRC32 只需保护**包头**与**摘要本身**。
> 若 CRC32 仍覆盖载荷，同一段字节会被哈希两次 —— 实测在 1200 字节块上
> 这是约 **20%** 的无谓 CPU 开销。改为「头 + 摘要」后，
> **包头由 CRC32 保护、载荷由摘要保护**，覆盖没有缺口。

发送方**必须**按本包的实际构成计算 CRC32；接收方**必须**按同一规则验证，
两者必须一致 —— 该规则由 `flags.bit5` 唯一确定，不依赖会话参数。

**为何必须固定变体（说明）**：CRC-32/ISO-HDLC 与 CRC-32C（Castagnoli，
多项式 0x1EDC6F41 / 反射 0x82F63B78）**互不兼容** —— 两端各选一种会导致
**所有包校验失败**；而按 12 章「校验失败直接丢弃」的策略，
该故障表现为「传输永远无法完成」，极难定位。
因此本协议显式固定变体，不留实现选择空间。

## Flags 位定义

| 位 | 常量 | 值 | 说明 |
|----|------|-----|------|
| bit0 | FLAG_DATA | 0x0001 | 数据包标志；置位时**必须**携带 `chunk_digest` |
| bit1 | FLAG_RESEND | 0x0002 | 重传包标志；接收方**无需**区别处理（重传是幂等的） |
| bit2 | FLAG_LAST_CHUNK | 0x0004 | 最后一个 chunk 标志，置位时该包的 `chunk_id` = `chunk_count - 1`；**可选**，接收方**不得**依赖它判断完成（完成以位图为准） |
| bit3 | FLAG_PROBE | 0x0008 | 探测包标志；PROBE 与 PROBE_ACK 共用，以 `payload_len` 区分（8 / 9） |
| bit4 | — | 0x0010 | 保留；**必须**为 0 |
| bit5 | FLAG_CHUNK_DIGEST | 0x0020 | 逐块摘要标志；**当且仅当**本会话协商了逐块摘要（`chunk_digest` = 1）且本包为 `FLAG_DATA` 时置位 |
| bit6 | FLAG_BIND | 0x0040 | **仅用于 TCP 数据面帧**的绑定帧（见 07 章）；UDP 包**必须**为 0 |
| bit7-15 | RESERVED | 0x0000 | 保留位；接收方**必须**忽略未知标志位 |

## 数据包示例

**普通数据包**:
```
session_id: 0x0000000000000001
chunk_id:   0x00000010
payload_len: 1024
flags:      0x0021 (FLAG_DATA | FLAG_CHUNK_DIGEST)
payload:    [1024 bytes data]
chunk_digest: [8 bytes BLAKE3(payload)]
crc32:      [4 bytes checksum]
```

**探测包（PROBE）**:
```
session_id: 0x0000000000000001
chunk_id:   0x00000000
payload_len: 8
flags:      0x0008 (FLAG_PROBE)
payload:    [session_id in little-endian, 8 bytes]
crc32:      [4 bytes checksum]
```

> 探测包 payload 为 `session_id`（u64）的 **8 字节小端编码**。

**探测应答包（PROBE_ACK）**:
```
session_id: 0x0000000000000001
chunk_id:   0x00000000
payload_len: 9
flags:      0x0008 (FLAG_PROBE)
payload:    [session_id in little-endian, 8 bytes][status: 0x00]
crc32:      [4 bytes checksum]
```

PROBE_ACK 的 payload 为 9 字节：8 字节 session_id + 1 字节状态码
（0 = 成功，1 = 失败）。
**PROBE 与 PROBE_ACK 共用 `flags.bit3`，以 `payload_len` 区分**（8 / 9）。

## 错误处理

任一关键字段不匹配或校验失败均丢弃。校验失败的数据包**不得**标记位图。

- `payload_len` 越界（> 1400 或 > 协商 chunk_size）→ `INVALID_PACKET`，丢弃
- `chunk_id` 越界（≥ chunk_count）→ `INVALID_CHUNK`，丢弃
- `session_id` 不匹配 → `SESSION_ID_MISMATCH`，丢弃
- CRC32 校验失败 → `CRC32_INVALID`，丢弃
- `chunk_digest` 校验失败（仅在携带摘要的包上可能发生）→
  `CHUNK_DIGEST_MISMATCH`，丢弃，并按常规缺失路径请求该块

## 扩展

- flags 预留位（bit4、bit7–15）；接收方**必须**忽略未知标志位
- 不兼容扩展通过控制通道的协议版本协商：`login` 携带 `proto_version`，
  Server 在 `login_ack` 中回填选定的版本；Client 不支持该版本时**必须**关闭连接
  （见 06 章）
- **数据面格式与协议版本绑定（规范性）**：数据包格式的任何不兼容变更
  **必须**伴随 `proto_major` 的提升；Server **不得**向仅支持旧 major 的对端
  建立使用新格式的数据面会话
- **版本比较规则（规范性）**：版本号在控制面上编码为 **三个 `u8`**
  （`major` / `minor` / `patch`，见 06 章 `login`），
  按 major → minor → patch 逐段**数值**比较。
  - Client 声明其**最高**支持的版本；Server **应当**回填两者都支持的**最高**版本。
  - Server 回填的版本其 major **必须**等于 Client 声明的 major
    —— **major 不同即不兼容**，Client **必须**关闭连接，
    并以 `login_ack.code` = `PROTO_VERSION_UNSUPPORTED` 报告。
  - major 相同、minor 或 patch 不同即视为兼容：新增字段一律可选，
    接收方**必须**忽略不认识的字段。
  - **0.x 例外（规范性）**：本规范处于 `0.x` 阶段，
    `minor` 变更**可能**是不兼容的 —— 例如 v0.3.0 相对 v0.2 的控制面即**不兼容**
    （传输层、帧格式、消息集均已改变）。
    因此 `minor` 不同**不得**作为「可互通」的充分依据；
    实现**必须**以 06 章的消息集为准判断实际兼容性。
    版本策略见 26 章。

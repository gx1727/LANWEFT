# 26 下一阶段与路线图（Roadmap）

> **非规范性（Non-Normative）**：本章记录尚未冻结的议题与后续版本方向，
> **不构成互操作要求**（见 25 章）。规范正文与本章冲突时，以规范正文为准。

## 版本策略（规范性）

- 版本号形如 `major.minor.patch`，当前为 **`v0.3.0`**。
- **版本号只在上游明确指示时变更**。
  未获明确指示时，规范的任何修订（措辞澄清、勘误、章节增补）
  **不得**变更版本号 —— 修订**必须**记入本章的「修订记录」。
- 每次修订**必须**在本章留下记录：改了什么、涉及哪些章节。
- **设计阶段的含义**：本规范当前**未冻结任何实现**，
  线路格式与消息集仍在演进；版本号在此阶段**不承载兼容承诺**，
  「某版本号是否可互通」在本阶段**没有意义**——
  判断标准只有一条：**以 06、07、08 章正文为准**。
  冻结首个实现之后，版本号才回到「标识兼容边界」的职责。
- **0.x 阶段的兼容性**：本规范处于 `0.x` 阶段，`minor` 变更**可能**是不兼容的
  （例如 v0.3.0 的控制面与早期草案即**不兼容**）。
  因此 08 章「版本比较规则」中「major 相同即视为兼容」的结论
  **必须**结合本章与 06 章的消息集共同判断，
  **不得**仅凭 `minor` 不同就假定可互通。

> 换言之：版本号是**标识**当前规范状态，不是**自动递增**的计数器。

## v0.3.0 变更摘要：控制面由 MQTT 迁移到 TCP

### 迁移映射

| 早期草案（MQTT） | v0.3.0（TCP） | 说明 |
|------------------|----------------|------|
| Broker + Topic `/jiayi/fsp/{role}/{client_id}/{action}` | 直连 TCP 控制连接 | 连接即身份边界 |
| Broker ACL 隔离 `client_id` | 连接绑定唯一 `device_id` + 握手认证 | 见 21 章 |
| MQTT QoS 1 + 幂等要求 | TCP 可靠有序；仍要求控制消息**语义幂等** | 防实现层重发 |
| MQTT 持久会话（断线消息补发） | **删除**；重连时由 `login` 恢复列表 + `login_ack` 权威快照重建 | **原子整体替换** |
| `status` + retain + 遗嘱（Last Will） | **删除**；在线状态 = 连接存续 | 连接状态即在线状态 |
| 会话世代 `epoch`（对抗陈旧补发消息） | **删除**；TCP 无补发，快照取代增量 | 见下 |
| `login` / `login_ack`（纯认证） | `login`（含恢复列表）/ `login_ack`（含权威快照） | 一次往返完成「认证 + 重同步」 |
| `resume_session` / `resume_ack`（断线恢复） | 断线恢复并入 `login`；`resume_*` 仅保留**暂停后恢复** | 两条路径语义一致 |
| MQTT 服务属性表（QoS/Retain/LWT/持久会话/最大报文长度） | 帧格式表（长度前缀、`max_frame_len`、`TCP_NODELAY`） | 见 06 章 |
| 22 章「MQTT Topic 规范」 | **整章删除** | 无 Topic 体系 |
| 21 章 Broker ACL 配置示例 | 21 章重写为连接级认证与三层访问控制 | `examples/mosquitto/` 一并删除 |


### 附带收益

| 项 | 早期草案（MQTT） | v0.3.0（TCP） |
|----|------------------|----------------|
| 部署组件 | Broker + Server | **仅 Server** |
| 断线恢复往返 | `login` + `resume_session` + `resume_ack`（多次） | `login` + `login_ack`（**一次**） |
| 离线检测 | Broker 遗嘱代发 | TCP 断连 / 心跳超时（**更快**） |
| 多会话并发 | 受 Broker 主题模型牵制 | 一条连接承载 N 个会话，`session_id` 区分 |
| 背压 | Broker 队列（可能无限增长） | TCP 流控（**有界**） |
| 身份校验 | Topic 中的 `client_id` 需与载荷比对 | 连接绑定，**无二次声明** |

## 已知限制

- **不兼容**：v0.3.0 的控制面与早期草案（MQTT）**无法互通** ——
  传输层、帧格式与消息集均已改变。升级**必须**同时升级两端。
- **同一版本号下的两套线路格式**：按上游指示，本次控制面二进制化**未**变更版本号。
  因此 `v0.3.0` 这一版本号在修订过程中先后指代了 **JSON 线路格式**与
  **二进制定长线路格式**两套互不兼容的格式。
  实现**必须**以 06 章正文为准，不得仅凭版本号判断可互通性。
- 控制帧现为**二进制定长布局**（见 06 章）：定长帧头 + 定长区 + 变长区，
  无字段名重复开销。代价是可读性下降 —— 抓包不再自解释，
  实现侧**必须**提供与 `msg_type` 对应的解码日志。
- **同一版本号下的第三套线路格式**：本轮 P0 修订再次改变了线路格式
  （`session_id` 扩为 u64、控制帧新增 `connection_window`、TCP 数据面帧定稿）。
  按上游指示本次修订**未**变更版本号，
  因此 `v0.3.0` 这一版本号先后指代了 **JSON**、**二进制（u32 session_id）**
  与 **二进制（u64 session_id）** 三套互不兼容的格式。
  实现**必须**以 06、07、08 章正文为准，不得仅凭版本号判断可互通性。
- **线路格式尚未冻结（设计阶段）**：本规范处于 **0.x 设计阶段**，
  线路格式仍在演进 —— 本轮即把控制帧与 TCP 数据面帧的帧头
  改为「`magic` + `frame_len` + `header_crc32`」
  （控制帧帧头 8 → **16 字节**，TCP 数据面帧头 20 → **28 字节**）。
  **版本号在设计阶段不承载兼容承诺**：未发布过任何实现，也就没有"互不兼容"的对端。
  实现**必须**以 06、07、08 章**正文**为准；
  历史草案（JSON 载荷、`session_id` = u32 的二进制布局等）**一律不再可用**，
  不得据其实现。
- 断线恢复时，**下载方向**依赖 Client 提供恢复提示。
  若 Client 崩溃导致本地位图丢失且无法重建，
  该会话只能以 `SESSION_NOT_FOUND` / `SESSION_ABORTED` 失败。

## 待定议题

### 控制帧的紧凑二进制编码（已结项）

- **结论**：**已实施**。控制帧改为**二进制定长布局**（见 06 章「帧格式」与「消息体布局」）。
- **落地形态**：`u32 magic | u32 frame_len | u32 header_crc32 | u8 msg_type | u8 flags | u8 body_version | u8 reserved | body`，
  消息体 = 定长区（表格式偏移/大小）+ 变长区（顺序固定）；全部小端序；
  帧头 **16 字节**（`magic` = `0x574E414C`，`header_crc32` 覆盖帧头其余 12 字节）。
- **扩展规则**：同一 `msg_type` 的定长区**一旦发布即冻结**；
  新增字段只能追加在**扩展区**（变长区之后的尾部字节），接收方**必须**忽略扩展区。
  这取代了原先「忽略未知字段」的 JSON 约定。
- **配套变更**：`file_hash` 改为 32 字节原始 Blake3；`session_id` 统一为 `u32`；
  `result` / `direction` / `state` / `mode` 改为 `u8` 枚举；`proto_version` 改为三个 `u8`；
  错误码仍以符号名字符串承载（低频、需人工判读，不做数值化）。
- **保留的代价**：可调试性下降；实现侧需自备解码日志与抓包工具。

### TCP 数据面通道

- **现状**：UDP 主通道 + TCP 兜底（见 05、07 章）。
- **议题**：是否将 TCP 提升为数据面主通道。
- **收益**：可删除 07 章的 PROBE 握手、11 章的 `window` / AIMD、
  18 章的缺失分批与 08 章的包级 CRC32；吞吐不再受窗口大小与信用节奏的限制。
- **代价**：失去乱序写能力（TCP 交付有序），恢复起点退化为连续水位线；
  且移动端 WiFi 的丢包**不等于**拥塞，TCP 拥塞控制的误判会显著降速
  —— 而本协议的移动端客户端正依赖 UDP + 发送端本地 AIMD 规避这一点。
- **倾向**：维持 UDP 主通道。

### TCP 降级通道的线路格式（已结项）

- **结论**：**已实施**。TCP 数据面帧格式见 07 章「TCP 数据面线路格式」。
- **落地形态**：`u32 magic` + `u32 frame_len` + `u32 header_crc32` +
  `u64 session_id` + `u32 chunk_id` + `u16 payload_len` + `u16 flags` + payload；
  全部小端序；帧头 **28 字节**；**不携带载荷级 crc32**（TCP 已提供字节流校验），
  但帧头携带 `header_crc32` 用于帧同步与失步检测。
- **绑定帧**：`FLAG_BIND` 帧承载 `session_id`，用于把 TCP 数据面连接绑定到
  具体会话并完成权限校验（见 07 章）。
- **语义对齐**：chunk 边界、偏移映射、位图与裁决语义与 UDP 通道一致。

### 发送节奏的规范默认值方向（已结项）

- **结论**：`burst_size` 初值 = **min(256, `window`)**，与 `window` 解耦；
  `batch_gap_us` 初值 2000µs；`window` 规范默认值 8192、`connection_window` 16384
  （见 11 章）。默认突发约 300 KB，AIMD 仍为推荐性发送端策略。

### 缺失列表的编码效率

- **现状**：18 章规定单条 `missing_chunks` 最多 4096 条，逐个 `chunk_id` 编码。
  100 GB 文件缺失 1% 时需 217 批，按每批一个裁决周期计约 10.9 秒的串行地板。
- **待办**：评估 bitmap / range 编码（并为裁决引入 `snapshot_version`）。

### 写盘错误必须立即上报（已结项）

- 本地存储失败须按 10 章「终止权」报告，不进入内容重传。

### 离线投递队列

- **现状**：主动投递**只**发生在控制连接存续期间；
  Client 离线时 Server 无法投递（09 章）。
- **待办**：评估是否引入 Server 侧的**待投递队列**（Client 重连后补投），
  以及队列的容量、过期与去重策略。

### 接收方的接受策略

- **现状**：协议只定义「接受 / 拒绝」的**表达方式**
  （`delivery_response` + `DELIVERY_DECLINED` / `STORAGE_FULL`），
  具体策略（自动接受、询问用户、配额上限、静默时段）属产品决策。
- **待办**：由实现定义策略，并在 `delivery_response.code` 中给出可区分的原因，
  以便 Server 侧做退避决策。

### 下载方向的秒传（可选扩展）

- **现状**：秒传路径只覆盖**上传方向**（Server 侧已有相同 `file_hash` 的文件）。
  下载方向没有等价机制 —— 客户端本地已有该文件时，只能自行跳过下载，
  Server 侧的素材记录不会被更新。
- **待办**：评估是否在 `download_start` 中增加「本地已有该文件」的声明位，
  使下载方向也能走秒传路径。

### 分块摘要清单（可选扩展）

- **现状**：摘要对帐已能在**零内容流量**下定位差异区间并定点修复，
  代价是每端约 2N 的读盘与哈希。
- **待办**：评估「一次性下发分块摘要清单」（1 MB 粒度约 0.1% 流量，
  chunk 粒度约 0.67%）的收益 —— 它能把定位成本降到一次哈希，
  代价是多一个协议产物与存储开销。当前**不纳入**规范。

### 数据面的身份认证

- **现状**：数据面只有 CRC32，它**不提供**身份认证
  （见 20 章）。当前安全模型以「可信局域网」为前提。
- **待办**：若部署场景扩展到不可信网络，引入基于会话密钥的 AEAD
  （如 AES-GCM / ChaCha20-Poly1305）与 nonce / 代际机制。

### 恢复列表与权威快照的帧长上限（已结项）

- **结论**：**已定案** —— 采用「**限制单连接并发会话数**」方案，
  **不**引入 `login_ack` 分页，**不**提高 `max_frame_len`。
- **内容**：新增规范常量 `max_sessions_per_connection` = **64**（见 09 章）：
  一条控制连接上的**并发**会话数**必须** ≤ 64；
  `login.resume_count` 与 `login_ack.sessions_count` **必须** ≤ 64
  （06、13 章同步），超限时 Server 以 `session_abort`
  （`reason` = `TOO_MANY_SESSIONS`，见 19 章）拒绝**新发起**的会话。
- **为何选它**：64 条快照最大 2,688 字节、64 条恢复列表最大 1,280 字节，
  **远小于** `max_frame_len`（1 MiB）——
  「快照必须一帧内完整」由此**恒可编码**，
  而 u16 计数器的值域不再构成实际约束。
- **代价**：单条连接的并发会话数被限制在 64。
  该限制在现实规模下宽松（一个连接承载 64 路并发传输已属极端），
  且**不影响**已终止会话的历史数量。
- **未采纳**：②`login_ack` 分批（需改线格式与协议语义，
  留作将来「大集群 / 多租户」形态的预案）；③提高 `max_frame_len`
  （单帧内存占用上升，且未给条目数硬上限，属治标）。

### window / burst_size / credit_batch 的规范默认值（已结项）

- **结论**：`window` 规范默认值 **8192**、`connection_window` **16384**；
  `burst_size` 初值 = **min(256, `window`)**，与 `window` 解耦；
  信用批阈值 `credit_batch` 规范取值 `clamp(window / 8, 16, 1024)`（见 11 章）。
- **说明**：窗口推进由事件驱动信用承担，吞吐上界为
  `min(D, window / (d + K / D))`，固定墙钟周期不再进入除式。

### 秒传与并发会话的优先级（已结项）

- 先复用同方向的活跃会话，再判断授权与秒传条件；`asset_id` 随最终回执交付。

| `proto_version` 曾为 `"major.minor.patch"` 字符串 | 06 章 `login` / `login_ack`、08 章版本比较规则 —— 改为三个 `u8` |
| 转移表曾只有发送侧的 `NEGOTIATING → TRANSFERRING` | 10 章「每个视角都必须能从 INIT 走到 COMPLETED」—— 保留论证 |
| 发送节奏曾有「逐包 2–5ms」与「批量」两种口径 | 11 章「发送节奏」—— 统一为批量读法 |
| AIMD 曾直接收缩协议层 `window` | 11 章 AIMD 小节 —— 明确只调本地 `burst_size` / `batch_gap_us` |
| AIMD 曾用单次 tick 差值估算丢包率 | 11 章「估算约束」—— 明确用滑动窗口累计值 |
| 曾无「请求缺失列表」的消息 | 06 章 `mode=request` —— 保留 `report` / `request` 的区分 |
| 保底轮询曾另有 2 秒周期、看门狗曾另有 3 秒周期 | 11 章判据第 4 条 —— 统一为单一 1000 ms 规则 |
| 「消息丢失」与「连接断开」曾未区分 | 12 章「连接断开的语义（规范性）」—— 统一为「断连 = 中断 = 可恢复」 |
| 缺失列表上限曾未规定 | 18 章「缺失列表的下发上限（规范性）」—— 固定 4096 + `missing_count` |
| 控制面安全曾依赖 Broker ACL | 21 章 —— 改为连接绑定 + 握手认证 + Server 侧校验 |
| 身份一致性曾以 Topic 字段为准 | 23 章 —— 改为与认证主体直接比对 |

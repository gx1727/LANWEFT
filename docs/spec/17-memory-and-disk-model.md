# 17 存储与内存模型

## 目标

- 支持 GB 级文件
- 内存占用与文件大小**解耦**
- 支持乱序写与中断恢复

## 临时文件（规范性）

- 接收方**必须**为每个进行中的会话创建**临时文件**，
  其路径**必须**与最终文件路径相区分。
- 临时文件**必须**被标记为「未完成」（incomplete）——
  在会话提交前，临时文件**不得**出现在最终位置。
- 临时文件**可以**预分配（稀疏文件），以避免写入过程中的空间分配开销。

## 写入语义（规范性）

- 第 `chunk_id` 块的数据**必须**写在文件偏移 `chunk_id × chunk_size` 处。
- 重复写入同一 `chunk_id` **必须**是幂等的（允许重复覆盖）。
- 最后一个 chunk 的实际长度**可以**小于 `chunk_size`（见 08 章）。

> **与加密的约束**：应用层加密**不得**改变 chunk 与文件偏移的映射关系
> （见 20 章「数据面」）。

## 内存占用（推荐性）

- 常驻内存**应当**只包含：数据面 payload 缓冲、位图、会话状态。
- 内存占用**应当**与 `chunk_size` 成正比，
  而**不**与文件大小成正比 —— 这是「内存与文件大小解耦」目标的直接体现。

## 完成与提交（规范性）

完整流程见 12 章「完整性校验」与 10 章「秒传路径」，要点：

- 位图全真 → 计算全文件 Blake3 并与 `file_hash` 比对
  （`file_hash` 为 **32 字节原始 Blake3 摘要**，`hash32` 类型，见 06 章「基本类型」）
  → 通过后**原子重命名**为最终文件名 → 标记完成
- 原子重命名**必须**是同一文件系统目录内的 `rename(2)` 操作，
  以保证读者看到的要么是旧文件、要么是完整的新文件，
  不存在中间态。
- 提交前**必须**已持久化位图与临时文件（见 09 章「持久化」），
  否则重命名后无法回溯校验依据。

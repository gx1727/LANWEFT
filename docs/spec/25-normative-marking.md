# 25 非规范性内容标注规范（Normative Marking）

## 目的

本规范区分三类内容，读者据此判断某段文字是否具有约束力：

| 类别 | 含义 | 约束力 |
|------|------|--------|
| **规范性** | 协议要求 | 违反即为实现错误 |
| **推荐性** | 强烈建议 | 偏离时**应当**说明理由 |
| **非规范性** | 背景说明、实现建议 | **不承载**规范性效力 |

## 标注方式（规范性）

- 非规范性内容**必须**显式标注，标注形式为以下之一：
  - 章节标题后缀：`## 章节名（非规范性）`、`## 章节名（推荐性）`
  - 章节开头的引用块：`> **非规范性（Non-Normative）**：……`
- 规范性要求（含「必须」「不得」「应当」）**必须**写在正文，
  **不得**藏在引用块（`>`）中。
- **设计理由**（为什么这样规定）**不**是规范性要求，
  **应当**以「说明」小节或正文段落呈现，与要求区分开。
  典型写法：`## 为何必须固定变体（说明）`。

## 规范性用语的强度

| 用语 | 强度 | 违反的后果 |
|------|------|-----------|
| **必须 / 不得** | 强制要求 | 实现错误 |
| **应当** | 强制要求（允许有充分理由的例外） | 实现错误；例外**应当**有记录 |
| **建议 / 推荐** | 强烈建议 | **应当**说明理由 |
| **可以** | 允许但不要求 | 无 |

## 协议与实现的边界（规范性）

本规范是**协议设计说明书**，**不得**用具体实现定义互操作要求。
因此规范正文**不得**出现：

| 禁止出现在正文的内容 | 原因 |
|--------------------|------|
| 编程语言、库、框架名称 | 与协议语义无关 |
| 私有 API、数据结构的内部形态 | 实现自由 |
| 源码路径、仓库地址 | 属于工程组织，不属于协议 |
| 「参考实现采用 XX 写法，因此本协议规定 XX」 | 倒因为果 |

**判断准则**：该陈述若换成另一种语言或另一个实现就不成立，
则它**不**属于协议正文。

协议相关的**存储**或**算法**要求**应当**写成与实现无关的能力描述。
例如，位图的内部组织可以是任意位宽的字数组，
但协议只要求「能判定某 `chunk_id` 是否已接收」——
这条写成能力约束（见 18 章），而非数据结构规定。

若某项实现细节**确实**具有互操作意义（例如线上的字节序、字段偏移），
则它**必须**以**协议事实**的形式陈述，
**不得**以「参考实现如此」的形式陈述。

## 与前一版本对比的措辞（规范性）

规范正文陈述的是**当前**协议。因此正文**不得**：

- 使用「改由」「取代」「不再」「原本」等与前一版本对比的措辞；
- 引用协议中**已不存在**的概念（已移除的消息、字段、传输层组件）。

**判断准则**：该句若把「前一版本」替换成「当前版本」，是否仍然成立？
若不成立，说明它在陈述**演化**而非**协议** —— **必须**改写为直接陈述当前规则，
或移入 26 章「修订记录」。

例：

- ✗「TCP 控制通道**没有 Broker**，跨 `device_id` 的隔离**改由**以下三层承担」
- ✓「跨 `device_id` 的隔离**由**以下三层承担」

## 站点页面的内容效力（规范性）

站点页面（`docs/site/`）是本规范的可视化导读，属**非规范性内容**：

- 站点页面的呈现**不得**改变规范结论的强度 —— 源文写「必须」，站点**不得**弱化为「建议」。
- 站点页面**不得**引入源文没有的字段、数值或结论；数值类内容**必须**取自源文。
- 站点与源文不一致时，**以源文为准**（见 00 章「站点与源文」）。
- 站点正文由 `scripts/render-site.py` 从源文渲染，**不得**手工转抄 ——
  手工转抄造成的漂移不构成规范修订。

## 与 00 章的关系

00 章规定了本规范的基本约定；本章展开其判定细则并给出标注形式。
两者冲突时以本章为准。

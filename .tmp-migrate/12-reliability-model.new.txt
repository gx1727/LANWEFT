12 可靠性模型（Reliability）
本章要点：可靠性由「裁决 + 完整性校验 + 重传 + 中断恢复 + 完成与提交」五层构成。
接收方必须至少每 50 ms 下发一次 missing_chunks
（mode=report），包括缺失列表为空的情况；
发送方每 1000 ms 至少索要一次裁决 —— 看门狗与保底轮询使用同一个索要规则。
控制连接断开不得直接置为 ABORTED；文件级失配必须走恢复阶梯
① 摘要对帐 → ② 复核轮 → ③ 中止，每一级至多一次。
分层保障
可靠性分层（自下而上）
① 缺失裁决与位图 · 控制面统计缺失并下发 missing_chunks（mode=report）；接收端乱序写盘与位图
② 完整性校验 · crc32 包级 + 文件级 Blake3
③ 重传 · UDP 不即时重传；聚合缺失后统一下发；重传优先级高于新数据
④ 中断与恢复 · 不回滚已写入；恢复后加载位图并补传缺失
⑤ 完成与提交 · bitmap 全真 → 校验 hash → 原子重命名 → 发布完成消息
自下而上：裁决与位图是推进依据，包级 / 文件级校验负责完整性，重传与恢复负责补齐，最后才进入提交。

裁决是唯一的推进依据（规范性）：接收方必须至少每 50ms 下发一次 missing_chunks
（mode=report），包括缺失列表为空的情况；发送方据此推进窗口。
详见 11 章「窗口推进判据」。
missing_chunks 的 mode 为 enum8（0 = report、1 = request）；
chunks 为 chunk_list（u32 条数 + u32 chunk_id 数组，升序），
「缺失列表为空」即 chunk_list 的条数为 0；missing_count 为位图中
尚未收到的 chunk 精确总数（u32），不是本批 chunks 的长度。
见 06 章「missing_chunks」。
保底轮询（Keep-Alive Polling）
Client 发送完全部数据后，若 Server 持续返回 missing_chunks（mode=report）
且 chunks 为空、未置复核轮标志（即「没有缺失」而非「全部重发」），
但始终未下发 upload_complete，Client 进入保底轮询状态。
保底轮询使用 11 章判据第 4 条的同一个 1000 ms 索要规则：
Client 必须按该周期发布 missing_chunks（mode=request）
持续索要缺失列表，直至收到 upload_complete 或触发超时。
目的：防止对端状态机卡死导致的会话悬挂。
连接断开的语义（规范性）
控制连接断开时，该连接承载的全部会话必须视为中断（可恢复），
不得直接置为 ABORTED：
断连不回滚已写入的数据，位图与临时文件必须保留。
Client 重连后通过 login 的恢复列表恢复（见 13 章）。
会话活动超时（60 秒）可停止传输，不得据此判定远端提交失败；资源回收与最终结果分别按 09、13 章处理。
断连原因按 19 章分类记录：连接被关闭 → CONNECTION_CLOSED；
心跳超时 → TIMEOUT_HEARTBEAT；链路层异常（不可达、复位等）→ NETWORK_ERROR。
看门狗（Watchdog）
看门狗的职责与 11 章判据第 4 条的索要规则完全一致：
发送方每 1000 ms 至少索要一次裁决，直到收到 mode=report 为止。
重复的 mode=request 是幂等的，与幂等要求兼容
（见 06 章「未识别消息必须忽略，保持幂等性」）。
完整性校验
包级
每个 UDP 数据包尾部携带 CRC32，覆盖 16 字节头部 + payload
（见 08 章）；校验失败直接丢弃，不得写入位图。
TCP 数据面帧不携带 CRC32 —— TCP 已提供字节流校验与可靠重传
（见 07 章）。
缺失块的定点补发（规范性）
本协议不采用逐包 ACK，而采用「位图 + 缺失裁决」。
因此包级校验失败不会导致整文件重传：
校验失败的包被丢弃 → 对应块不标记位图 → 该块保持「未收到」状态；
接收方必须通过常规缺失裁决（missing_chunks，mode=report）
报告该块；
发送方必须按 11 章的「重传优先级高于新数据」只补发该块。
单次校验失败的代价是一个块，与文件大小无关。
包头被损坏导致该包的 chunk_id 不可信时，归属由位图裁决自动恢复：
真正丢失的块本来就未被标记，裁决必然把它报出来。
文件级
传输完成后，接收方计算全文件 Blake3 哈希，与请求中的 file_hash 比对
（file_hash 为 32 字节原始 Blake3 摘要，hash32 类型，非十六进制串）；
一致才进入 COMMIT 并发布完成消息（上传方向 upload_complete，
下载方向 download_complete）
文件级校验失败：不得直接终止会话，必须进入恢复阶梯（见下）。

为何把摘要对帐放在复核轮之前（说明）：复核轮是「把第一次做的事原样再做一遍」，
因此它只修复瞬态故障（发送侧偶发读错、接收侧写入丢失或扇区被重映射）；
对持续性故障（接收侧某一偏移反复写坏）它只会完整地重传一遍文件后再次失败。
摘要对帐是双向比对，既能定位损坏区间，也能区分
「接收方副本有误」与「发送方源文件本就不满足请求」，因而信息量更高、
网络代价更低。
摘要对帐（Reconciliation）
数据修复代号（规范性）：每个会话从代号 0 开始。对帐定位可疑块并清位时切到 1；
全量复核清位时切到 2（允许从 0 直接到 2）。同一会话代号不复用、不回退。
接收方必须将代号、清位后的位图和修复次数作为一次可恢复的更新持久化，再发布新代号的裁决。
更新须与在途写盘串行化：切换生效后，旧代号的写入不得落盘或标位。
发送方按有序控制连接上的 report 设置 DATA 代号；新代号的补发须重新读取源数据，
不得给旧队列中的载荷换标志后重发。位图未清零的正确块继续有效。
目的：在不传输文件内容的前提下，定位「接收方临时文件」与「发送方源文件」
之间的差异区间，从而把修复代价从「整个文件」降到「损坏的那几块」。
适用前提（规范性）：发送方必须仍持有该源文件，
且其 size 必须与会话记录一致。
对帐区间（规范性）
对帐以 chunk 为最小单位。区间由 (first_chunk, chunk_count) 唯一确定：
first_chunk（u32）：区间起始的 chunk_id（含）；
chunk_count（u32）：区间包含的 chunk 数。
区间的字节范围为
[first_chunk × chunk_size, (first_chunk + chunk_count) × chunk_size)，
并必须截断到文件末尾（最后一个区间的末尾 chunk 可能不满块）。
区间的摘要（hash32）：该字节范围的 BLAKE3 摘要，
必须与文件级 hash 使用同一算法与同一输出长度（32 字节）。
因此，根区间（first_chunk = 0，chunk_count = chunk_count）的摘要
恒等于该文件的文件级 Blake3 摘要。
消息与方向（规范性）
reconcile_request（0x14）：接收方 → 发送方，携带待比较的区间列表；
reconcile_response（0x15）：发送方 → 接收方，携带各区间在发送方侧的摘要。
发布方恒定：请求方恒为接收方，应答方恒为发送方
（与 missing_chunks 的方向规则同源，见 06 章）。
流程（规范性）
接收方在 VERIFY 阶段检测到文件级失配 → 必须先尝试摘要对帐
（至多一次，见「上限」）；接收侧状态必须由 VERIFY 退回 TRANSFERRING
（见 10 章）。
接收方发布 reconcile_request，第 1 轮只携带根区间，
并置 flags.bit0（根轮标志）。
发送方收到请求后：
- 必须校验源文件的 size 与会话记录一致；不一致时必须置
reconcile_response.flags.bit0（源文件已变更）且不计算任何摘要；
- 必须为请求中的每个区间读取源文件的对应字节并计算 BLAKE3 摘要，
然后以 reconcile_response 返回。
接收方收到应答后，必须用临时文件的对应字节独立计算摘要，
并与应答中的摘要逐区间比对：
- 根区间一致 → 双方文件内容相同 → 请求的 file_hash 与实际文件不符
→ 接收方必须发布 session_abort（reason = SOURCE_FILE_MISMATCH）
并终止会话，不得进入复核轮；
- 根区间不一致 → 继续第 5 步。
下降：接收方必须把每个「不一致」的区间二等分为左右两个子区间
（左半 = 前 chunk_count ÷ 2 个 chunk，右半 = 其余），
组成下一轮的待比较区间集合。同一轮的所有区间必须同层。
二等分规则由 (first_chunk, chunk_count) 唯一确定，双方无须协商。
重复第 3–5 步，直到某区间的 chunk_count 达到最小粒度
（规范取 1，即定位到单个 chunk）；该 chunk 即为可疑块。
接收方必须把全部可疑块的位图位清零（置为「未收到」），
随后按常规缺失裁决（missing_chunks，mode=report）报告它们；
发送方必须按 11 章的「重传优先级高于新数据」补发这些块。
修复阶段不引入任何新消息 —— 复用既有的位图与裁决机制。
补发完成后，接收方必须重新计算文件级 Blake3；通过则进入 COMMIT，
否则转入复核轮。

三者互不叠加，且在进程重启后不得重新获得机会

边界情形（规范性）
源文件已变更：reconcile_response.flags.bit0 置位时，
接收方必须中止对帐并转入复核轮（源文件已变，复核轮同样会失败，
但复核轮是最后一级）。
请求被拒绝：reconcile_response.flags.bit1（请求超限）置位时，
接收方必须中止对帐并转入复核轮。
对帐不可用：发送方不实现摘要对帐（收到请求后不回应答）时，
接收方必须在等待超时后转入复核轮，不得无限等待。
本地 I/O 失败：接收方在回读临时文件计算区间摘要时遇到 I/O 错误，
必须发布 session_abort（reason = FILESYSTEM_ERROR）终止会话，
不得把它当作「内容不符」。
区间摘要一致但文件级失配：只可能发生在根区间，
此时必须按第 4 步判定为 SOURCE_FILE_MISMATCH。
对帐期间的连接中断：对帐计数随会话元数据持久化（见 09 章），
恢复后不得重新获得一次对帐机会；恢复流程按 13 章执行。
代价说明：每轮比较两个半段（否则无法确定该往哪一侧下降），
因此单次对帐的读取与哈希总量约为 2N（N 为文件大小），
而网络流量仅为每区间 32 字节。
它与复核轮的取舍取决于「链路速度」与「本地磁盘 + 哈希速度」之比：
1 Gbps 链路上全量重传 100 GiB 约需 859 秒，而对帐约需 143 秒（每端）；
10 Gbps 链路上则相反。因此对帐不取代复核轮，而是它的前置一级。
复核轮（Re-verify Round）
复核轮是恢复阶梯的第 ② 级：当摘要对帐无法定位、或对帐后仍失配时启用。
文件级失配意味着「接收到的字节整体不等于源文件」。
若一个包已经损坏，且错误的 CRC 余数近似均匀，漏检的条件概率约为 2⁻³²。
实际漏检率还取决于包损坏率与差错模式，不能仅凭文件大小推出。
文件级校验还覆盖包校验之后发生的写盘差错。
未检出的损坏会一路存活到文件级校验，从而触发恢复。
复核轮的手段是：重新读取源文件并全量重发 ——
它是最后一级的有界手段（代价为一个完整文件），
因此必须在摘要对帐之后才启用。
前置条件（规范性）：接收方必须已完成一次摘要对帐，
或因对帐不可用（发送方拒绝、源文件已变更、对帐超限）而无法进行对帐；
不得跳过对帐直接进入复核轮。
接收方（规范性）：
接收方必须进入复核轮，不得立即发布 session_abort。
接收方必须清空位图（全部块置为「未收到」），临时文件保留
（复核轮将覆盖写入相同偏移）。
接收方必须发布 missing_chunks（mode=report）并置复核轮标志
（flags.bit1 = 1）；该条裁决的 chunks 必须为空列表，
missing_count 必须等于 chunk_count（见 06 章）。
接收方必须记录复核轮计数，并必须将其与位图一同持久化
（见 09 章「持久化」），使进程重启后不得重复使用复核轮。
复核轮结束后，接收方必须重新计算文件级 Blake3 并再次比对。
发送方（规范性）：
收到带复核轮标志的裁决时，发送方必须按 11 章判据第 3 条
「复核轮」条目重置顺序流与在途量基线。
发送方必须重新打开源文件并重新读取内容 ——
不得复用先前已读入内存或页缓存中的旧副本；
发送方应当绕过操作系统页缓存重新读取（实现建议）。
发送方必须从 chunk_id = 0 起全量重发。
发送方必须对同一会话最多响应一次复核轮。
终止条件（规范性）：
复核轮结束后文件级校验仍失配 → 接收方必须发布
session_abort（reason = FILE_HASH_MISMATCH）终止会话。
此时源文件确实不可读或已被改动，已无可恢复的手段。
复核轮至多一次：接收方不得对同一会话发起第二次复核轮。
为何不立即终止（说明）：文件级失配一律立即终止，会让一个刚传完的百 GB 文件
因为一次瞬态读写错误而被丢弃。复核轮允许在同一会话中重新校验和提交。
复核轮至多一次的约束保证了最坏情况下的代价上界是两次传输，
而不是无限重试。
复核轮能修什么、不能修什么（说明）：复核轮是「把第一次做的事原样再做一遍」，
因此它只修复瞬态故障 ——
发送侧偶发读错（重读即可）、接收侧写入丢失或扇区被重映射（重写同一位置即可）。
对持续性故障（磁盘满、只读挂载、同一个逻辑地址反复失败），
复核轮只会完整地重传一遍文件，然后再次失败并中止。

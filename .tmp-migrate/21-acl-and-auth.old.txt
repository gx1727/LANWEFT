21 访问控制与认证（ACL & Auth）
本章要点：控制通道的认证在连接握手阶段完成，Server 必须在 login 中校验认证凭据，
失败必须以 login_ack（result = 0）回应并关闭连接；
凭据必须与 device_id 绑定。
跨 device_id 的隔离由连接级、Server 级、资源级三层承担。

认证（规范性）
控制通道的认证在连接握手阶段完成（见 06 章「连接生命周期」）。
Server 必须在 login 中校验认证凭据；
校验失败必须以 login_ack（result = 0，即 fail）回应并关闭连接。
凭据必须与 device_id 绑定：认证通过后，连接即与该 device_id 绑定，
该连接上的一切会话必须属于该 device_id。
认证方式必须至少支持以下其一。

访问控制（规范性）
跨 device_id 的隔离由以下三层承担：
跨 device_id 隔离的三层
1 · 连接级
一条控制连接只承载一个 device_id（见 06 章「会话与连接的关系」）；跨 device_id 的会话在协议层无法表达
2 · Server 级
Server 必须校验会话的 device_id 与连接绑定一致；不一致必须以 session_abort（reason = ACL_DENY）拒绝
3 · 资源级
素材记录（asset_id）的所有权由 Server 维护；asset_recall 必须校验发起方的 device_id 对该记录的所有权，越权时回 code = ACL_DENY（见 06 章）

传输安全（规范性）
控制通道必须支持 TLS；应当启用。
未启用 TLS 时，认证凭据以明文传输 ——
不得在非受信网络（含公共 WiFi）中这样部署。
控制通道与数据面相互独立：
数据面不复用控制连接的 TLS 会话；UDP 数据面不自带加密（见 20 章）。
强约束
一条连接必须绑定唯一 device_id。
Server 不得在连接上接受与绑定身份不符的会话。
会话必须绑定唯一 device_id。

常见实现陷阱：把 device_id 直接当作凭据（令牌不得由 device_id 直接推导）；
认证失败后仍然保持连接；用客户端证书时未把 login.token 置为空串；
在公共 WiFi 之类非受信网络上以明文凭据部署。

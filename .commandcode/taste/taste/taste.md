# Taste
- Prefers finished changes be both committed and pushed (to origin/main) before reporting results, rather than pausing to ask "should I commit?" / "should I push?" — the default expectation is the work lands on the remote. Confidence: 0.7
- Validates design claims with throwaway minimal code experiments rather than more prose analysis: repeatedly asks for a "最小实验"/"最小验证" prototype of the current design plus its results ("给我结果就可以了"). Confidence: 0.6
- For non-trivial design/spec changes, wants a written plan (a checklist of required edits, non-goals, and verification) reviewed before any file is touched — says "先不要直接改，列表 plan". Confidence: 0.55
- Wants conclusions and results, not narration of process: asks for "给我结果就可以了" and expects direct recommendations ("最终建议如何修改"), with terse, directive replies. Confidence: 0.55
- Skeptical of representations that add computation for negligible byte savings (e.g. "multiplier/multiplier-offset" encoding vs. plain u16 offsets); prefers the simpler, shorter field layout — dropping redundant fields rather than introducing new abstractions. Confidence: 0.5
- Prefers capabilities designed as explicit graded levels/tiers with a server-side configurable default (e.g. security lv1 CRC32 → lv2 BLAKE3 keyed MAC → lv3 AEAD, switchable by config) instead of one hardcoded policy; the default must stay at the lowest/current tier for backward compatibility rather than the stricter one (corrected a proposal to default to lv2 with "默认使用 lv1 级"). Confidence: 0.65
- Prioritizes throughput/efficiency of the fast path over conservative safety margins: willing to accept known-risky lower-layer behavior (e.g. IP fragmentation of large UDP datagrams) on the assumption of a stable LAN if it cuts per-packet/syscall overhead, and pushes back when limits are derived from worst-case transport constraints — explicitly asks for a "trust mode" that trades "相信" the network for throughput. Confidence: 0.8
